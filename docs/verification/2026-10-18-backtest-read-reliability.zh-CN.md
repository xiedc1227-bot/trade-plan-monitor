## BR-V01 — 已复现原因

独立的历史／任务读取共用一个元数据归属者，发生重叠就立即拒绝，即使是正常页面读取。确定性重叠测试复现了缺少读取准入的问题。实际测量约为：运行历史 555 ms、任务 64 ms、数据集 69 ms、已审核计划库 2483 ms。最初 1 秒等待读取仍在实际五路并发中失败；最终准入等待为 5 秒，最多 8 个等待读取，仍使用既有单个物理线程。过载继续有界并明确提示。

真实后端／Chrome 准备流程复现了此前 10000 ms 候选就绪失败。捕获的 GET 返回 200、`CANDIDATE`、修订 9，而界面仍保留提取中／读取错误状态。前端封闭候选字段漏掉了已发布的 `confirmationSummary`。尝试字段也漏掉了既有可选 `repair_feedback` / `repair_context_json`，已通过独立传输测试复现。另外，终态摘要后的临时详情读取失败会停止自动恢复。恢复计数在接受摘要时过早重置，不能可靠限制完整读取的恢复次数。

接收有效候选后，流程又暴露旧记录阻断：存在汇总时隐藏了必需补充控件，但提交校验仍要求这些值。现继续展示对应控件，没有移除审核要求。已与原文绑定的明确值不会转成缺失原文问题。不改变交易或提取语义。

实际四份计划页的视觉复核又发现 HTTP 合法但传输校验不通过的情形。完整详情页为 2007934 个 UTF-8 字节，却有 58137 个 JSON 节点，超过浏览器既有的 50000 节点预算；单个候选均有效。服务端投影现将同一节点预算、32 深度与 2 MiB 一同执行，既有自适应分页先返回前 3 项，再从偏移 3 返回剩余一项。没有提高阈值，也没有截断原文／证据。红／绿回归覆盖字节未超限但节点超限的页面。
