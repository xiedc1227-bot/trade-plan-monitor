# A05 Historical Index Permission Recheck (Offline)

## Scope

The installed monitor may recheck a persisted `idx_mins` permission block at an independent `INDEX_PERMISSION` deadline. Existing `INDEX_RECOVERY` deadlines remain for index retries. The probe uses the controller's durable 300-second reservation, shared cooldown, single physical worker, and pacing. It calls only `idx_mins` for a `READY` SSE index with a persisted, completed SSE open-day anchor from the preceding seven calendar days. It requires the frozen, unexpired `BOARD_INDEX` semantic revision, `idx_mins` interface scope, and current configuration, generation, and admission authority before reservation, at queue admission, at the physical worker start, and before permission is cleared. A stale binding or unavailable SSE capability requires a safe restart; it does not authorize a probe.

## Response and scheduling rules

- The request uses `freq="5min"`, exact anchor-day `09:30:00`–`15:00:00`, and the certified index fields. A START-labeled response requires exactly 48 complete regular-session bars. An END-labeled response permits those 48 bars or exactly 49 rows if the sole extra row is the same index and day at `09:30:00`. The extra row has separately checked finite positive OHLC, nonnegative volume and amount, and consistent high/low; it is excluded from completed bars and all caches. Any other schema, identity, timestamp, number, or coverage keeps the block. The prior live report observed 49 rows but did not record the 49th identity, so this rule has not certified that live response or unlocked live use.
- The independent permission deadline works without a current-day calendar or snapshot and does not advance the market-work cursor. A missing trusted anchor causes zero SDK calls and zero durable writes, then a 30-second in-memory defer. Restart restores the original durable due time, allows one immediate check, then defers again. A successful proof clears only the historical permission latch; it does not write business snapshots or fill provider caches. Failure retains the block and reservation.
- An index recovery that would hit a blocked, uncached historical `idx_mins` request is deferred in memory before acquisition. Its persisted cutoff, first failure, due time, and attempt count remain unchanged. Other due indexes with historical data already cached may recover. At an equal due time, `INDEX_PERMISSION` runs before `INDEX_RECOVERY`, allowing the original recovery to run if the proof finishes within its existing five-minute window. If the proof crosses `first_failed_at + 5 minutes`, that original recovery expires under the existing policy; preserving the original cutoff beyond this bound remains an S3-05/full A05 gap. Permission admission uses the existing 15-second queue timeout, 15-second physical timeout, and 1.25-second pace as a 31.25-second guard before a known market deadline or a possible deadline on an unknown-calendar weekday. The owning event loop freezes a bounded market window; queue and SDK worker checks use that immutable window without a worker-thread calendar or SQLite read. At `10:05:11`, the installed runtime loop defers permission maintenance and executes the `10:05:12` market task first. A queued or not-yet-started probe yields without a physical call or permission-failure backoff; an already reserved 300-second retry remains reserved. Queued configuration and semantic-file changes revoke admission even after the original file is restored. An already-started SDK call that unexpectedly crosses one or more market deadlines still requires explicit pending/degraded handling. A05 is not yet closed.

## Offline verification

Focused integration tests cover valid 48/49 responses, invalid extras and incomplete responses, exact request arguments, no cache or snapshot write, independent wake without a current-day calendar, missing-anchor restart behavior, semantic/configuration/generation/stop and cross-day guards, controller cooldown and failure retention, and process-only retry deferral. No real Tushare call, external notification, user database migration, deployment, or push was used.
