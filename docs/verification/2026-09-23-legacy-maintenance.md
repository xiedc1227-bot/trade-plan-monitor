## Scope and result

The approved D8/A13 missing-heartbeat resolution is connected through the production Web composition and system page. Active plans with no heartbeat enter `BLOCKED`, not an endlessly stale/recovering display or an automatic plan replay. The Web service remains available, but monitor tasks, provider requests, heartbeat and alert dispatch do not start; ordinary HTTP mutations return `409`. A preview lists exact active plan identities and a fingerprint. A separately checked confirmation atomically invalidates those plans, clears/audits pending closes, suppresses existing delivery eligibility and records a batch audit. Holdings and confirmed trades are not changed. The operator restarts the tool before creating new plans.

## Terminal-receipt transaction primitive

`DeliveryEligibilityRepository.suppress_invalidated_identity` now validates the canonical alert against an exact plan identity, initializes a missing HOLD receipt, and advances it to terminal `SUPPRESS/ACTIVE_IDENTITY_INVALID` with two revisioned audit records in the caller's transaction. A mismatched identity writes nothing; repeated suppression is idempotent; rollback restores an existing HOLD. The reader now accepts this generic invalidation reason for legacy alerts, fixing the prior contradiction with long-outage/manual bulk suppression while retaining rejection of explicit-only terminal reasons. Focused RED tests first failed on the absent method. `tests/integration/test_delivery_eligibility_storage.py`, `tests/unit/test_legacy_recovery_delivery_eligibility.py`, and `tests/integration/test_runtime_plan_expiry.py` then passed together: 116 passed, one existing warning. Ruff and diff whitespace checks passed.

The later connected batch below uses this primitive. Scanning all old alerts inside startup would make restart duration depend on historical volume and malformed rows; the existing current-plan send gate remains the immediate safety boundary. V1d and business step 1 remain open. No user database or external sender was touched.

## Bounded post-admission old-alert sweep

Startup freezes only the indexed highest alert sequence. Each subsequent 30-second liveness heartbeat may inspect at most 100 older alerts in sequence order, then advance its in-memory cursor only after the receipt/audit transaction commits. Each batch must still own the just-written liveness revision, so a superseded runtime generation cannot write cleanup state. It matches the canonical alert's plan ID/version/hash/symbol against a superseded `PlanVersion` and a deactivation audit with the exact >120-hour or manual-legacy cause; ordinary deactivation alone is not enough. A terminally invalidated version is also refused at activation, so reusing its original identity cannot make old alerts current while cleanup catches up; normal reactivation remains allowed. The per-alert terminal record never claims that an earlier external delivery did not occur. A malformed canonical alert or corrupt metadata receives a stable, payload-free `ALERT_INVALIDATION_UNCLASSIFIED` audit instead of a guessed receipt. A transient sweep failure rolls back that batch and is retried without preventing the heartbeat. Restart may re-scan earlier rows but does not duplicate terminal receipts. The sender's current-plan gate remains the immediate exclusion while cleanup catches up. No schema migration, provider call, sender call or holdings change is part of this increment.
