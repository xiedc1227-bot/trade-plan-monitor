# S3-02 realtime index-minute permission recheck: offline verification

## Scope

`rt_idx_min_daily` has an independent maintenance deadline and durable `INDEX_REALTIME_MINUTES` permission reservation. A migrated legacy `index_minutes` block initially fences both `idx_mins` and `rt_idx_min_daily`; a successful current-day realtime proof clears only the realtime latch. The probe uses a certified ready SSE identity, a currently persisted open SSE day, a completed first five-minute bar no earlier than `09:35:12`, and the existing controller's 300-second reservation, shared 429 cooldown, 1.25-second physical pacing, and frozen market-deadline window. It performs one read-only SDK request without filling index caches or publishing evaluation, alert, delivery, or market-index snapshot rows.

## Response proof

The worker first records a logical admission under the short calendar lock. The provider freezes the completed-bar cutoff immediately before invoking the physical SDK endpoint, after a second authority, epoch, and market-window check. It requests exactly `rt_idx_min_daily` with `freq="5MIN"` and the certified field set. The entire response is bounded to 49 rows and must have exactly one `ts_code` or `code` identity column, unique required columns, optional `freq` equal to `5MIN`, canonical current-day source timestamps interpreted only with the certified `START` or `END` label, no duplicate or unfinished/future bars, finite nonnegative volume and amount, and valid positive OHLC. At least one returned row must represent a completed real five-minute bar. A `09:30` opening snapshot under `END` may accompany real bars but cannot establish permission by itself. Full market-data coverage is a separate business-readiness test, not a requirement for this endpoint-readability proof. A bad row invalidates the entire proof and retains the latch and reservation.

## Calendar version and concurrency

The supported runtime SSE calendar write path is `ProductionMonitorPipeline.refresh_references`, which owns the unit-of-work commit through `_commit_trading_days`. Every such SSE correction, including an identical rewrite, revokes the old token and advances the epoch under a short lock before the attempted write. A successful commit installs the new in-memory calendar and token. A failed transaction leaves the old token revoked; a later owner-thread SQLite read is required before another attempt can arm a new token. The SDK worker only checks the frozen window, current authority, and token under the short lock; it does not read SQLite. A correction before its gate prevents the SDK call. A call logically admitted just before correction can physically begin afterward, but its response cannot clear the latch because the owner rechecks epoch and persisted SSE calendar after the SDK returns. The lock covers neither SQLite nor the SDK call.

## Offline evidence and boundary

Temporary SQLite and a fake SDK cover legacy migration inheritance, successful scope-isolated recovery, malformed and over-limit batches, missing calendar and first-bar deferral, shared 429, physical pacing, queued market-window veto, worker-side no-SQLite checks, same-value correction while queued or in flight, and transaction failure/re-arm. No real Tushare request, user database migration, cache publication, business decision, notification send, push, or deployment was performed. The result proves controlled endpoint readability only; it does not assert actual supplier entitlement or that market-index data are business-ready. Direct external Repository/SQL calendar writes are outside this single-owner runtime commit guarantee.
