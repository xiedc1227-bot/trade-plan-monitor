## R14-P3. Reviewed plan and observation oracle

The source plan remains byte-for-byte the `LITERAL` fixture: `003043.SZ`, BUY 100 only when a **completed** five-minute close is 9.80–10.00 yuan inclusive **AND** that bar's volume is at least 1.5 times the arithmetic mean of the **previous five completed** five-minute bars; SELL 100 at 10.80–11.00 inclusive from registered inventory; pure risk below 9.50. These are historical test thresholds, **not** a claim that they match current prices or a recommendation to trade. The fixture's `humanTestSupplements` explicitly supplies `TRADING_DAY=2026-09-14`, `CONTIGUOUS_TRADING_BARS`, once-per-activation policies and the two conflict choices; none is attributed to the original source. If the approved session moves to 15 or 16 September, including because the 14th is closed, the original literal text may be reused only with a separately reviewed, dated human supplement, not by silently changing the plan. Any alternate price-adapted demonstration plan requires separate user review and budget approval and cannot certify the original thresholds.

Use the regular plan drafting/review/activation UI in the isolated app. Compare the actual Pro extraction against independent source values, clause offsets, missing policies, ambiguity, and unsupported terms before any save or activation. A model output can be syntactically valid yet semantically wrong; a human oracle must mark those fields. Confirm source treatment, current `reviewId`, content hash, expected revision and plan version. Never activate a draft with invented quantities, altered ALL/ANY, unconfirmed supplements or a stale review. Register test-only inventory separately if the SELL branch is to be eligible; no real holdings are read or changed.

Because the app starts with an empty isolated database, the harness watches for the first approved `003043.SZ` activation and invokes the **existing production current-day recovery service once**. This is explicitly `TEST_TRIGGERED_PRODUCTION_RECOVERY` in the audit, uses at most one of the three permitted `rt_min_daily` starts, and is not presented as a natural startup-recovery event. Its persisted one-minute count and error/real-time-yield status must show enough contiguous history for the previous-five-bar oracle; otherwise BUY volume validation remains unverified. Later five-minute evaluations still come from the normal production scheduler and fresh supplier responses.

For every market observation, retain only sanitized audit and local database evidence: endpoint/attempt count, timestamp and row count, `SourceTimeLabel=END`, units (price yuan→fen, volume shares, daily volume×100, amount yuan, daily amount×1000), calendar status, freshness/empty/gap classification, six-bar lineage, completed five-minute cutoff and result hash. **Natural trigger rule:** If no real bar naturally meets BUY, SELL or risk, mark each absent branch `NOT_OBSERVED`; do not inject synthetic bars into a claimed real session, move thresholds, or mark PASS. ## R14-P5. Decision after a real run

Offline wiring evidence is recorded in `remediation/evidence/R14-preparation/offline-wiring.json`. The test enters the real FastAPI lifespan and production composition, sends the three fixed source strings through the ordinary extraction API to a controlled HTTP transport, then uses a **separate synthetic numeric-equivalent shorthand** to exercise the current review/activation API. Its ten scheduler deadlines are selected with the production scheduler but advanced by a virtual clock; the two persisted completed evaluations and 39 physical SDK-query entries come from simulated valid DataFrames. A second launcher test enters the same lifespan through a test-local server adapter, proves a refused `daily` query produces `BUDGET_DENIED`/exit 1, and checks factory restoration and inactive cleanup. The direct SDK transport test verifies 15-second timeout, TLS identity and retries disabled. These tests do **not** run a real Uvicorn socket/browser, prove that the literal AI output can be reviewed to activation, or establish real provider entitlements. Those remain `UNVERIFIED`/`NOT_RUN` until the bounded live session and human review.

- `PASS` for a particular real branch requires a recorded actual request and response, valid current certification and open-day calendar, complete fresh data, correct server evaluation/lineage, and actual local browser receipt with matching IN_APP event. A real AI case additionally requires human comparison with its independent oracle and current review.
- `PARTIAL` records any real valid subsets, while naturally untriggered actions, unavailable permissions, missing model output, expired profile, or unobserved recovery remain explicitly `NOT_OBSERVED`/`NOT_RUN`/`FAILED` as appropriate.
- `FAILED` includes wrong semantic fields, a false alert on incomplete data, stale review activation, incorrect version/event/cutoff/quantity, budget enforcement failure, external send, or a claimed PASS without its evidence. Exit code zero or `NOT_RUN_MARKET_WINDOW` is never a PASS.
