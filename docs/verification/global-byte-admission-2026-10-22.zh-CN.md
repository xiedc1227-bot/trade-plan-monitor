# 全局字节准入 P0 验证报告

[规格](../specifications/backtesting/SPEC-global-evidence-byte-admission.zh-CN.md) · [任务](../specifications/backtesting/TASKS-global-evidence-byte-admission.zh-CN.md) · [测量证据](evidence/2026-10-22-global-byte-admission/measurements.json)

## GBA-V01. 结论

P0 可行性实验已完成；P1 不推进。原型通过共享账本对 SQL 载荷分配进行准入，并保留原校验器，但未通过合法大输入可用性和并发性能门槛。生产保持不变。这不是可直接部署的性能优化。

执行了预先声明的提前停止规则：合法大行无法准入后，未运行固定性能验收。改为保留 1/2/8 读者工作负载的全部 5 轮诊断及 5 轮交替混合诊断，共 60 个批次、195 次请求尝试。其中 170 次成功、25 次失败，失败全部发生在预算线程的 8 读者场景。未替换失败样本。这些小规模诊断分组不能证明 p95 改善。

## GBA-V02. 实现内容

`scripts/experiments` 下的实验模块实现共享 `Budget`、显式租约、快照内 `Scan`、可持续推进的 `Flights`、临时投影适配器、合法大行构造、诊断运行器及进程内变异。没有增加生产注册或配置开关。适配器调用原投影参数规范化/作用域构造，并使用各 repository 原有事务。注入同一个协调器/账本，覆盖实验读取实例，包括临时停止后健康读者。

元信息对全部选中字段使用 `typeof` 和 `octet_length`，检查 UTF-8 能力，采用 32 行分页、每扫描器 128 KiB。载荷查询仅选择已获准定位符并保持原排序。初始工作区为 1 MiB，仅在单行保守上界需要时扩大。默认全局限额仍为 64 MiB。原始输入/传输预留是原子的；比对先取得工作区，再借用证明。等待输入收集的读者仅持有元信息。不匹配比对关闭后才进入唯一排队主请求位置。不缓存完成证明，也不在提交后回退。

大工作区推进测试在收集阶段暂停主请求，同时让 7 个跟随者各申请 16 MiB。等待主请求时，跟随者不能占用这些工作区；收集完成后，获准比对能完成，全部 8 个读者获得证明。游标或子进程清理失败时，保留相应全局租约并关闭新准入。普通回退在预算扫描源上使用完整原校验器；传输回退发生在提交前，对同一份保留字面输入执行校验。

## GBA-V03. 内存与大输入门槛

一条包含 480 根日线、使用受支持十进制精度、规范化且通过完整校验的候选，其 JSON 为 16,472,833 字节，低于 16 MiB 持久化上限。原完整校验器接受它。新方案的保守工作区上界为 296,534,034 字节（282.80 MiB），因此扫描器在任何载荷查询前拒绝它。另一条中等大小合法行成功在子进程提交前回退到线程。接近上限记录被拒绝属于可用性门槛失败，不能仅因没有越界分配就认定优化通过。

普通冻结样本包含 2008 个候选，预检原始输入预留为 39,184,065 字节，此前实测保留量为 30,826,621 字节。8 读者下，进程输入账本达到 65,398,465 字节（62.37 MiB），并排空至零。原生产账本未覆盖相同类别；诊断中新账本在原线程样本中为零，表示它未被使用，并非原线程不占内存。

独立进程内存观测每方案运行 3 次，采用 8 个监控加一个结果读取，每 20 ms 配对读取父子计数。下表数值是同时刻合计量峰值的中位数，不是独立峰值相加。所有运行的最大值仍低于预先声明的 768 MiB 工作集 / 2560 MiB 私有提交量实验上限。采样可能遗漏更短峰值，私有提交量与驻留工作集不同。预算线程运行在 27 次尝试中有 15 次失败，因此不能把它较低的内存解释为等价工作量下的改善。

账本在尺寸假设下约束已计量的 Python 输入工作；SQLite/驱动/分配器的原生边界仍未证明。元信息查询执行、页缓存、内部转换、解析模型及解释器不能由租约高水位认证。通过采样进程上限并不等于证明部署内存上限。

## GBA-V04. 优化前后诊断对比

这些是同一主机/运行时上、冻结只读数据和合成无所有者权威下的完整读取。各轮交替方案顺序，每组包含 5 次观测，诊断计时包含计数器采样。全部成功请求的完整输出哈希一致。失败读取计入次数和批次时长。原线程数据来自本次运行，不是此前传输实验。

预算线程在实测并发分组中丢失了全部共享。8 读者分组里，原线程与预算进程各在多轮中执行 5 个物理证明和 35 次共享；预算线程执行 15 个物理证明，没有共享，并拒绝 25 个请求。实验的立即校验策略没有原主请求的比对协调：跟随者可能在证明完成边界之后才完成比对，随后竞争未改变的唯一排队位置。确定性测试证明这一策略可以推进，但该工作负载中的等价可用性和延迟不达标。

样本每次预算扫描执行 2 次元信息查询和 666 次载荷查询。原扫描使用一个有序载荷查询及按行缓冲。逐列预检、更小分组和重复独立查询增加 CPU 工作。8 读者下，预算进程即使共享相同数量的物理证明，总 CPU 仍约为原线程的 3.01 倍。不能把混合结果耗时下降解释为进程隔离收益：预算线程同样更早返回结果，同时监控完成后移。新的收集工作改变了 CPU 重叠/调度，完整批次与监控行为没有改善。

## GBA-V05. 正确性、取消与审查

最终聚焦测试：23 项通过，耗时 5.30 s。最后补充字面输入测试前的相关回归：116 项通过，耗时 67.11 s，存在既有 Starlette 警告。另一次注入实验适配器的运行中，5 项权威/时间/断连测试通过，耗时 5.06 s，包括临时停止后健康所有权；它在同一注入账本上执行 25 个物理证明、27 次扫描并排空至零。这些数字表示独立运行，不是相加后的唯一测试总数。

覆盖内容包括精确字节准入、等待取消、停止/排空、独立分配、查询前租约、UTF-8/NUL/BLOB 保留、旧/缺失/head/规范化篡改、真实 SQLite 已提交快照之间的字面不匹配、完整预算回退、接近上限合法输入拒绝、中等行传输回退、相同输入共享、大工作区推进、带存储暂停的重复观察者取消、游标清理失败及子进程清理欠额。既有完整校验器和传输测试覆盖物理崩溃/挂起、帧协议及提交后失败。没有删除权威或完整性检查。

全部 3 项进程内变异被检出：提前释放、漏记 SQL 工作区和跳过字面比对。变异没有修改文件。限定范围 Ruff 通过。最初全部 1802 个已跟踪文件和冻结输入哈希保持不变，测量时实验源码指纹与实施完成时源码一致；后续诊断清理修复单独记录于 GBA-V07。没有重启生产服务或清理历史。测试使用本地临时样本，诊断数据不含原始证据载荷。

实施审查在测量前消除了一种潜在等待环：收集阶段的跟随者最初可能先申请大工作区，再等待证明发布；现在等待时不持有该工作区。游标/子进程清理欠额也在测量前接入外层账本。这些修正属于实际测量源码。完成的冻结诊断没有出现已准入字节越界，所有非故障注入运行最终均为零租约，且子进程已退出。这并未解决可用性/性能失败或尚未证明的原生内存门槛。

## GBA-V06. 下一步与复现

不启用 P1，也不增加生产开关。下一轮设计必须先减少大行表示重叠，同时保持字面/规范化检查；恢复已准入跟随者协调，同时不让物理推进依赖未准入工作。只有字节上界仍可成立时，才能减少元信息/载荷查询放大。保持 64 MiB 限额、独立快照/权威、唯一物理校验者/排队位置及取消排空。原生分配及可强制执行的部署内存契约需要另行评估。

使用 `.venv/Scripts/python.exe -m scripts.experiments.global_evidence_benchmark --help`，提供 `--monitor`、`--results`、`--run`、`--output` 运行已声明诊断。`--smoke` 不计入诊断，`--memory` 选择独立进程内存运行。输入必须是带有匹配不可变结果所有权目录的冻结副本。合法大行探针为 `.venv/Scripts/python.exe -m scripts.experiments.global_evidence_large`。可移植证据保留全部尝试、声明列顺序的内存采样、脱敏失败日志、源码/输入哈希及门槛决策。

变更快照正确性已做确定性测试；硬门槛失败后，未运行变更快照 8 读者性能、固定验收、生产组装及真实所有者/浏览器验收。没有启用生产路径。已有 AI 提取和日库存工作保持不变。实施阶段没有提交或推送；后续提交审查已另行获得授权。

## GBA-V07. 提交审查

审查复现了诊断运行器的清理缺陷：读取服务停止或证明排空失败后，非守护内存采样线程仍存活。现在采样器通过外层 finally 块停止并等待退出，同时保留原始失败。两种故障注入在修复前均已复现，修复后通过。没有改变准入、权威或校验器行为。

本次提交回归运行 120 项测试全部通过，耗时 68.62 s，存在 1 项既有 Starlette 警告。限定范围 Ruff 通过，提前释放变异再次被检出。修复后的运行器完成 3 个冒烟批次，全部 6 个请求成功，完整输出哈希一致、剩余预算为零且子进程退出。该冒烟运行与回归运行存在重叠，不计入性能比较。

原始 60 批次诊断数据及测量源码哈希保持不变。证据另行记录当前源码哈希、原始测量运行器源码、回归日志及审查冒烟输出。全部 1802 个原有已跟踪文件和冻结数据库指纹保持不变。提交限定为 20 个 P0 文件，排除 AI 提取和日库存改动。P1 仍不推进，也没有启用生产路径。
