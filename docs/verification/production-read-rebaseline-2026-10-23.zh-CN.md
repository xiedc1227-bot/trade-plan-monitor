## PRR02. 测量方法与限制

基线提交：`c7ba0d4`。开始时没有运行中的项目服务。使用原有配置/数据，在本地启动当前生产组合，启用既有的有界诊断开关。小型启动器只控制正常关闭，并在采样之外获取所有权状态，没有注入参考权威、冻结时钟、实验分配器或替代校验器。

实际状态：`RUNNING / STANDBY / NO_ACTIVE_PLANS`。历史包含 `5` 个运行和 `14800` 条明细。请求选择真实列表中的首个已完成运行。普通单证明路径下，监控读取校验 `2473` 个历史指数候选，保留输入为 `39820239 B`。这些观察不代表正在交易的活跃时段，也不覆盖全部结果规模。

固定运行 `20` 轮，轮换结果单读、监控单读及结果/监控同时读取的顺序：`80` 个 HTTP 响应全部为 `200`。`40` 个结果响应的完整哈希一致。保留全部尝试，包括重试。报告中位数与范围，不报告 p95。

首轮浏览器测量包含直接进入、推迟启动和双页面同时进入，每类 `6` 轮；关页后没有等待物理工作结束，保留为探索性的连续开页负载。独立的受控波次仍固定每类 `6` 轮，每轮开始前等待未完成读取、活动/排队证明所有者、保留字节、存储暂停及 socket 子任务全部归零。正常进入与推迟对照均启用相同的浏览器路由拦截，仅初始 dashboard 请求的发送时点不同。

推迟对照将结果页自己的 dashboard 请求保留到结果视图就绪，再转发给原服务器，并等待响应完整接收。没有模拟响应，也没有把未真实读取的内容视为已校验。此对照估计调度机会，不是已上线候选或正式验收。使用新的浏览器上下文和项目已固定的浏览器。双页面场景同时打开真实监控页，其标题显示时间不代表监控数据就绪时间。

## PRR04. 主要瓶颈与归因限制

结果审计校验是结果侧主要成本：单读耗时中位数 `1.550 s`，并发时 `4.076 s`。结果工作线程 CPU 单读为 `1.875 s`，并发为 `2.086 s`。结果准入等待约 `0.00001 s`，本批样本不支持扩大队列或增加工作线程。

监控完整指数校验中位数为 `2.302 s`，约占监控单读耗时的 `94%`，线程 CPU 为 `2.297 s`。单读时，独立的前后权威检查各约 `0.025 s`。并发时，指数收集耗时从 `0.079 s` 增至 `1.402 s`，但并发收集线程 CPU 只有 `0.156 s`，不能据此认定加 SQL 索引就能消除主要成本。时间线支持 CPU/执行竞争；墙钟减线程 CPU 不能单独确定 GIL、调度、I/O 或 GC 等待。嵌套阶段耗时不能相加。

四个监控请求进行了两次完整快照尝试：单读第 `6`、`13` 轮，并发第 `16`、`19` 轮。最长为 `6.989648 s`，轨迹 `ae18ad8d561c43a3940eb77af4f8215d`，两次快照共占 `6.464507 s`。重复尝试由现有权威/身份重试条件触发；当前时间线没有指出具体哪个比较字段改变。不能减弱第二次检查，也不能跨权威变化复用第一次证明。这是新观察，不是对历史 `8.69 s` 请求的重建。

可直接处理的额外竞争来自 [App.vue](../../web/src/runtime-status/App.vue)：`onMounted(monitor.start)` 在结果路由也执行。[stream.ts](../../web/src/runtime-status/stream.ts) 在连接事件流前立即获取完整 dashboard 快照。因此，进入历史结果页会同时启动结果校验和额外的启动监控校验。受控浏览器调度结果指出了一个有效的首选干预点，无需修改任何校验器。

## PRR05. 只做一个最小候选

范围限定为：首次进入 `backtest-run-detail`，且应用监控流尚未启动。立即读取主要结果，初始结果请求结束后再启动同页监控流。其他路由保持原启动行为，从已有监控页面进入结果页时保持正在运行的监控。不需要全局请求调度器、跨标签页领导者、新缓存、后端队列或新依赖。

初始结果成功或失败均释放启动门。拟设置 `5-second` 最长推迟，防止结果读取卡住而无限延后监控。离开路由时为新路由释放启动门；卸载时关闭并阻止迟到回调启动已放弃的工作。使用路由/请求代际及单个有所有者的计时器。推迟期间顶部横幅必须如实显示尚在连接，不能根据旧状态声称实时连接或允许执行操作。启动后，原有快照、心跳、协议不匹配、过期、重连和新鲜度行为不变。

浏览器对照推迟到视图就绪，没有这个生产计时器；实施时必须另行验证更窄的请求结束边界及超时。预期收益是首次进入时更早看到历史结果。它不会消除另一个真实监控页面造成的 CPU 竞争，不会加速全部监控读取，也不会消除必要的权威重试。不能因为这些限制仍存在就扩大任务。

## PRR06. 收益门槛与停止条件

预先固定 `20` 对现状/候选交替浏览器对照，使用同一运行、配置和已排空起点。要求首次结果就绪中位数同时至少改善 `20%`、减少 `1.0 s`。只报告中位数/范围；若要声明 p95，每方案仍需至少 `100` 个成功观察。诊断中的 `50.63%` 不是验收门槛，也不是保证。

同时验证结果单读 API 及真实监控/结果并发的响应耗时和实测总 CPU 中位数，回退均不超过 `10%`，错误/拒绝/超时不增加。不能因为页面看起来更快就忽略其他指标失败。监控首次启动的明确有界延后单独报告；已打开的监控页面不能被新启动门延迟。

若候选减弱权威/完整性/新鲜度、提前退还在途工作、破坏排空、留下无主计时器/请求，或需要已完成证明缓存、分配器/IPC 重构，立即停止并拒绝该候选。固定对照未达到收益门槛或保护指标恶化时停止，不追加样本直到通过。允许修复明确的正确性问题后重跑相同的预定检查；反复无法达标则结束候选，不转成新的基础设施项目。

候选通过后，仅交付这个有边界的前端改动并停止扩展。只有后续生产测量表明仍存在值得处理的用户可见问题，才单独规划有范围限制的后端 CPU 任务。本次前端实验不降低既有后端/原生验收限制。
