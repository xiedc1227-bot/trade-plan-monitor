# 总览重试与监控停止问题排查

## 范围

调查“监控总览”的重试操作为何没有更新指数走势，修复运行时调度故障、随后出现的 monitor-contract `2` 健康读取故障以及供应商限频提示的分类缺陷。本次不修改 API Schema、供应商配置、凭证、采集周期、交易规则或生产数据库。

## 已观察到的服务状态

- Web 进程仍可通过 `127.0.0.1:8765` 访问，但 `/api/v1/dashboard` 返回 lifecycle/coordinator 为 `STOPPED`，原因为 `RUNTIME_STOPPED`。
- 生产数据最后一次心跳为 `2026-10-08T10:36:46.124891+08:00`，可见指数的已存数据截止仍为 `2026-09-16T13:55:00+08:00`。
- 查询当天 `000001.SH` 历史走势返回 `404 NOT_FOUND`；`/api/v1/health` 返回 `500 INTERNAL_ERROR`。
- `useDashboardMarketIndexTrends.refresh` 只重试读取选中指数已保存的历史数据，不启动供应商采集或重启运行时；这与 `SPEC-monitor-index-trends.md` 一致。

## 根因与修正

1. 已选中的市场任务到期时，`_reconsider_progress` 选择立即唤醒。`RuntimeProgress.complete_step` 再次读取时钟，此前会拒绝因此产生的负延迟，即使只前进了一微秒。使用 SQLite 备份的诊断运行时，在调度循环中复现了准确异常 `ValueError: local reconsideration must be scheduled within 0..30 seconds`。监督器的有限次数替换仍使用同一份故障代码。
2. 已经过期的唤醒时间现在按零延迟立即到期处理。未来唤醒最多 30 秒的限制、准确完成 token、基于单调时钟的逾期判断和已停止 owner 保护继续生效。修正不会为已经到期的唤醒重新提供宽限期。
3. 监督器的旧版 `DEGRADED` 健康投影会清空 `stopped_at`，但 monitor-contract `2` 仍识别为已经完成物理清理的停止 owner，并要求停止时间，因此产生校验错误。现在 lifecycle 为 `STOPPED` 时，读取权威改用 owner 的实际健康状态，保留停止时间和 generation，旧版投影保持不变。
4. 供应商提示的分类此前优先匹配权限字样，再匹配明确的限频字样。模拟 HTTP `200` 应用错误 `每分钟最多访问2次，请查看权限说明` 时，域名和直连 IP 两种传输都错误设置了权限阻断。现在明确的限频提示优先匹配，使用已有的冷却机制。结构化 HTTP 授权失败以及真实权限拒绝（包括提及 K 线频率的权限拒绝）仍归类为权限阻断。这是已复现的缺陷；10 月 8 日的原始供应商提示未被保留，因此不能断定当时那次供应商失败就是由该缺陷引起。
