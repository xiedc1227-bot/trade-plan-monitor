# 监控闭环回测操作指南

英文规范：[monitor-loop-backtest.md](monitor-loop-backtest.md)。本文说明已实现的每日连续研究流程：逐份准备并审核计划、组合为一条计划链、一个账户及一次运行／结果。实际证据和边界见[验证记录](../verification/monitor-loop-backtest.zh-CN.md) RP-V19/RP-V20。预置计划日期流程见 [PD-V01–PD-V04](../verification/2026-10-15-preloaded-plan-dates.zh-CN.md)。

## ML-O01. 支持范围

每次运行冻结一条由完整已审核 Schema 5 快照组成的有序计划链、一个标的和一份期初账户。在适用交易日边界，已审核后继先替换普通权限，再开始监控／执行；无更新时延续仍有效的版本。过期后没有普通权限。真正替换会关闭旧普通意图，同时保留账户和既有风险义务。后续原文持仓仅供比较，绝不重置账户。

仍支持单份原文准备。多计划同时运行及多标的共用资金仍不在范围内。准备、同步、数据集校验及回放共用一个未完成任务槽。排队、运行中、等待取消及过期但未确认的工作，在终态完成或明确恢复前保持占用；切换页面不能释放任务。

这是离线模拟，不激活实时计划、不发券商订单、不发送真实通知、不重写监控持仓。历史兼容运行仍按原契约读取。

## ML-O02. 准备并审核有序原文

打开 `/backtests/new`，使用“准备计划”。每次只准备一份 UTF-8 `.txt`/`.md` 文件或粘贴一份原文，不再选择完整／修改类型。第一份建立计划链。“准备下一份原文”默认关联刚审核的计划；新打开页面时，若计划库只有一个标的且最新生效日唯一，则默认关联该版本。多个标的或最新日期相同才需选择前序。也可明确选择“不关联，开始新的计划链”。刷新保留明确选择。保存时由服务端复制并锁定准确前序；未审核候选不能作为前序。`plans.json`、`entry-fields.json` 和文件名均不作为计划证据。

保存时从明确适用日期说明或带日期的计划标题提取 `effective_trade_date`。缺少年份、日期冲突或相对日期须在提取前确认。成文时间和历史可用时间仍为可选。例如 `生效交易日：2026-09-24` 自动识别；`9月24日若企稳` 需要确认。先保存日期不明确的原文，确认日期后再次保存，再提取。准备身份保留在 URL 中，刷新后可恢复。

点击“提取计划”，按保留、修改、新增和取消核对规则、前后值及原文依据。首份计划的规则作为新增展示。新准备计划以已审核前序为底稿。AI 只返回带原文引用的变化；服务端按稳定规则标识应用保留、修改、新增和取消。未提及规则与未改变字段保留准确的前序依据，无需重复声明保留。同一章节不同字段的兼容变更自动合并；互相矛盾的值或不存在的目标仍作为处理错误。取消按含义唯一对应规则，无需原文包含内部编号。只有真正含糊的原文含义或目标才作为业务问题；未提及绝不取消。解决真正不明确的内容后，统一审核本份计划。后续计划沿用准确的已审核前序和期初账户，账户描述不会重置它。新准备计划采用 `POSITION_LIMIT_ONLY`：不要求或检查现金，仍严格执行最大持仓和每笔交易授权。历史回测保留原资金模式。已审核条目不可原地修改，后续变更需准备另一份原文。

按实际数量重复准备。在已审核计划库勾选 1–256 份条目，组合用于一次回测。服务端按生效交易日排序，拒绝重复日期／来源 ID、混合标的和缺失或不匹配的直接前序，沿用第一份的账户。组合不调用 AI。独立完整计划替换策略；后续账户描述不会重新初始化连续账户。浏览器不生成冻结审核权限。

默认关联前序只作用于新准备计划保存时，不会改写历史独立审核版本或已冻结回测。重建历史计划链时，应先准备并审核首份，再让每份后续原文关联刚审核的新前序，最后组合这些准确的新条目。核对 `base_hash` 是否等于直接前序的 `extraction_candidate_hash`；只有首份应为独立计划。有原文依据的取消优先于继承。明确保留风控时，保留前序依据和已确认的停牌口径。当原文明确把同一个旧风险价格改为修复门槛、并说明不是新仓位止损时，应审核为取消该价格线退出规则，不能静默沿用。见[四份原文继承链验证](../verification/2026-10-17-full-inheritance.zh-CN.md)。

回测提取使用独立的 `ai.backtest_max_output_tokens`（默认 16384）与 `ai.backtest_timeout_seconds`（默认 120），不改变普通提取预算。完整请求仍受 `max_input_chars` 限制。紧凑返回格式引用服务端规范条款 ID；精确原文位置、单位和固定产品常量由服务端重建并校验。发送完整当前原文及已审核前序策略；重复历史证据保留在服务端不可变上下文中进行继承校验。不截断原文，不补造缺失策略。已分类的提取、格式及引用错误最多自动纠正两次，每次作为独立的持久化尝试记录（每个原文版本最多三次物理调用，与传输重试共享上限）。真正不明确的内容、服务商结果未知、输入超限和输出截断不进行自动纠正重试。用尽次数后的处理错误仍显示为软件／提取诊断，不要求填写内部字段。AI 语义分类和变更依据仍需整份计划审核，不能自行批准。历史冻结输入保持原有解释契约。

新后续请求使用 `monitor-loop-delta-wire-v3`。模型声明交易授权和先后顺序；前一交易日条件使用 `DAILY_PRIOR_CLOSE`，后续分笔使用 `AFTER_RULE_COMPLETED`。语气保留或当前等待不等于取消明确的未来条件交易；要求重新制定买区或另行决定是否交易的内容仍只生成提醒。可选建议不能成为强制条件。格式校验检查所声明的结构，整份计划审核仍须核对声明是否符合原文。

条款分组减少重复分类，同时保留每个规范条款。纠正携带上一轮未审核候选及其分类。无效身份／路径和空修改产生处理诊断。规则数量在明确取消后计算，证据索引跟随保留规则。内部 `source-clause-pool-v2` 存储对准确证据和重复字段路径列表去重，解压仍受 1 MiB 限制；不提高服务商输出字节／节点上限，历史候选仍可读取。参见[当前通用流程验证](../verification/2026-10-17-generic-inheritance.zh-CN.md)。

输入超限、输出截断、证据不匹配和服务商错误分别保存明确提示。旧批次中未开始的条目显示“等待提取”。每个当前原文／前序周期最多明确提取 3 次；结果未知的付费请求保持任务槽占用，直到确认结束。不确定的写入用原请求体和原幂等键重试。旧批次准备仍按原流程读取与审核；新界面一次准备一份。四份实际原文的结果及仍待审核事项见[真实验证](../verification/2026-10-16-single-plan-library.zh-CN.md)。

## ML-O03. 期初账户、费用与时间

期初账户只初始化一次。批次描述原文实际持仓，不是模拟买入，不收购买费用。取得日期、可卖量、成本、现金及累计费用跨全部版本连续保留。后续原文的 0 或 200 股陈述产生可见差异，不兼容的账户依赖指令保持阻断。取得单价、批次总成本、原文参考价及具有有效时点的期初估值分别记录。例如，100 股、每股 40.105 元保留总成本 401050 分。未知现金、库存、成本或可卖量不能变成虚构的零。人工修正必须有明确审核证据。

新建预置计划未提供 `available_at` 时，以生效交易日 Asia/Shanghai 09:30 作为模拟可用边界。未知的 `authored_at` 和 `available_at` 保持 null，不补造原文时间。集合开始取该边界、首个生效日午夜及期初快照中的最晚值，且必须仍在首个生效日；次日快照或尚不可用的期初估值会被拒绝。后续版本在生效日开盘切换，仍遵守既有有效期约束。该假设不证明计划历史上已发布。已有明确可用边界与历史冻结输入保持原意，不自动平移日期；行情可用性检查继续生效。

选择 `FOLLOW_REMINDERS` 或 `OBSERVE_ONLY` 及精确费用/滑点。前者从有效提醒生成完整数量请求，后者不改变持仓。`RECORDED_ACTIONS` 保留为有界领域兼容值，不增加自动请求；原文准备界面提供两种已实现自动响应选择。整手、T+1、CORE、仓位上限及风险/冲突检查由服务端权威执行。含费用现金检查仅适用于历史 `KNOWN` 资金输入，不适用于新准备计划的 `POSITION_LIMIT_ONLY` 模式。完整数量失败时不替代为部分交易。

省略/null 结束日期在接受提交时一次解析为上海日期与证据截止。明确结束日期包含当日，不能早于历史起点或超过提交时的本地日期。重试/重启复用原截止。当前未完成交易时段只保留可用完整证据；真实缺口保持阻断。原文可用/生效前不产生事件。结束保留未平持仓，不生成清仓交易。报告分别展示请求/解析结束日期、实际证据截止、不可用市场收益指标和历史成本损益。

## ML-O04. 公开 API 与结果读取

修改请求使用既有本地 Origin 防护及 `Idempotency-Key`。发送前冻结 Body/Key，未知响应必须以完全相同的一对明确重试。服务端修订与身份为权威。

| 操作 | 路由 |
|---|---|
| 保存一份原文及可选前序 | `POST /api/v1/backtest-plan-library/preparations` |
| 分页读取已审核计划 | `GET /api/v1/backtest-plan-library` |
| 组合已审核版本 | `POST /api/v1/backtest-plan-library/compositions` |
| 兼容旧批次创建 | `POST /api/v1/backtest-preparations` |
| 读取耐久进度 | `GET /api/v1/backtest-preparations/{preparation_id}` |
| 读取完整条目详情 | `GET /api/v1/backtest-preparations/{preparation_id}/items` |
| 修改原文或顺序 | `PUT /api/v1/backtest-preparations/{preparation_id}/source` |
| 明确提取或重试 | `POST /api/v1/backtest-preparations/{preparation_id}/extractions` |
| 修正条目／审核冻结整链 | `POST /api/v1/backtest-preparations/{preparation_id}/reviews` |
| 请求取消 | `POST /api/v1/backtest-preparations/{preparation_id}/cancellations` |
| 确认未知提取已结束 | `POST /api/v1/backtest-preparations/{preparation_id}/recoveries` |
| 提交／读取运行 | `POST /api/v1/backtest-runs`, `GET /api/v1/backtest-runs/{run_id}` |
| 读取因果审计／成交 | `GET /api/v1/backtest-runs/{run_id}/details`, `GET /api/v1/backtest-runs/{run_id}/fills` |
| 读取完整权益 | `GET /api/v1/backtest-runs/{run_id}/equity-series` |

新单份命令使用 `preparation_id`、`source`、可选 `reviewed_base`（`preparation_id`、`manifest_hash`）；组合命令使用 `preparation_id` 与 `plans` 引用数组。计划库分页使用 `offset` / `limit`（上限 100）。旧集合创建必须填写 `input.schema_version: backtest-preparation-v2`；其他集合命令必须填写 `schemaVersion: backtest-preparation-v2`。审核资源区分 `ITEM_CORRECTION` 与 `CHAIN_REVIEW`。条目分页绑定 `expectedRevision`，须按实际 `nextOffset` 读取至完整。修改原文／顺序会使旧分页身份失效。

运行提交必须填写 `schemaVersion: prepared-loop-plan-v2`，绑定 `preparationId`、`manifestHash`、`response`、`costs` 和可选 `endDate`，不接受手写未来交易。`monitor-loop-result-v2` 展示有序来源／版本汇总及 `backtest-report-v5` 头部，审计行为 `monitor-loop-event-v2`。公开头部省略私有原文及完整日程，不能用于重新计算私有报告哈希。后端仍必须验证不可变输入／报告。旧 `monitor-loop-result-v1`、`backtest-report-v4` 和 `monitor-loop-event-v1` 的语义及字节保持不变。

原生审计读取使用 `kind=DECISION`，页面由服务端排序，最多 100 项。回执保留公开模拟身份；内部存储成交键绑定运行，避免顺序实验碰撞。既有旧暂存成交仍严格校验，可重放且不新增重复行。

结果展示每日适用情况、替换／延续／无权限转换、已关闭意图、实际账户背景差异、证据截止、评估／提醒／请求／执行及实际成交回执，不虚构逐笔损益。既有权益接口先在同一读取快照内验证完整因果链，再投影期初账户及每日最后一个实际估值。存在实际估值事件时包含非交易日，未知值保留为 null，并公开过期状态。不会只聚合可见事件页、虚构缺失日期，或超过 2,000 点／4 MiB 边界后截断。历史 v4 原生权益仍为未记录。原生闭环导出在流式输出前返回 409，界面操作不可用；支持的冻结研究导出字节保持兼容。

## ML-O05. 失败、取消与未知操作

503 表示局部服务能力失败或有界 SQLite BUSY/LOCKED 冲突；原文/运行表单保留原请求供明确安全重试。409 表示状态/绑定或共用未完成槽冲突，其他操作前先读取权威状态。任务失败与服务降级是不同事实；刷新或历史读取均不静默重新提交工作。

取消确认不代表物理完成。正在提取的任务在自有调用结束前保持准入。未知代次跨刷新/导航保持可见，释放前须通过明确恢复操作核实旧调用已经结束。迟到原文结果受代次/修订隔离。回放取消或发布失败不产生已完成的部分报告。取消/租约/提交竞争保留既有 Claim Token 与原子发布检查。

## ML-O06. 存储与有限边界

默认独立路径为 `data/backtest-market.sqlite3`、`data/backtest-results.sqlite3`、`data/backtest-preparation.sqlite3` 及 `data/backtest-cursor.key`。保留既有路径/存储域校验，浏览器/API 命令不接受任意服务端文件路径。回放只读耐久复制输入/证据，配置、供应商、AI 和通知调用均为零。

集合最多包含 256 份原文／版本，每份 150000 字符，UTF-8 原文合计 8 MiB。同时受既有 4 MiB 编码 HTTP 请求上限约束：领域字节上限不代表接受 8 MiB Web 请求。准备投影最多 2 MiB，每页最多 100 个完整条目并采用自适应偏移，结果最多 4 MiB。每个当前来源／前序绑定的提取周期最多 3 次尝试；闭环记录最多 70000 条，审计最多 420001 行。结果以最近 30 次运行作为总上限，包括置顶，使用有界清理并保护自有输入／报告文件。整数保持安全，金额计算保持精确。历史同步仍只有一个活动任务，以 BACKGROUND 优先级，在日历／日线／分钟／涨跌停真实请求起点间至少等待 1.25 秒。缓存命中不新增等待；取消会在下一供应商调用前观察节流。不增加全局配额分配器或动态 CPU／内存控制器。

`SQLITE_SIDECARS_REQUIRE_STOPPED_CHECKPOINT` 的启动恢复仅限已有有效 SQLite 主文件、空 `-wal`，且边车只有 `-wal`/`-shm`。先检查不可变主文件并记录全部源文件指纹；要求完整 `CURRENT` 存储域结构，没有迁移或元数据修正原因，再复核指纹。使用 SQLite `PRAGMA wal_checkpoint(TRUNCATE)` 和配置的 busy timeout，随后关闭恢复连接。绝不手工删除 WAL/SHM 文件。

恢复后重新执行严格清单检查。残留边车、失败／忙碌 checkpoint 或不可读文件均阻止初始化。迁移清单保持只读，并拒绝所有边车。非空 WAL、回滚日志、孤立文件、旧／未知结构、待扩展结构及 UTC／无效元数据均不自动恢复。回归位于 `tests/integration/test_backtest_migrations.py` 和 `tests/integration/test_backtest_production_composition.py`。

## ML-O07. 复现本地验证

在 `trade-plan-monitor/` 使用既有开发环境执行。下列检查使用合成事实和一次性存储，不使用真实用户数据或付费供应商。若默认 OS pytest 临时根目录不可用，可追加新的工作区 `--basetemp=.pytest_cache/local-verification-unique` 目录，不修改检查：

```text
.venv/Scripts/python.exe -m pytest tests/integration/test_monitor_loop_production_composition.py tests/integration/test_backtest_isolation_fault_matrix.py tests/integration/test_monitor_loop_parity.py -q -m "not live"
.venv/Scripts/python.exe -m pytest tests/integration/test_monitor_loop_plan_switch.py tests/integration/test_plan_preparation_review.py tests/integration/test_monitor_loop_result_api.py -q -m "not live"
.venv/Scripts/python.exe scripts/verify_backtest_thread_load.py --profile windows-threads --offline
npm --prefix web run test:e2e -- tests/e2e/monitor-loop-backtest.spec.ts
.venv/Scripts/python.exe scripts/generate_frontend_types.py --check
```

Windows 负载命令分别运行 600 秒十只股票监控基线和 600 秒顺序准入原生回放/WAL 负载，回放准入起点间隔至少 120 秒（每十分钟最多五次实验）。这只约束离线夹具，不新增生产提交限速。每阶段至少采集 1000 次状态请求，验证全部计划评估及稳态语义提醒。状态 p95 <= 250 ms、p99 <= 1000 ms、p95 增量 <= 100 ms、调度 p99 增量 <= 250 ms 保持原计划门槛。`--smoke` 仅是短时开发试跑，不能证明这些门槛。被忽略的 `.pytest_cache/backtest-thread-load.json` 记录主机、时长、实际百分位、内存/WAL 观察及完成任务，双语报告保留实际证据。RP-V19 重跑这一未改动的单计划原生负载夹具，四原文业务验收另由真实浏览器检查。夹具只验证实测工作量，不认证真实 AI/供应商、大型生产数据集或全部共用主机争用场景。

实测负载修正先过滤当前评估历史再解码旧数据标记，并在一次监测事务内复用兼容判定。损坏及旧数据仍保留原保护；不引入持久缓存、历史重写或监测规则变化。

## ML-O08. 惰性启动与明确服务控制

应用启动、监测导航、路由预取及服务状态读取不触碰回测存储、游标密钥、提供方和执行线程。首次实际回测读取才进行一次元数据准备；准备尚未完成时可能返回 503。元数据就绪不会授权待恢复工作。真正新增的准入仅授予所选任务执行权限；重放旧幂等收据不会获得权限。当前回测页面分别展示服务准备/故障、任务状态和原文状态。

通过 `GET /api/v1/backtest-service` 读取惰性、`no-store` 状态。状态包括 `DISABLED`、`NOT_INITIALIZED`、`STARTING`、`READ_READY`、`READY`、`RECOVERING`、`DEGRADED`、`STOPPING` 和 `STOPPED`。`READ_READY` 允许元数据读取，执行协调器仍保持休眠。`READY` 表示具备执行能力，不会自动恢复历史任务。仅执行侧失败时，`DEGRADED` 仍可能保留健康的元数据读取；应检查能力，而不能把所有降级状态当成不可读。

状态包含 `epoch`、`revision`、`generation`、`canRead`、`canSubmit`、`canCancel`、`canExport`、`physicallyDrained`、`authorizedJobIds` 和 `reason`。epoch 是 32 位十六进制启动身份，禁用服务时为 null；修订/代次为安全整数。最多授权一个任务。`SERVICE_REPAIR_REQUIRED` 是安全的降级原因。读取/取消/导出能力表示服务接口是否可用；具体操作仍受自身状态/模式约束，包括不支持的原生闭环导出。服务修订、准备修订和任务领取代次分别归属。

正常页面只显示简短状态及 `服务管理`。展开后可刷新、查看待恢复任务、停止服务、查看更新时间及返回链接。服务异常、控制未知、停止中／已停止／未启用或发现中断任务时展开；已授权运行中的任务不触发该提示。任务进度、取消和重试仍在原页面。键盘 Enter／Space 只切换管理面板，不控制服务。

`canRead=true` 且没有当前 `authorizedJobIds` 后，界面以 `limit=1` 最多检查一项未完成任务。检查成功后，在 `epoch`、`revision`、`generation`、状态或授权变化前复用结果，也可手动查询。后台临时 503 留到既有状态轮询，不误报异常；明确手动查询失败仍显示。可读前不扫描，发现任务不授予执行权限。实际页面检查和保留的浏览器验证限制见 [SC-V01–SC-V04](../verification/2026-10-18-compact-backtest-service.zh-CN.md)。

明确选择局部修复。向 `POST /api/v1/backtest-service/recovery-requests` 发送当前 `epoch`、`expectedRevision`、`action` 和 `resumeJobIds`，沿用既有来源及幂等保护。`RETRY_PREPARATION` 要求所选任务列表为空且已实际排空。`RESUME_JOBS` 要求恰好一个所选任务 ID。不论自动发现还是手动查询，待恢复任务均须勾选确认并明确点击恢复；浏览历史或变为就绪均不提交第一项待恢复任务。修复本身不创建付费提取、不提交新运行，也不改变冻结截止。待确认控制应使用原始请求体/键重试。启动身份/修订变化冲突时重新读取状态，不能静默改写待确认命令。

向 `POST /api/v1/backtest-service/stop-requests` 发送 `epoch` 和 `expectedRevision` 停止该服务。两种控制均返回 202，并带 `Cache-Control: no-store`、`Location: /api/v1/backtest-service` 和 `Retry-After: 1`。确认发生在繁重工作完成之前，受计划的 1 秒门槛约束。确认代表意图已接受，不代表实际清理完成。继续观察状态：自有工作及最终清理结束后才能进入 `STOPPED`。卡住的自有调用可能停留于 `DEGRADED` 且 `physicallyDrained=false`，排空前阻止替换。仅停止服务不会清除未知耐久提取记录或任务准入；应通过该记录明确且有证据的恢复路径解决。

每次启动最多缓存 1000 条控制键收据。重载保留耐久任务/原文身份；应用重启改变 epoch 并丢弃当前会话执行授权。两者均不静默重跑排队、到期、取消中或未知工作。局部修复/停止期间监测导航仍可使用；只有实际监测证据支持时才能声称监测健康。

## 原文事实与集中确认

已加载结果的顶部“收益汇总”展示“总盈亏”“已实现盈亏”“浮动盈亏”“回测截止日期”。它位于操作、标签页、规则对照和逐份诊断之前，查看成交或明细时仍保留。前三项为元金额，盈利／亏损明确显示正负号，零保持 `0.00 元`。闭环结果读取已保存报告的 `cost_pnl_fen`、`realized_pnl_fen`、`unrealized_pnl_fen`，已计入成本的费用不再重复扣除。本金缺失不会隐藏已知的成本盈亏。

截止日期使用已确定的回放结束日期（`eventEnd`），不是任务完成日期或今天日期。闭环结果另显示上海时间的 `evidence_cutoff`。这是历史回放盈亏，不是实时账户估值。缺失盈亏显示 `暂不可用`，部分已知金额继续显示，未知项绝不替换为零。汇总不包含本金收益率。

面板复用既有结果请求，不增加 API 调用、回放、AI 提取、新审核或存储报告变化。明确提供已实现／未实现值的旧经典结果使用精确整数分合计；没有这些字段的旧研究结果显示不可用。宽屏四列，较小屏幕两列，极窄屏幕一列。参见[验证记录](../verification/2026-10-18-result-profit-summary.zh-CN.md)。

## ML-O21. 运行记录筛选与时间含义

运行记录页面的常用查询保留股票代码、回测截止日期和固定状态。两个日期均可选，且包含边界当天。对所有结果类型，都比较回放覆盖的截止日 `eventEnd`，不比较程序何时完成。例如选择 2026-10-09 至 2026-10-09，可找到覆盖结束于当天的运行，即使它是在之后执行的。非法或反向日期在查询前拒绝。多个条件按 AND 组合，翻页保持同一筛选条件。

筛选界面已移除数据集哈希和计划版本 ID，包括高级／旧记录查询入口。已有页面链接在首次读取前清除 `datasetHash` / `planVersionId` 及其绑定游标，返回第 1 页，同时保留股票、截止日期、固定状态及明确的旧时间条件，避免不可见条件隐藏记录。内部 API 筛选及存储标识继续保留用于排查。排序使用文字说明，替代不可操作的选择器。列表结果时间仍倒序排列，并沿用运行 ID 作为次序依据。连续回放的该时间戳为证据截止时间，不是程序实际完成时间；实际完成信息仍以有记录的任务历史为准。

新增只读查询为 `GET /api/v1/backtest-runs?symbol=002240.SZ&eventEndFrom=2026-10-09&eventEndTo=2026-10-09`，日期参数使用 `YYYY-MM-DD`。旧 `completedFrom` / `completedTo` 链接保留原有结果时间含义，仅在已有条件时显示于“旧链接时间条件”，不转换成覆盖日期；如果不需要旧约束，切换上方常用日期前先清空它们。不重写存储报告、哈希、时间戳、保留规则或原有排序。参见[验证记录](../verification/2026-10-18-run-record-filters.zh-CN.md)。

## ML-O22. 临时读取与准备进度

正常重叠读取等待既有元数据归属者，最多 8 个等待读取，每次准入等待最多 5 秒。不增加线程或重任务队列。历史／计划库 GET 对临时 503 最多尝试 3 次，间隔 1 秒；导航会取消延迟重试。真实过载、停止／降级服务、持续锁及无效响应仍明确提示，服务修复继续通过服务管理明确执行。初始化诊断只记录失败类型／看门狗，不记录原文或凭据。临时读取不会恢复任务或发送付费提取。

准备进度识别既有确认汇总和纠正诊断。若摘要已经完成、详情页临时返回 503 或修订 409，页面可沿用 2 秒调度，最多再刷新 3 次；摘要单独成功不会重置该上限。工作仍进行时继续既有单个在途轮询；隐藏／卸载停止读取，过期结果不能覆盖新证据。不自动重发写操作。进度／取消／未知结果确认及原正文／键重试继续受原有保护。

旧候选仍要求明确补充证据时，即使有确认汇总也显示对应控件，不能借汇总静默批准未绑定参数。新的原文已绑定事实继续自动识别。重新打开旧候选使用已存记录，不重写存储候选、已审核政策、冻结报告或四份计划结果。参见[实际与生产路径验证](../verification/2026-10-18-backtest-read-reliability.zh-CN.md)。

较大详情页同时遵守 2 MiB 和浏览器既有的 50000 JSON 节点／32 深度预算。较小页通过同一修订的 `nextOffset` 继续读取，直到全部完整原文条目已加载。不丢弃原文或证据，也不提高预算。字节合法的 200 响应若超出浏览器结构预算，仍不能被接收。

## ML-O23. 自动准备数据

已审核原文回测选择计划、可选结束日期和费用后点击开始。程序检查本地证据和准确匹配的已验证结果副本，必要时下载缺失的已结束日期历史数据，重新检查后提交回放。历史数据页用于查看、筛选、分页和任务控制，四个人工准备入口已移除。不调用 AI，访问两个页面均不启动下载。

状态区说明检查、补齐历史数据、验证和回放。即使下载同时完成，取消也阻止后续回放；应等待服务端取消或终态确认。同步回执丢失时，使用同一请求重试先核实结果，再进行其他操作；此前取消仍然有效。任务或检查失败时，使用重试回测，已经下载的缓存会保留并重新检查。数据任务记录链接允许离开页面后继续查看、取消已接收任务。离开、刷新页面不会自动续接剩余流程或恢复历史任务。API `GET /api/v1/backtest-run-data` 只读；同步仍使用既有 `DATA_SYNC`、`allowNetwork: true` 和 `refresh: false`。

有效缓存自动复用。只剩结果自带副本时，服务端核对审核依据、账户、数据要求、覆盖和准确截止时间；最多检查 20 个首份计划匹配的输入。新输入、数据集标识绑定本次提交，旧事实字节和报告保持不变。不同截止时间、计划变化、覆盖不足或副本损坏不能绕过校验。当日尚未发布数据、供应商权限凭据、限流或历史事实不可用仍明确失败，程序不补造价格、不扩大历史截止时间。既有默认结束日期语义和旧冻结数据集回放保持兼容。合成测试不代表真实供应商认证。

实现与证据：[AD-01–AD-03](../../tasks/automatic-backtest-data.zh-CN.md)、[验证记录](../verification/2026-10-18-automatic-backtest-data.zh-CN.md)。
