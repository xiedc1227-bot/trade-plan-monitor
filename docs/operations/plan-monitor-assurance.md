# Plan monitoring assurance: operating guide

Use this guide to inspect source coverage, understand monitoring readiness and identify the human steps still required. Engineering evidence does not establish corpus acceptance or actual-installation readiness.

## PMA-O01 — Inspect coverage and repair the exact source

In `/plans`, inspect the source coverage and its blocking spans alongside the saved rule. An incomplete draft can remain available for correction. Readiness can explain NEEDS_REVIEW only for a native-valid incomplete Schema5 DRAFT that is unreviewed, unactivated and has complete, unique owner identities. This preserves null/source bytes and unknown facts, grants no authority, and retains upgrade reasons, second-read binding and existing response/admission budgets. Incomplete Schema6–9 drafts and Schema5 drafts with missing or duplicate owner identities still return unavailable/503; this limited path does not omit owners to claim partial support ([R141](../verification/2026-10-27-plan-monitor-assurance.md#pma-r141--bounded-incomplete-draft-readiness-without-partial-scope)). Restore the complete source-defined condition, save a new version and review that exact version before activation. Source, parameters or mapping changes invalidate the previous binding. There is no general ignore/background waiver for a mandatory condition. The 4000-fen repair journey is an assisted repair, not a successful raw extraction ([R102](../verification/2026-10-27-plan-monitor-assurance.md#pma-r102--source-repair-and-actual-version-switch-cancellation)).

Explicit-path text has finite syntax support: twelve existing scalar families can accept unquoted values after strict JSON syntax failure and native constraint validation. Unsupported paths, negation and mandatory tails remain blocking. Four complete account-fact forms can be classified as context; this does not verify their truth, initialize holdings or grant approval ([R132](../verification/2026-10-27-plan-monitor-assurance.md#pma-r132--bounded-explicit-source-syntax-and-account-facts)).

## PMA-O02 — Let defined conditions evaluate on their owned data

After the exact definition is reviewed and the applicable activation and data prerequisites are met, supported conditions use the existing runtime evaluator. The automatic-alert journeys demonstrate repeated native evaluation without new plan reviews or FACT records. Missing required evidence withdraws current readiness; exact restoration can revalidate the original proof only within its unchanged lifetime, while a new native cycle creates new evaluation evidence. Opening or refreshing readiness does not collect data, evaluate conditions or renew proofs ([R101](../verification/2026-10-27-plan-monitor-assurance.md#pma-r101--initial-native-browser-readiness-journeys), [R104](../verification/2026-10-27-plan-monitor-assurance.md#pma-r104--same-page-native-loss-restoration-and-recovery)).

## PMA-O03 — Clarify definitions and retain necessary confirmations

Use existing clarification/supplement and review steps for missing definitions. An unchanged reviewed definition need not be redefined daily; changed meaning, scope, period or binding requires the applicable review again. Clarification does not assert that a runtime event has occurred. Retain explicit plan review/activation, applicable inventory/cost and official-fact confirmations, and per-occurrence exception approval.

The verified H04 registration journey covers only Schema5 ordinary `REVIEWED_FACT/TRADE_DATE` exact leaves. A=true does not satisfy B; an explicit B=false stays false. Other owners and scopes are outside that accepted journey. These examples establish specific behavior, not a total manual-step count or a reduction percentage ([R103](../verification/2026-10-27-plan-monitor-assurance.md#pma-r103--exact-leaf-registration-and-complete-calendar-reevaluation)).

## PMA-O04 — Read conditions, execution and notification separately

A complete FALSE result means the condition was checked and unmet. First evaluation, missing/stale evidence and normal official-close waiting require their own explanation; the accepted earlier-history-loss journey reports UNKNOWN/AUTHORITY_UNAVAILABLE. Inventory changes can preserve market comparisons while withdrawing old execution eligibility. A confirmed technical-risk obligation can remain when its current comparison becomes FALSE; it does not prove executable shares or permission to sell. QUEUED and historical DELIVERED receipts do not establish current notification service ([R106](../verification/2026-10-27-plan-monitor-assurance.md#pma-r106--native-official-close-waiting-and-required-history-loss), [R126](../verification/2026-10-27-plan-monitor-assurance.md#pma-r126--inventory-read-races-preserve-conditions-not-stale-execution), [R107](../verification/2026-10-27-plan-monitor-assurance.md#pma-r107--independent-risk-browser-engineering), [R105](../verification/2026-10-27-plan-monitor-assurance.md#pma-r105--native-notification-receipts-and-current-service-loss)).

If the runtime requires restart, failed progress and its original deadline remain until actual stop cleanup; a refreshed heartbeat cannot hide STALLED or restore execution eligibility ([R138](../verification/2026-10-27-plan-monitor-assurance.md#pma-r138--revoked-progress-retains-failure-until-explicit-stop)). Readiness is an explanation and grants no trading authority.

## PMA-O05 — Keep history distinct from current qualification

Historical source/response bytes, hashes and focused semantic review remain preserved. Historical zero issues, local update readiness or successful public JSON round trips do not establish complete current coverage. Recorded examples retain exact current BLOCKED/UNRESOLVED results, including normalization loss; a blocked predecessor does not qualify a new current chain ([R137](../verification/2026-10-27-plan-monitor-assurance.md#pma-r137--recorded-historical-semantics-retain-current-blockers), [coverage contract](../specifications/monitoring/SPEC-source-condition-coverage.md#scc-s05--versioned-proof-and-historical-compatibility)).
