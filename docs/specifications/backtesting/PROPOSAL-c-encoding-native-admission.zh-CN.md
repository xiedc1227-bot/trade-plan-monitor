# C 编码开销、原生内存所有权与大行准入

## CNA01. 决策与范围

继续独立 P0 实验，P1 保持 NO-GO。优先处理规范化/规划开销、与版本匹配的原生内存所有权边界，再打通大行完整读取。下一步不应只是增大块大小或未经证明调低系数。保留独立权威检查、完整性校验和物理排空。

本方案承接 `d0ba977` 的 [P0 报告](../../verification/bounded-c-p0-2026-10-23.zh-CN.md)。本次仅新增双语分析/方案及[脱敏诊断证据](../../verification/evidence/2026-10-23-c-encoding-next/analysis.json)，不修改生产/实验实现、不写入真实数据、不重启服务、不提交或推送。并行 AI 提取及日库存工作不在范围内。下一次实施前先补齐双语规格/任务一致性。

## CNA02. 失败项与本次新证据

| 门槛 | 已记录 P0 结果 | 解释 |
|---|---|---|
| CPU | 原版 `2.406250 s`；C256 `2.953125 s`；`+22.73%` | 超过 `10%`；优于 Python token 方案仍不足以通过 |
| 原生内存 | 编码预留 `12 * target + 4096`；长 Decimal 完整校验追踪峰值 `23.88 MiB`，密集对象 `137.50 MiB` | 诊断预留与追踪峰值不是原生内存上界 |
| 可用性 | 长 Decimal 工作区 `197697036 B`；密集对象 `145472808 B`；上限 `67108864 B` | 均在 payload 前拒绝；纯校验器成功不够 |

新增只读归因使用未改变的冻结数据库：`2008` 条历史记录、`5` 个指数、最大原始 JSON `35587 B`。当前 C256 的三轮分阶段测量、独立的两次原版/候选剖析及一次生产者计数均与参考完整输出一致。数据库指纹不变。这些是归因测量，并非新的前后性能验收，不能跨会话比较绝对耗时。

计数记录 `8032` 次遍历、`8032` 次 C 调用、`8032` 个块，最大输出 `35587 B`，超过目标的根对象为 `0`。样本中每条记录的四次域哈希/字面量遍历都只需一次 C 调用。因此，大数组拆分不能解释这批样本的回退；合批应作为独立大输入实验。

三轮候选分阶段耗时中，规范化约占 `47%`。带探针剖析中，原版规范化累计 `2.7181 s`，候选 `4.9037 s`；候选 `bound()` 调用 `2177305` 次，累计 `1.6728 s`。C 编码累计为 `0.3758 s` 对 `0.4047 s`。这些嵌套/带探针数字不可相加，也不能量化无探针条件下的因果占比。逐行线程 CPU 计时粒度不足以精确归因，分阶段使用累计墙钟，整轮 CPU 单独报告。

## CNA03. CPU 与表示归因

`normalize()` 先构造 `SizedDict`/`SizedList`，再生成 `dict(result)`/`tuple(result)` 并遍历子项核算大小。容器缓存消除了每轮重建整树大小表，却没有消除额外容器遍历、浅副本、生成器开销及重复标量核算。`DecimalText` 在规范化 Decimal 字符串后还新增了字符串子类分配。构建期间模型导出和规范化容器仍然重叠。

排序后的 bar 向量、request 列表和排除根哈希的映射是普通容器，进入编码时还会重新求边界。计数证明常见小行每次编码都能装入目标，却仍承担规划成本。四次独立遍历租约也仍存在，应测量其贡献，不能预设它是主因。

版本匹配的 CPython 源码还确认了一项临时分配：C 列表编码调用 `PySequence_Fast`，后者会复制 `SizedList` 这样的非精确列表。这是引用向量副本，并非每个元素的深拷贝。排序字典也会分配条目列表；普通字典在 `sort_keys=True` 时同样需要该工作，不能全部归因于子类。参见 [C 编码器](https://raw.githubusercontent.com/python/cpython/v3.14.7/Modules/_json.c)和[序列转换](https://raw.githubusercontent.com/python/cpython/v3.14.7/Objects/abstract.c)。

建议分别实验：

1. 将规范化与保守大小累加融合为一次遍历，避免仅为求大小创建 `dict(result)`/`tuple(result)`，复用已验证标量边界，保留 Decimal/时间规范。比较容器子类与精确容器配合有界行内计划的开销，不替换为无界全局大小表。
2. 仅在模型推导的分配前边界证明每次调用可装入时，尝试普通容器小行路径。原始 JSON 长度不是编码大小证明，仍须覆盖指数展开、默认值、转义及非法输入。未知模型/构建必须重新验证后才可使用快路径。
3. 独立评估大数组按大小划分的精确列表批次，预先计入引用向量、writer/UTF-8 重叠和前一输出块，避免未计费切片/拼接。测量支持调整前，保持 `64 KiB`、`256 KiB` 诊断目标。
4. 上述测量后再考虑 snapshot 哈希与字面量双消费。哈希排除 `snapshot_hash`，字面量包含该字段及 EOF。明确测试成员/逗号路由，bar/request/formula 检查保持独立；不能预设合并遍历对小行一定更快。

## CNA04. 先闭合原生边界，再减少准入预留

区分三项义务：逻辑输出上界、输入工作区分配/所有权上界、进程整体工作集/私有提交上界。任何一项都不能替代另外两项。Python 的 [tracemalloc 文档](https://docs.python.org/3.14/library/tracemalloc.html)说明其追踪 Python 分配的范围；[Pydantic JSON API](https://pydantic.dev/docs/validation/latest/concepts/json/)没有为完整字节解析提供有界工作区契约。

冻结 Python、解析器、SQLite、驱动、模型及构建指纹，取得匹配的原生源码/构建来源。本次尝试的公开 `pydantic-core v2.46.4` 源码标签仍不可用，不能用邻近版本代替并宣称通过。先解决来源门槛；无法闭合时保留 NO-GO，不再反复调整系数。

建立分配表，覆盖 SQL execute/step/cast 与驱动缓冲、不可变字节、前后行重叠、解析器临时区和字符串缓存、成功/失败模型、模型导出、规范化计划、排序引用向量、Unicode writer 扩容/重新分配及宽度变化、UTF-8 转换、比较视图/副本、全部选中结果及替换、异常链和清理。逐项记录分配器、最大同时存活数量、分配前所有者、转移及物理释放条件。只有证明共享同一不可变所有者后，引用别名才可只计一次。

采用源码推导上界，加实际原生分配器、进程工作集和私有提交的隔离观测。SQLite 计数仅作补充且依赖版本，不是完整进程上限。重复采样可以推翻上界，不能证明不存在瞬时尖峰；样本低于某个系数也不能使其成为已证明边界。原生故障注入须覆盖分配失败、writer 扩容、非法 UTF-8、深层/重复/额外 JSON 及大量模型错误，包含最终异常脱敏之前的峰值。

密集非法 OHLC 样本在保留错误期间追踪分配约 `149.53 MiB`，共产生 `40000` 条错误。缩短最终错误消息不能抹去之前的峰值。须覆盖当前读取范围内任意畸形持久化输入，而不只是合法模型形状。不得通过部分解析、`model_construct()`、截断校验或新增数量限制改变可接受输入及失败语义。如需结构预扫描，应独立证明其启动分配有界、完整计费，并与证据认证严格分离。

## CNA05. 合法大行为什么仍被拒绝

旧 shape 公式为源数据、原始捕获和解码文本预留两代重叠。`ByteScan` 只减去了驱动 Unicode 改 bytes 的节省，剩余 JSON 项约为 `12 * N`，其中仍包含新解析器已不需要的解码文本预留。实际实验在调用新校验器前仍先执行 `scan.acquire(work)`。因此这是确定性的准入计算拒绝，并非测得解析器 OOM 或新的哈希错误。

不能立即改成 `2 * N`、把已计费输入副本挪到模型类别，或提高 `64 MiB`。先证明哪些缓冲消失、哪些代际不再同时存活。接近 `16 MiB` 的行，四份完整副本已几乎耗尽输入预算，还没计入元数据和编码。必须同时减少表示重叠并按字节调度；单纯减少读者不能让超限的单个工作区装入。

CNA04 通过后，分别定义**证明**与**比较**所需的完整推进预算。每个请求仍独立进行 SQL 元数据/原始内容比较和权威检查。仅在与仍运行的物理证明逐字段、逐类型、逐行完全相等后，跟随者才可省去模型解析；摘要相等不足以准入。租约计划包含当前主请求/跟随者持有行、转移重叠、结果消费及排空代际。

payload 执行前原子预留完整推进预算，不能持有部分扫描/原始行租约再阻塞等待编码扩容；多个扫描占满剩余容量时，嵌套获取会妨碍推进。优先在已筹资预算内分发子租约。若形状相关扩容不可避免，必须不阻塞，并明确释放/重试协议，保留原始时钟和尝试数；结构预扫描不能形成循环筹资。

先保障主请求，再资助能完整装入比较工作区的跟随者。保留 `8` 个读者准入，但按字节限制同时物化的大工作区。保留公平性/期限，证明或 cohort 等待前释放扫描许可，小输入仍须达到 `1` 次证明加 `7` 次加入。不要承诺同样数量的大行同时加入。完整集合装不下时，应在提交 worker 前选择完整校验的流式路径，释放不兼容的已保留前缀，不能复制在途证明。必须先证明单行可装入，才能称为可用回退。

## CNA06. 实施顺序与停止条件

| 阶段 | 交付物 | 出口/停止条件 |
|---|---|---|
| P0-A | 双语规格/任务；源码/构建来源；分阶段所有权表；冻结归因基线 | 解析器/原生来源未闭合时禁止改变预留 |
| P0-B | 单遍规范化/规划；独立小行路径与大行合批消融实验 | 完整字节/输出/错误等价；边界不降低；CPU 对比原版 |
| P0-C | 编码器/解析器/驱动成功及失败原生边界；重复完整进程内存测量 | 原生重叠未证明或超过上限时继续阻断 P1 |
| P0-D | 已筹资的证明/比较预算及加权大行 SQL 路径 | 合法大行通过元数据、payload、完整校验、排序选取及排空；无死锁/提前退账 |
| P1 | 条件性集成及真实 owner/浏览器对比 | 正确性、可用性、内存及性能门槛先全部通过 |

保持 `64 MiB` 输入、`768 MiB` 聚合工作集、`2560 MiB` 私有提交、`1` 个物理证明、`1` 个排队 owner、`15-second` 等待、`90-second` 资格和 `2` 次尝试。此前 `2-slot` 独立扫描候选作为独立变量。门槛失败时仅允许 `3` 轮标明诊断性质的测量。合格候选须完成 `10` 组 A/A、`20` 组 ABBA/BAAB，混合进程收益至少 `20%`，结果读取回退最多 `5%`，监控/总 CPU 回退最多 `10%`，拒绝/超时不恶化。真实 owner/浏览器每版本须 `100` 次尝试，低于 `100` 次成功不得宣称 p95，保留既有 `20%` 混合 p95 目标。本方案不宣称已改善浏览器或尾延迟。

## CNA07. 不可降低的语义与验证矩阵

每个请求保留独立前后权威检查、激活重读、原始事务/观测时钟和尝试预算。不共享权威凭据、不缓存已完成证明、不只校验最新记录、不信任存储哈希。校验全部历史行、全部 `19` 个原始字段及 SQL 类型、head/缺失依赖、严格模型、规范 UTF-8 和 EOF、排序后的 bar/request 域、根哈希、公式定义及每个 fact 的公式哈希。

覆盖合法长 Decimal、密集数组和全部选中指数，精确块/标量边界、控制字符/补充平面 Unicode、排序、末尾历史篡改、重算全部关联字段后的域篡改、畸形/错误密集输入、模型替换和前后行重叠。覆盖 `1/2/8` 读者、相同/变化/晚到 cohort、大/小行公平性、元数据/查询次数及满预算推进。分配变异须识别无租约缓冲和提前退账，完整性变异须识别遗漏域/字面量/权威检查。

取消仅解绑观察者或阻止未开始工作，不会中断同步原生调用或释放其内存。所有权保留到真实返回、块消费、cursor 关闭及物理 worker/bridge 排空。跟随者不能取消其他观察者的证明。验证准入前、解析/编码/比较期间取消、最后观察者离开、时间边界两侧及 stop。清理失败时，即使 CPU 许可已释放，也必须保留债务并隔离后续代际，绝不能返回部分证明。

## CNA08. 复现与限制

证据包含成功诊断源码、源码/输入指纹、分阶段结果、剖析调用次数及完整输出等价断言。将源码保存为 `.pytest_cache/bep-next-analysis-probe.py`，在仓库中使用已有冻结数据库运行 `.venv/Scripts/python.exe .pytest_cache/bep-next-analysis-probe.py`。脚本只读该数据库并写入临时分析。此前两次在测量后的报告写入阶段因编码名称拼写失败，没有保存性能证据；修正后完整运行才是本次报告的数据集。

本次分析没有实现新的准入机制，也没有证明原生内存上界。优化顺序依据常见小行的实测规划开销及尚未闭合的分配契约，不应表述为保证的性能收益或对当前门槛的放宽。
