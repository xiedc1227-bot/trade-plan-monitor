## RLT01. 8.691 秒观测能够证明什么

历史浏览器记录测量请求发出到响应完成，不是 worker CPU、首字节延迟或整个页面渲染。以结果请求开始为相对零点：

| 观察事件 | 相对时间，秒 |
|---|---:|
| 初始 dashboard 请求开始 | -0.658 |
| 结果请求开始 | 0.000 |
| dashboard 响应完成 | 3.543 |
| 结果响应完成，HTTP 200 | 8.691 |

两个可见请求重叠 3.543 秒；dashboard 完成后，结果还持续 5.148 秒。不能把重叠时间直接扣作 CPU，也不能把剩余区间全部算成结果计算。未记录服务器隐藏工作与等待。

该页面自身首次心跳不能解释这次请求：socket 在初始快照后打开，原有服务器心跳周期为 20 秒，结果更早完成。其他已存在客户端的心跳仍可能参与，但未被证明。同一服务此前已完成结果读取，因此也不能只归因为进程冷启动；未测量 OS 文件缓存状态。

同一最终流程的两次并发结果请求各耗时 4.933 秒，key 相同时共享在途结果投影。这与双页面比单次异常值更快并不矛盾：请求数量不等于物理工作量，也不代表后台重叠相同。每个调用者仍独立读取可变结果元数据。历史浏览器跨度缺少服务器入口、排队、worker、GC 和响应阶段计时，因此无法事后完整还原原始 8.691 秒的全部原因。

## RLT02. 新定位的基础成本

分析当时 8765 端口没有监听。不能用合成权威替代真实验收。补测通过 `mode=ro` / `query_only=ON` 读取真实结果库及已有不可变复制文件，在隔离 ASGI 应用中使用生产结果路由/服务/所有权/响应校验代码。不涉及 provider、任务执行或业务写入。监控竞争者使用此前冻结的 2,008 候选只读副本、固定时钟和合成所有者缺席权威，只验证 CPU 竞争，不证明真实所有者就绪。

一次独立分段计时的完整结果请求为 2.2194 秒：

| 包含子阶段的计时 | wall 秒数 |
|---|---:|
| 元数据结果查询 | 0.0017 |
| 结果投影 | 2.2149 |
| 输入/报告/诊断快照 | 2.1554 |
| 复制输入校验，包含 bundle 与 39 天 | 0.3587 |
| 全部审计校验及诊断 | 1.7585 |
| 原始复制对象读取，41 次 | 0.0116 |
| 公开响应再次校验 | 0.0007 |

审计校验约占该请求的 79.2%。这些嵌套值不能叠加。响应为 15,559 字节。仅扫描全部 2,961 条审计行 / 3,199,278 payload 字节的原始 SQL 组件计时为 0.0183 / 0.0063 / 0.0063 秒，不声称冷缓存测量。查询已使用 `ix_backtest_detail_retention` 搜索 kind/run identity。未测得新增索引、加大分页、减少证据行或弱化响应校验的依据。

独立 worker 剖析定位到 2,961 次 `decode_audit_record`、15,295 次回测 `canonical_json` 和 2,263,592 次递归 `canonical_value`。插桩请求为 4.9291 秒，属于剖析开销，不是普通延迟。主要路径将存储 payload 规范化后解析成类型化事件，检查事件 identity/hash，再次规范化用于 payload 相等比较，随后又规范化同一事件用于有序事件集摘要。参见 [results.py](../../../src/trade_plan_monitor/backtest/results.py)、[loop_publication.py](../../../src/trade_plan_monitor/backtest/loop_publication.py) 与 [loop_report.py](../../../src/trade_plan_monitor/backtest/loop_report.py)。

## RLT03. 竞争、GC 与排队评估

5 轮交替完整路由观测，将结果完成与整批完成分开计时，完整响应保持一致：

| 范围 | 结果中位数，秒 | 整进程 CPU 中位数，秒 |
|---|---:|---:|
| 仅结果 | 2.2301 | 2.1563 |
| 结果加完整监控读取 | 4.3369 | 4.4688 |

第二个 CPU 值包含两个任务。这证明 CPU 竞争机制成立，不能据此精确归因原始异常值。本地解释器启用了 GIL，Python 密集线程不能无限制并行执行。参见 [Python threading](https://docs.python.org/3.14/library/threading.html)。增加线程尚未被证明有效。

保持 GC 启用进行观察：这些样本中单次收集最大为 0.1092 秒，不能解释本轮多秒残余，也不能排除历史未观察的暂停。普通元数据执行在隔离状态下很便宜，但 `get_run` 先等待 metadata gate，再可能等待 result gate。重型 review-context 读取也使用 metadata 路径。这些队列值得观测，不是原始请求的已证实原因。不得提高原有 5 秒 metadata 准入等待和 60 秒 result 准入等待。

补充 overview 竞争者在该冻结日历/数据选择下没有复现明显变慢。日历未知分支可能遍历历史，但旧请求日志不能证明当时走了此分支。未测得对应跨度前，不应归咎所有 overview 轮询或改变其观察语义。

## RLT04. P0：先补齐归因，再宣称修复尾延迟

先记录双语实施规格/任务。增加有界、可关联的观测，覆盖浏览器请求/首字节/正文/就绪，HTTP 入口/响应开始/正文结束，metadata 准入及 worker 开始，result 准入/加入/worker 开始结束，复制输入/报告/审计校验、诊断、公开校验和序列化。区分逻辑调用者与物理共享工作，共享 worker CPU 只计一次。记录取消/观察者退出与实际物理排空。保留原有截止时间和强所有权。

分开记录单调 wall 时间与 worker 线程 CPU；进程 CPU 包含竞争任务。仅记录阶段/类别/计数/字节/generation 和不含业务含义的请求关联标识，不记录凭据、原文、计划正文、SQL 参数或每一行审计内容。限定诊断窗口和事件/字节上限，观测失败不能授权数据或改变请求结果。比较开启/关闭观测，目标 CPU 开销 <=2%、wall 开销 <=5%。依据 [Python 时钟语义](https://docs.python.org/3.14/library/time.html#time.thread_time)，将[剖析](https://docs.python.org/3.14/library/profile.html)排除在普通计时外。

真实服务有意启动后，先确认成功/就绪再测量。分别在独立读取、启动 dashboard 重叠、已有客户端心跳、错开到达、排队/观察者退出场景至少记录 20 次成功观测，并进行有界双/八读取压力测试。单列失败及类别，不能把 503 当快速成功。对新捕获的 >=8 秒请求，阶段区间与端到端时间误差应在 5% 内，否则明确保留无法归因的缺口。发布中位数、范围/最大值和全部样本，不根据小样本推断 p95，也不能在未复现时宣称已复现历史请求。

## RLT05. 条件式 P1：去掉重复事件编码，保留完整证明

P0 之后，评估仅当前行存活的已验证规范表示，供紧邻的 payload 相等检查和有序事件集摘要复用。保留统一校验核心及现有公开辅助函数行为。保留类型模型校验器与事件哈希、存储 content domain/hash、SQL 与 payload identity、version/authority/time 绑定、sequence/run membership、count、带长度前缀的有序事件集哈希，以及报告/输入/冻结日/诊断检查。继续遍历按保留状态要求存在的全部行；EXPIRED/NOT_RECORDED 处理须保持真实，不能从内存恢复已过期证据。

被忽略目录内的进程级可行性实验，仅在同一受管不可变事件下一次编码时复用已有文本，上限为 1 个事件 / 256 KiB，物理完成即释放。5 轮交替观测的结果中位数为 2.0852 → 1.8925 秒，CPU 为 2.0625 → 1.8438 秒（约 9.2% / 10.6%）。每次遍历减少 2,961 次编码，该样本最多保留 8,419 UTF-8 字节；完整响应对象和响应哈希均一致。这不是生产代码、完成证明缓存、临时/进程内存验收测量或完整性/篡改验收结果，也不保证消除原来多秒波动。

生产设计应在行校验/流摘要流程内直接传递已验证字节，不引入通用对象身份缓存或外部传入的预验证标志。计入对象/字符串开销，每行及时释放，保留全部现有类型/大小/Decimal/时区/规范规则并安全拒绝。不能换编解码器或 JSON 模式来省遍历。禁止仅凭 run-id/report-hash/mtime/data-version 信任、只读最新记录或先响应再后台校验。

建议实施验收：同一 2,961 事件样本至少交替测量 10 轮、不插桩，目标 CPU 和 wall 中位数改善 >=10%，峰值内存退化 <=10%，现有混合场景退化不超过 10%。当前探索性 wall 改善 9.2% 尚未达到建议的 10% 目标。仅保留重复证据通过选定门槛的正式实现，不为适配原型而降低门槛。覆盖零/小/大轨迹、两种事件 schema、非零成交/receipt、Unicode/Decimal/时区边界、SQL/row/event/report/ordered-set 哈希改变、缺失/重排/额外行、retention/pin/publication 变化、取消/全部观察者退出和真实存储排空。移除相关检查的变异必须被捕获。

## RLT06. 条件式后续工作与保护边界

如果 P0 发现重型 review-context 阻塞廉价元数据，单独评估将该读取交给现有有界 result 所有权管理。保留每个调用者全新的 membership/pin/retention 检查，不新增 CPU worker pool。如果消除实测重复后仍由 CPU 竞争主导，进程隔离需要独立的事务、IPC 复制/内存、取消、子进程失败和物理排空规格，不是快速配置修改。
