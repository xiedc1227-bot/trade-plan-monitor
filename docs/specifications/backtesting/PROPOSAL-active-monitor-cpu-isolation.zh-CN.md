## AMC01. 结论与范围

保留的 6.502 秒结果请求，其服务端区间的 99.678% 位于结果工作线程内。它与一次实际监控 HTTP 读取重叠，而非断连 socket 心跳。结果工作线程消耗 2.578125 秒 CPU，监控快照消耗 2.6875 秒 CPU。证据支持活动 CPU 竞争，但不能将全部耗时增加独占归因于 GIL 等待。独立权威检查也存在墙钟时间明显、线程 CPU 很少的情况，需要继续细分。

建议先完成 P0 归因与隔离可行性实验，再有条件地推进 P1 纯指数证据校验进程隔离。权威采集以及每个请求的事务/组装保留在父进程。不将整个监控读取或权威提供器迁入进程或任意工作线程。本方案不修改生产代码、服务状态、配置或历史数据，也不提交/推送。

## AMC03. 覆盖与剩余不确定性

离线对齐覆盖全部 80 次直接结果响应及其物理关联。优化后轮次的 20 个 `live-monitor-overlap` 样本中，只有 10 个实际与捕获的 `monitor.read` 重叠，其结果中位数/范围为 3.7745 / 2.258–6.502 秒。其余 10 个的中位数/范围为 2.246 / 2.030–2.621 秒。阶段名称仅表示有客户端连接，不表示每次结果读取都与 CPU 校验重叠。评估下一步改动时必须区分。

优化后另一次独立发起的请求，在未捕获监控重叠时仍耗时 4.752 秒。采集有界，即使记录中丢失区间为 0，也不能证明所有竞争线程/进程/请求均被追踪。当前证据无法唯一拆分 GIL、系统调度、SQL/文件等待和 GC。快速样本中墙钟减线程 CPU 的小负值按时钟/记账粒度影响保留，不截断成精确等待。两轮所有者及后台活动不同，不能从这些分组推导因果提速或总体 p95。两轮各 7 次受保护的 HTTP 503 继续在原始证据中单独保留。

## AMC04. P0：有界归因与可行性

实施前补齐语义等价的英文/中文规格与任务。保留当前源码及冻结证据指纹。在现有 1800 秒 / 1024 条追踪 / 64 个活动追踪 / 64 个区间 / 128 条已完成记录 / 1 MiB + 2 个备份边界内，增加默认关闭的聚合诊断阶段：

- 将权威检查细分为事件循环采集、健康/投递 SQL、配置/语义检查及依赖/进度采集，不改变顺序或结果。记录有界事件循环延迟和可选 GC 时长；不逐行记录区间，不记录 SQL/正文/凭据。同步观测不能在一次权威采集中让出执行或改变其原子性。
- 分开记录指数收集/扫描、原始输入精确比较、主从等待及物理类型/哈希/规范格式校验。记录墙钟和工作线程 CPU、候选/字节数、加入/不匹配/回退、取消、队龄及物理完成。逻辑调用关联到同一个物理证明，CPU 仅计一次。
- 对每个捕获到的 >=5 秒结果请求，将区间对齐到服务端总耗时的 5% 以内，未归因差值原样保留。保留原有提交/启动/准入/发布/审计/响应头/响应体阶段。观测开关开销目标仍为 <=2% CPU / <=5% 墙钟，性能分析器运行单独统计。
- 在忽略目录中，针对相同不可变输入做隔离实验：既有线程校验与 1 个 Windows spawn 进程内完全相同的纯校验器对照。测量冷启动/导入、热执行、父进程编解码/复制 CPU、IPC 延迟、子进程 CPU 和合计内存。保留每一行的原始类型/规范字节，比较完整校验结果。生产权威、ORM/session/engine、活动时钟或配置对象不得跨 IPC。冻结的无所有者夹具仅用于可行性对照，不冒充真实所有者验收。

不为本次分析重启真实服务，也不向用户流量附加性能分析器。后续真实所有者测量必须在服务有意可用、有界诊断窗口下进行，保留就绪、正常关闭/排空及历史数据，并区分新采集和保留的 6.502 秒观察。P0 应给出测得的推进/停止结论，进程隔离尚未成为获验收的实现。

## AMC05. 条件 P1：仅隔离纯指数校验

现有 `RawIndexCandidate` 包含冻结的原始 SQL 列及原始载荷字节；`IndexEvidenceFlights` 已完成有界输入收集、每个跟随者自身新扫描的精确比较，并拥有单个物理校验器。这是候选最小边界：获准入的主读取在 1 个受管理子进程中调用既有 `_latest_index_records` 校验核心，再继续各调用者原有的父进程组装。结果审计校验保留现有路径。

父进程职责保持不变：每个调用者的前权威检查、观察时间、BEGIN 快照、全新精确输入扫描/比较、命名空间/激活/当前输入检查、组装与后权威检查，保留全部既有比较及最多 2 次尝试。子进程使用原有类型模型、域哈希、元数据/head/提供器/公式绑定、规范字节直接相等比较及校验后排序，对所有传入候选逐一验证，包含未被选中的损坏历史。封闭的内部 IPC 信封将提交的在途身份、有序完整输入、数量、语义版本及完成状态绑定到返回的不可变结果；该信封仅补充原有证据校验，绝不替代。缺失、截断、重复、其他在途任务或失败的子进程输出必须拒绝。

保留 1 个物理校验器、1 个不同输入排队所有者、8 个拥有的读取、15 秒协作等待/检查点预算、64 MiB 保留证据上限、当前元数据/结果闸门及仅在途精确输入共享。不引入通用进程池或更大队列。父进程必须持续拥有已提交子进程工作，直到实际完成/确认退出、消费结果及清理；观察者退出不得提前释放许可或字节。单个跟随者退出不能取消仍有活动主/从观察者的证明。全部观察者放弃时采用协作取消及物理排空，不将强杀工作进程作为常规取消捷径。关闭、子进程崩溃/挂起及存储清理失败必须保留暂停/围栏，不能授权释放数据库或返回成功。重复取消仍需等待清理并保留原始取消身份。

IPC 会引入原始输入计数以外的额外副本。P0 必须测量；P1 规格必须在实施前固定合计输入/复制预算，统计父进程/序列化/子进程/输出/瞬时对象，并保留现有 64 MiB 边界，不能给每份副本各套一个相同上限。完整缓冲传输无法容纳时，另行评估有界流式传输，或针对该请求保留现有全量校验线程路径。提交前回退必须明确并进入性能统计；子进程失败不得静默创建重复工作或重置截止时间。不为后续调用者保留已完成证明或响应。Windows spawn 入口安全、惰性子进程所有权及物理排空后的子进程回收需要独立测试；普通 Python future 取消无法取消已经运行的任务。

如权威子阶段仍是主要停顿来源，应以单独改动和明确的权威一致性设计处理。将整个提供器迁到 `to_thread`、缓存此前权威/健康结果，或响应后再检查权威，均不在本方案内。

## AMC06. 测量与验收建议

采集前固定样本数量/顺序；保留失败、回退、冷/热启动及不满足重叠条件的样本。相同输入和边界下，针对隔离及主动错峰的混合可行性场景，运行 10 对 A/A 对照和 20 个交替 ABBA/BAAB 块（每版本 40 次观察）。分别记录结果完成与整批完成，记录实际重叠和全新的前后权威检查配对，不能仅统计连接数。合成闸门/延迟用于确定性竞争测试，不计为真实延迟收益。

真实所有者验收应预先固定主活动监控 HTTP/结果负载每版本 100 次尝试，另行覆盖活动心跳、错峰到达、排队/取消观察者及有界 2/8 客户端负载。HTTP 失败全部保留在分母中。报告成功条件下的延迟及拒绝/取消/超时、墙钟/CPU 分区、父子进程合计 CPU、事件循环延迟、子进程数量、保留字节及合计 RSS/private 峰值。小样本报告中位数/范围/最大值；只有每版本 >=100 次成功观察且披露不确定性时，才声称 p95 性能变化。不延长运行直到达标。

建议推进/停止门槛：受控混合结果墙钟中位数改善 >=20%；只有达到所需成功样本数量时，主真实混合 p95 改善 >=20%；隔离结果中位数回退 <=5%；监控完成中位数及父子进程合计 CPU 回退 <=10%。要求受保护拒绝率不变差，无新增超时/泄漏，不削弱权威/证据断言。在生产实现前根据 P0 固定绝对合计内存预算；不能将父进程 CPU 降低描述成总 CPU 降低。这些是建议目标，不是已测收益，也不保证每次请求都小于 6.5 秒。未达标或内存/生命周期失败则暂缓 P1，保留当前行为。

正确性矩阵：旧/未选中历史及同长度/恢复时间篡改，非法类型载荷，head/提供器/公式/行/哈希/规范格式不匹配，输入缺失/重排/增加，保留规则/pin/发布变化，激活/代际/配置/进度变化，日期/目标/90 秒边界，近上限载荷及字节回退，主/从/全部观察者离开，提交前/IPC/校验/返回阶段取消，重复取消，子进程失败/挂起，stop/checkpoint/close 竞争，以及清理失败保留正确存储暂停。移除规范/完整性、权威、在途绑定、子进程完成及排空闸门的变异必须被检出。浏览器验证覆盖结果/来源/刷新/返回监控及活动心跳/重连，检查完整响应且无业务写入。

## AMC07. 备选方案与顺序

| 备选方案 | 评估 |
|---|---|
| 增加线程、延长等待或提高证据/读取上限 | 不会消除 GIL 约束的工作，可能增加竞争；排除 |
| 全局串行或结果优先 CPU 调度 | 可能将延迟转移给监控/排队结果并饿死检查；不作为默认下一步 |
| 共享整份健康/权威或保留已完成证明 | 改变新鲜度及已接受共享边界；排除 |
| 重做已否决的 Decimal memo 或结果规范字节 P1 | 既有实验未通过门槛，无新证据支持重启 |
| 1 个进程内的纯指数校验器 | 推荐的可行性边界；可能改善并发，IPC/内存/生命周期代价尚未测量 |
| 细分归因后迁移权威 I/O | 单独条件工作；保留事件循环所有权及明确一致性契约 |

Python 文档说明 CPU 密集线程的 GIL 限制及独立进程的隔离能力：[threading](https://docs.python.org/3.14/library/threading.html)。运行中的 future 无法通过普通 executor 取消停止，进程任务还存在序列化/导入约束：[concurrent.futures](https://docs.python.org/3.14/library/concurrent.futures.html)。放弃线程等待者不会终止物理工作：[AnyIO threads](https://anyio.readthedocs.io/en/stable/threads.html)。这些依据支持边界选择及所有权要求，不构成本应用的性能预测。
