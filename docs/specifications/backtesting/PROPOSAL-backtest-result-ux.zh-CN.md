# 回测结果阅读与原因定位交互优化方案

状态：设计提案，不代表实施批准。日期：2026-10-20。代码基线：`6fc98f1`。[英文规范版本](PROPOSAL-backtest-result-ux.md)。

## UX01. 目标与范围

用户明确指出，主要问题是**结果难读，难定位交易和原因**。优先改善已完成回测的复盘：理解结果、选择成交或未成交记录、查看当时依据，无需手工寻找事件 ID。

沿用 `backtest-web` → `backtest-api` → `backtest-results` 的模块边界。本方案调整展示方式，并提出有界只读接口，不改变 `backtest-engine` 的决策。配置简化和运行对比放在后续。

围绕四个问题组织结果工作区：

1. 这次回测发生了什么？
2. 这笔交易为什么成交？
3. 为什么有条件或提醒，却没有成交？
4. 当时采用的是哪份计划和哪些历史依据？

以下问题来自源码、现有契约与测试检查，不是用户研究或真实行情浏览器验收的测量结果。

## UX04. 建议的信息架构

保留 `/backtests` 历史记录、`/backtests/new` 创建回测和 `/backtests/:runId` 结果入口。结果标题改为用户可读的“股票＋研究区间”；运行 ID 缩略展示，完整值在来源信息中可复制。

| 主区块 | 回答的问题 | 默认内容 |
|---|---|---|
| 结果概览 | 发生了什么？ | 适用的财务数据、成交笔数、未成交意图数、期末持仓、计划级异常及复盘入口 |
| 交易复盘 | 为什么成交或执行失败？ | 精简记录、时间／计划筛选、选中记录依据、费用与持仓变化 |
| 未成交原因 | 为什么没有交易？ | 现有逐份计划诊断、响应模式、计划要求与实际依据、精确记录入口 |
| 计划与来源 | 用了什么规则和数据？ | 冻结计划版本、规则变更、运行设置、证据截止与可复制核对标识 |

以次级入口保留“审计事件”，供查看完整记录顺序。模式和可用性允许时保留参考指数、权益视图。现有 `tab=summary|fills|details|equity|market-index` 链接继续可读，新展示路由不得重新解释历史含义。

桌面布局：紧凑标题和指标 → 导航 → 左侧复盘列表、右侧选中依据。依据面板约占复盘区域 40%，并设置可读最小宽度。小于 1024px 时将依据放在选中列表下方；小于 768px 时采用纵向记录摘要。必要时移动端使用独立详情视图，返回恢复筛选与选择。

会话中的交互示意使用明确标记的模拟数据，演示记录选择和两种原因状态，不是已实现产品的截图。

## UX05. 如何阅读结果概览

### UX05.1 财务数据

- 保留 `BacktestProfitSummary` 的成本口径总盈亏、已实现盈亏、浮动盈亏；将费用、成交数作为紧凑辅助信息，避免长列表重复金额。
- `POSITION_LIMIT_ONLY` 优先展示盈亏金额、费用、持仓和执行情况；以简短资金模式说明替代不适用的权益／收益率／回撤指标。不虚构本金、收益率、Sharpe ratio 或超额收益。
- 历史 `KNOWN` 资金模式在有效时继续展示权益及服务端已有比例；比例转换为易读百分比，不改变规范值。`UNKNOWN`、估值不完整和期初成本缺失继续明确展示未知。
- `null` 表示不可用，不是零。已经计入盈亏的费用不能再次扣除；账户累计盈亏不能标成单笔盈亏。
- 同时展示研究区间与实际 `evidence_cutoff`，统一使用 Asia/Shanghai；证据不足对结果的影响放在对应数据旁。

### UX05.2 可直接进入复盘的问题

提供“查看执行受阻记录”“查看依据不完整的计划”等简短入口。全运行查询尚未提供时，入口明确写成打开**计划代表性样例**，不能暗示进入全部符合条件的事件。

不要将不同口径的计数绘成成交漏斗：`evaluations`、条件、提醒、意图、执行尝试和成交单位不同；一个意图可能多次尝试，`unfilled_intents` 不等于 `BLOCKED` 尝试次数。

## UX06. 交易复盘与因果解释

### UX06.1 精简记录

桌面默认列：时间、方向、数量、成交价、费用、结果、“查看原因”。完整 ID、分项费用、释放成本、批次分配和现金明细放入选中面板。P0 可以直接展开已有回执事实，但必须如实说明尚不可用的因果详情。

P1 增加全运行日期、计划版本和执行状态筛选。成交与执行尝试分开：允许切换“已成交记录”和“执行尝试”，受阻的尝试不能算一笔交易。展示明确数量和状态文字，不只用颜色。

服务端提供经过验证的逐笔记账投影后，才能提供逐笔盈亏排序。买入可以标为“不适用”，缺少期初成本的卖出可以标为“未知”。不得用两页任意相邻数据相减推算卖出盈亏，也不得在浏览器按 FIFO 自行匹配买卖。

### UX06.2 选中记录的依据

选择记录后，在保留列表上下文的同时打开一个依据面板：

1. **一句结果说明：**依据已记录的结构化事实生成简明解释。
2. **计划要求与实际依据：**版本、规则、比较方式、门槛、实际值、时点，以及已记录的数据频率和价格基准。
3. **因果路径：**计划背景 → 评估 → 提醒 → 请求 → 执行 → 持仓／账户结果。使用真实 `cause_event_id` 边和明确版本／权限绑定，不能将计划背景虚构成因果边。
4. **执行限制：**完整数量授权、可卖数量／T+1、最大持仓、响应模式、响应延迟及已记录阻断原因。
5. **记账信息：**价格、数量、费用、释放成本，以及有权威快照时的前后持仓。
6. **核对详情：**完整 ID、原始枚举／原因码、精确值和来源。

文案示例，不代表某次真实运行的结论：

- “买入条件满足，按所选响应延迟模拟买入 100 股。”
- “目标批次可卖 0 股，本次卖出尝试未成交。”
- “所需历史窗口不完整，无法判定条件满足或不满足。”

不将即时 AI 叙述作为默认解释。采用确定性的展示映射与证据，未知原因码保留原文。不能将已记录失败描述为修改计划后必然可自动修复。

### UX06.3 定位与返回

使用可恢复选择的 URL，例如拟议的 `/backtests/:runId?tab=trades&fillId=...`、`/backtests/:runId?tab=reasons&versionId=...&sequence=...`。验证身份和不兼容参数组合，打开／关闭记录保留筛选条件。

浏览器前进／后退恢复选择和筛选。通过已访问游标历史增加明确的上一页，不伪造未签名游标。直接打开深链接且没有前页历史时，可以显示“返回第一页”。

跨页原因按身份读取，不下载前面所有分页。切换运行或选择时取消旧请求、清理旧依据。点击参考指数日期时，将日期保留在结果查询中并在服务端应用。

## UX07. 解释未成交，同时保留不确定性

将 `PlanExecutionDiagnostics` 提升为独立、明显的区域。每份计划展示生效日期、可用时的成交数、响应策略及现有分类：

| 现有分类 | 用户含义 |
|---|---|
| `MARKET_UNMET` | 行情条件未满足 |
| `QUALITATIVE_UNRESOLVED` | 定性条件未量化或未核验 |
| `PROCESSING_ERROR` | 已记录的提取或校验问题 |
| `DATA_UNAVAILABLE` | 行情依据不足 |
| `EXECUTION_BLOCKED` | 执行或响应限制 |
| `NO_BUY_RULE` | 未授权直接买入 |
| `NO_EVALUATION` | 没有可用评估 |
| `CONDITION_MET` | 条件满足，需要继续检查执行 |

`LoopDiagnosticExample` 已有 `sequence`、`requirement`、`actual`、`root_outcome` 和 `reason`。P0 先把这些信息展示清楚，P1 再让样例直接进入相应上下文。

现有诊断每份计划最多 8 条样例、合计最多 256 条，必须保留 `sampled` 提示。不能将抽样结果当作原因总数、占比或排名。已有评估计数包含重复时点评估，不代表独立交易机会数。

`OBSERVE_ONLY` 要醒目说明本次没有请求模拟响应。`NO_BUY_RULE` 不代表计划没有卖出或风险退出行为。`ANY` 条件中已有分支满足时，不能把未使用分支解释成阻断原因。沿用服务端 `root_outcome`，前端不重新计算条件树。

### UX08.1 已有能力如何复用

| 需求 | 已有支持 | 仍需工作 |
|---|---|---|
| 结果概览 | 指标、`report.cycle`、期末持仓和截止边界 | 展示重组及资金模式适用性 |
| 成交基础信息 | `BacktestLoopFillView.eventId`、回执结算、账户和持仓 | 展示模型保留身份，精简行与回执面板 |
| 代表性原因 | `planDiagnostics` 和样例 `sequence` | 选择及精确读取 |
| 事件关联 | `event_id`、`cause_event_id`，连续模式的 `version_id`、`authority_id` | 有索引、有界的原因及后续结果查询 |
| 全运行查询／筛选 | 已有签名游标有界分页，但缺少相关筛选 | 新公开查询契约和读取索引 |

| 图表联动交易 | 已有权益图的坐标提示，缺少选择和缩放契约 | 共享选择、有界序列及已验证标记身份 |

### UX08.2 候选接口

以下路径和字段为**拟议设计**，不是现有 API。实施前在中英文 `SPEC-backtest-api`／`SPEC-backtest-results` 中确定具体契约，并重新生成客户端类型。

| 候选读取接口 | 用途与约束 |
|---|---|
| `GET /api/v1/backtest-runs/{run_id}/review-events` | `startOn`、`endOn`、`versionId`、`eventKind`、`executionStatus`、`reasonCategory`、`limit`、`cursor`。参数单值，拒绝未知、重复及不兼容组合。`executionStatus` 仅适用于 `EXECUTED`，原因分类由服务端定义。 |
| `GET /api/v1/backtest-runs/{run_id}/review-context` | `fillId`、`eventId`、`sequence` 三选一，另有 `limit,cursor`。返回选中记录、已验证原因／后续结果、冻结计划背景及明确缺失的关联。 |
| `GET /api/v1/backtest-runs/{run_id}/review-series` | 仅 P2：指定区间和受支持序列标识，返回有界图点与稳定事件引用；提供序列适用性、来源频率、价格基准和可用性。 |

拟议限制：列表／上下文默认 20 条、最多 100 条，图表最多 2,000 点，每个响应沿用现有小于 4 MiB 的结果分页边界。大型因果上下文分页并标记省略／缺失关系。游标绑定运行、规范化筛选或选择器、稳定排序和快照／高水位。

新接口区分 `availability`（`AVAILABLE`、`EXPIRED`、`NOT_RECORDED`）、查找完整性（`COMPLETE`、`PARTIAL`）和投影就绪状态（`READY`、`NOT_READY`）。这些是拟议字段，不替换旧 schema。在可用结果中找不到身份是查找失败，不是“零成交”。原因明细过期时，仍保留长期成交记录。

只读已验证、已发布的产物。任何 GET 都不能启动任务、调用行情供应商、执行 AI 提取、重放决策、重建过期证据或按需构建全运行索引。

如果现有索引不足，增加身份、序号、时间、计划、事件类型和因果边的派生读取索引。发布时构建，或通过明确、有界的维护操作处理仍保留且已验证的记录。关联现有内容哈希，不改写规范事件载荷、结果哈希或历史结果。缺少索引的旧运行继续可通过现有视图读取，并说明精确定位限制。

### UX08.3 图表边界

`POSITION_LIMIT_ONLY` 仅在存在适当冻结序列时绘制已记录的累计盈亏金额和持仓。单个运行总额不足以生成每日曲线，P0 可以不放图表。

价格 K 线、买卖标记和动态规则线放在 P2。需要从本次冻结数据集中提供有界视图，并匹配价格基准与频率；不得读取今天的复权序列，也不得无标记混排日线和五分钟数据。降采样只影响展示，不改变精确表格和事件定位。数据缺口保留断点，不插值补齐缺失证据。

## UX10. 建议实施顺序

以下是拟议交付切片，不是已完成任务，也不修改项目当前任务清单。

| 切片 | 交付内容 | 依赖／完成条件 |
|---|---|---|
| P0 阅读改善 | 按模式调整概览、精简成交默认列、展开回执、突出逐份解释、折叠来源和优化文案 | 可复用现有读取。明确代表性／当前页范围，不宣称全局搜索或完整因果链。 |
| P1 精确定位 | 上下文读取、事件筛选、诊断深链接、跨页原因、上一页历史、稳定 URL 选择、已验证记账投影 | 明确并实现公开契约、读取索引策略、保留期行为及后端契约测试。这是解决定位困难的核心。 |

## UX12. 设计取舍与评审状态

- 采用列表旁展开依据，避免为每类数据继续增加独立标签，保留复盘上下文。
- 采用精确记录解释，优先于 AI 总结，保持结论可追溯、未知依据可见。
- 采用小范围服务端读取扩展，避免下载全部分页，在有界读取下解决跨页定位。
- 采用适用的盈亏和执行数据，避免通用绩效仪表盘，因为主要资金模式没有本金分母。
- 暂缓优化器、策略排名、自动执行、批量任务和基准收益功能。
