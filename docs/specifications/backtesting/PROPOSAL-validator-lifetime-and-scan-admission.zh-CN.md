# 校验器生命周期与独立扫描准入

## VLS01. 决策

继续开展隔离 P0，分别测量校验器表示生命周期和 SQL 扫描并发限制两个候选方向。P1 仍为 NO-GO。本分析承接 `72bd925`，不修改生产代码，不授权实现或推送。实现前补齐双语规格和任务。保留已有改动及并行 AI 提取、日库存工作。

[上一轮报告](../../verification/evidence-representation-2026-10-22.zh-CN.md)中的合法大输入可用性、并发 CPU/延迟及原生内存边界仍未通过。新增[脱敏证据](../../verification/evidence/2026-10-23-validator-lifetime-analysis/analysis.json)包含测量、限制及可复现探针源码，冻结监控数据库字节保持不变。以下发现用于选择候选方案，不代表集成门禁通过。

## VLS02. 内存在哪里重叠

当前路径为 `RawIndexCandidate.decoded()` → `MarketIndexSnapshot.model_validate_json()` → `canonical_value()` → 域哈希 → 最终规范化序列化 → 存储字面内容/标量比较 → 排名。证明期间持续持有原始输入字节。解码 JSON、解析模型和规范化树同时存活；域序列化又引入临时字符串、UTF-8 编码和拼接后的哈希输入。最终规范化字符串在域哈希完成后生成，不能把这些不同阶段的峰值直接相加。

进程内边界探针使用受支持的 16,472,833 字节样例，包含 480 根 bar 和 8500 位小数。原校验器接受该输入。JSON 含中文显示名称：16,472,825 个字符的解码字符串占 32,945,708 字节。虽然主要内容是 ASCII 小数，它并非全 ASCII JSON 文档。

| 边界 | 已跟踪存活字节 | 累计峰值字节 |
|---|---:|---:|
| 模型解析前 | 32,946,766 | 32,947,060 |
| 模型解析后 | 57,247,373 | 98,838,172 |
| 模型导出前 | 57,247,913 | 98,838,172 |
| 模型导出后 | 57,475,187 | 98,838,172 |
| 首次域编码前 | 73,973,570 | 98,838,172 |
| 快照域编码后 | 106,921,559 | 115,068,947 |
| 快照 SHA-256 入口 | 90,449,062 | 156,340,002 |
| 完整校验/排名后 | 7,841,664 | 156,340,002 |

本样例模型导出边界仅增加 227,274 字节存活量。Decimal 规范化和整份文档的表示，比这个字典本身更值得优先处理。最大峰值约 149.10 MiB，出现在快照域编码返回到哈希入口之间的输入构造阶段。编码临时量、Unicode 缓存和拼接分别占多少，仍需更细粒度及原生剖析，才能承诺具体节省量。解析阶段已经达到约 94.26 MiB，仅移除最终字符串不能解决全部峰值。

这些是构建原始样例后开始跟踪的 Python 分配，包含包装器开销；不包含预先构建的原始输入，也不约束原生分配或进程工作集。规范化 bar 列表和快照 payload 字典主要共享引用，把它们各算成深复制会高估内存。被选中的最新模型需要保留用于输出。循环还可能在校验下一行时保留上一行候选/模型；应明确验证该生命周期及异常 traceback 的持有情况。

## VLS03. 单请求 CPU 成本

实际监控请求 `ALWAYS_ON_INDEX_CODES`：冻结样例中为 5 个指数、2008 条历史候选。最初仅覆盖面板的 1628 行探针不计入正式公布的计时证据。校准后的探针使用独立显式读事务，运行 3 轮；下表为未启用剖析时的中位数。

| 计时区域 | 墙钟秒数 | 线程 CPU 秒数 |
|---|---:|---:|
| 完整元数据预检 | 0.0269 | 0.03125 |
| 有序 payload 扫描，不含预检 | 0.0389 | 0.03125 |
| 有序 payload 扫描及精确比较，不含预检 | 0.0464 | 0.046875 |
| 原完整校验器/排名，不含 SQL | 1.8468 | 1.84375 |

扫描与“扫描加比较”是两项替代测量，不能当成独立阶段相加。Windows CPU 采样存在量化精度。另一次带剖析的运行发现重复工作：2008 次 shape 加 2008 次 `dataclasses.replace()`，共构造 4016 个 shape，并执行 2008 次精确比较和保留体积计算。比较仍覆盖全部 19 个选取字段及存储类型。不能用单请求几毫秒的差值解释并发时数秒的延迟。

完整校验剖析记录了 1,236,442 次 `canonical_value()`、447,344 次 `canonical_decimal()` 和 892,736 次 Decimal `as_tuple()`。模型校验还检查 Decimal 展开长度和 bar 关系。这支持后续评估规范化和类型分派的 CPU 成本，但不授权删除任一层校验。剖析累计时间彼此重叠，且受到插桩影响；不能除以上述未插桩的 1.8468 秒来计算占比。

## VLS04. 并发扫描放大 CPU

即使没有物理校验器，8 个独立预检同时执行，CPU 中位数已达 4.15625 秒、墙钟 0.7118 秒；1 个预检仅为 0.03125 CPU 秒。完整“元数据加 payload 加比较”批次消耗 7.015625 CPU 秒、1.3345 墙钟秒。因此，无须运行证明就能复现扫描侧的放大。但不能将本次耗时加到之前完整共享组的测量上，两者调度及重叠不同。

另一项敏感性探针保持 8 个请求，每个请求均执行自己的完整事务、元数据预检和精确 payload 比较，仅改变同时扫描数。3 轮交替顺序测量中，每种配置均成功完成 24/24 次比较。

| 同时扫描槽位 | 批次墙钟中位数，秒 | 进程 CPU 中位数，秒 |
|---:|---:|---:|
| 8 | 1.3226 | 6.765625 |
| 4 | 0.8226 | 2.515625 |
| 2 | 0.5361 | 0.921875 |
| 1 | 0.5893 | 0.59375 |

建议先评估 1、2 个槽位，再微调相等比较。本样例中 2 个槽位延迟较低，1 个槽位更省 CPU；尚不足以选择生产默认值。SQL/Python 边界切换、GIL 重获、原生分配器/互斥竞争及调度，仍是具体放大机制的待验证假设。探针证明了对并发度的敏感性，没有把原因定位到某一把锁。

敏感性探针刻意在开启事务前获取槽位，使用各自独立的实验预算和未计入预算的预建主请求输入。它不覆盖共享证明、权威检查、全局字节账本、取消和清理失败。生产不能直接把这个包装器套在整个读取/共享调用外：若主请求持有唯一槽位等待已获预算的跟随者，会产生死锁。

## VLS05. 内存候选顺序

1. **先减少表示重叠，保留模型契约。** 实验让原模型解析器直接接收 UTF-8 字节，同时保留原始 SQLite TEXT/BLOB 区别和严格的非法输入行为，与旧“解码再解析”路径比较。只移除已证明不必要的解码文本及上一轮引用，保留选中输出模型和原始证明输入的所有权。不得改用 `model_construct()`、`json.loads()` 后宽松校验或仅校验最新记录。
2. **移除整份哈希副本。** 先实验按域增量更新哈希，替代完整域前缀与 payload 拼接；再评估所有域哈希的增量规范化序列化及与存储字面内容的逐块比较，包括精确的输入结束检查。保留字节顺序、转义、分隔符、键排序、Decimal 格式、时间精度、请求/bar 顺序和全部公式/哈希校验。需要字符串的调用方继续使用现有公共 API，私有证明接口另行规定。
3. **约束生产者，不能只约束消费者。** `JSONEncoder.iterencode()` 会输出片段，但不承诺片段大小上限。切分一个已经分配的大 token 不能证明分配前安全。编码器 token、UTF-8 扩展、排序引用、比较缓冲、模型/原生解析工作量及重叠代际都必须按原有分类计费。有界输出需要最大 token 证据，或具备正确规格的标量流式编码器。不得把原本计费的输入文本移出 64 MiB 账本来制造通过结果。
4. **最后才考虑直接遍历模型。** 了解 schema 的规范化遍历器可能省去规范化树和重复通用分派，但等价性改动更大。评估前覆盖序列化器、别名、字段新增、精确模型类型、可选值及全部标量规则。前面改动已足够时优先延后。保留有限数/展开长度检查，不引入无界跨请求规范化缓存。

各候选分别测量后再组合。细碎的增量哈希更新可能增加 Python 调用/GIL 开销，Python 流式编码器也可能失去当前快速编码路径。在现有字节预算内比较缓冲大小；内存减少不自动等于 CPU 改善。解析器及原生分配仍可能让大行无法满足边界。合法输入仍失败时继续阻断 P1，不能提高限额或把准入失败称为成功回退。

## VLS06. 独立扫描的 CPU 准入

增加实验扫描许可，与请求准入、物理证明准入分离。保留 8 个已准入读取者、1 个物理校验器和 1 个排队所有者。先比较固定 1、2 个扫描槽位，不引入自适应调度。每个请求仍在原事务中独立完成全部元数据测量和字面比较，不共享预检证书、事务或已完成证明缓存。

实现前定义资源顺序。在协调器/数据库清理锁之外，先取得或预留该 SQL 阶段需要的全部字节租约，再获取扫描许可。一旦取得许可，该阶段不能继续等待其他字节资源。等待输入发布、已获预算共享组结束、排队所有者或证明结果之前，必须关闭游标并释放许可。主请求必须在等待已获预算的跟随者之前释放 payload 扫描许可。预留和待完成跟随者保持有界，明确测试饥饿、旧代际借用者和主请求前进保障。不得在整个 `Flights.run()` 调用期间持有扫描许可。

许可等待沿用原截止时间及取消/停止信号，不刷新权威状态、观察时间或证明有效期。添加许可时保留既有事务边界，测量在读事务内等待对 WAL 和事务寿命的影响。前述“事务前准入”探针不构成移动生产权威检查或事务边界的安全证据。

完整共享组的准入测量完成后，再考虑移除第二个 shape 分配、合并固定字段测量循环或按字节准入的批量 fetch。保留类型、基数、顺序及实际大小检查。不能用存储哈希、元数据相等或混淆标量类型的 Python 元组比较替代精确内容比较。任何批量 fetch 都须在读取前预留字节，包括驱动预读和同时存活的前后行；固定行数缓冲不足以证明安全。

## VLS07. 完整性与生命周期不变量

每个请求保留独立的前后权威检查、activation 复读、原事务/观察时钟及 2 次尝试行为。保留 15 秒等待截止和 90 秒有效期边界。只有完整相等后才可共享仍在途的纯证明。校验全部历史候选、缺失 payload、head 身份、标量/存储类型、规范化字面内容、bar/request/snapshot 哈希、逐 fact 公式哈希及现有模型约束。不信任存储哈希，不走仅最新记录捷径。

取消只移除观察者或未启动准入，不能返还仍被 SQL 缓冲、原始输入引用、解析/编码或已提交 worker 传输占用的预算。保持所有权，直到实际物理排空，以及适用的 `DRAINED` 或受监督 worker 退出/桥接清理完成。跟随者不能取消其他读取者的证明。游标/worker 清理失败须跨代际保留字节债务和存储围栏；释放信号量不能伪装成存储清理完成。停止时唤醒字节和扫描等待者，但不重新开放准入。

必测场景包括接近上限的合法 ASCII/中文/补充平面 Unicode 行、超长 Decimal、非 JSON 大列、新旧行及异常引用；非法 UTF-8/BLOB/NULL/数值存储；各类哈希与标量篡改、缺失/增加/乱序行、非规范转义、重复键和尾部内容。验证输出生产者的分块边界与分配前内存，不能只检查最终输出相等。覆盖相同/变化输入、快证明慢比较、迟到请求、边界两侧截止、等待期间权威变化、跟随者/主请求取消、停止及游标/worker 清理失败。确定性相等重叠须保留 1 次证明和 7 次加入，且不得接受已完成证明。

## VLS08. 交付与决策门禁

1. **P0-A 契约与归因：** 补齐双语规格/任务，复现完整 2008 行范围；分别追踪解析/规范化/编码/哈希/字面比较，以及 SQL execute/fetch/测量/比较/许可等待及线程 CPU。记录原生分配、父子进程峰值、用户态/内核态 CPU 和资源所有权。插桩归因与计时验收分开。
2. **P0-B 校验器生命周期：** 分变体实验字节解析、引用释放、增量域哈希和有界规范化比较。用完整旧校验器对合法与篡改输入做差分验证。只有确有需要且测量支持时，才为新遍历器制定规格。
3. **P0-C 扫描准入：** 在相同全局账本下的完整已获预算共享组中比较 8、2、1 个槽位。先验证等待关系、独立权威检查、物理排空、清理失败及合法大行/混合负载，再考虑组合结果。之后才评估测量/fetch 微优化。
4. **P1 决策：** 保留冻结的 64 MiB 输入限额、768 MiB 工作集和 2560 MiB 私有提交实验上限，以及原生/所有权证明和可用性门禁。采样不等于硬边界证明。前置线程正确性/可用性通过后才恢复进程传输；任何硬门禁失败均停止固定性能验收。

通过门禁的候选仍执行 10 对 A/A、20 组 ABBA/BAAB，相同/变化的 1/2/8 读取者、混合结果读取、迟到及回退。保留进程集成的混合结果改善至少 20%、单独结果回退至多 5%、监控/总 CPU 回退至多 10%，且拒绝/超时率不恶化。报告全部尝试及等量完成工作。获批集成候选之后进行真实 owner/浏览器验证，每个变体 100 次尝试，不足 100 次成功不声称 p95。

## VLS09. 来源与分析限制

Python 文档说明了增量[哈希更新](https://docs.python.org/3.14/library/hashlib.html#hashlib.hash.update)、[JSON 编码片段](https://docs.python.org/3.14/library/json.html#json.JSONEncoder.iterencode)及 [Python 分配跟踪范围](https://docs.python.org/3.14/library/tracemalloc.html)。Pydantic 的 [model_validate_json](https://pydantic.dev/docs/validation/latest/api/pydantic/base_model/#pydantic.BaseModel.model_validate_json) 支持字节输入，[先解析再校验流程](https://pydantic.dev/docs/validation/latest/concepts/performance/)说明额外中间字典的成本。这些文档仅说明 API，不证明应用等价性或内存边界。

测量运行时为 Python 3.14.7、Pydantic 2.13.4、SQLite 3.50.4 和 SQLAlchemy 2.0.52。本轮只新增方案文档和脱敏分析证据，没有重启服务、修改运行/测试代码、进行浏览器验收、提交或推送。测量属于 3 轮诊断和边界探针，不能证明此前真实页面尾延迟已经修复。精确原生竞争归因、可强制执行的内存边界及组合后的生命周期正确性仍待完成。
