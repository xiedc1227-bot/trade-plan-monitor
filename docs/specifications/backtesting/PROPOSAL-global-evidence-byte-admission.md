It follows the [bounded transport verification](../../verification/bounded-validation-transport-2026-10-22.md). ## GBA01. Findings and scope

Recommend an isolated P0 experiment for snapshot-local size discovery, admission before payload SQL execution, and one application-owned byte ledger. Keep process integration conditional. No production code, service, live database or existing validation has changed in this analysis.

The current 64 MiB counter in `IndexEvidenceFlights._lead_owned` charges a candidate after the SQL driver fetched it and `RawIndexCandidate.from_values` encoded its JSON text. `yield_per=128` limits row count, not bytes. `_compare` keeps a borrowed flight alive while independently scanning another transaction; its SQL buffers, decoded text and encoding overlap are outside that counter. The full thread fallback also uses the same unbudgeted scanner. Thus the existing counter bounds retained sharing input, not all concurrent evidence allocations.

The previous frozen fixture has 30,826,621 bytes of retained raw input. Adding the 16,777,216-byte transport reserve and 7 conservative follower SQL batches of 7,454,438 bytes gives 99,784,903 bytes (95.16 MiB), exceeding 67,108,864 bytes (64 MiB). This is an arithmetic envelope, not an observed simultaneous peak. It omits additional conversion/native costs and cannot certify production safety.

The ledger must be owned by application composition and injected into all relevant readers, including stopped-health diagnostics, thread fallback and overlapping draining generations. `get_health` currently constructs a separate `RuntimeStatusReadService`; a ledger per service would multiply the allowance. “Global” here means all admitted index-evidence input work in this application process, including child transport leases. Result projection models, other application work and interpreter/native baseline still require a separate aggregate process-memory gate. Multiple server processes would require an explicit cross-process or partitioned budget before this claim can extend to them.

## GBA02. Discover size without fetching payload

In each request's existing explicit read transaction, scan a bounded metadata page containing integer row locators, missing-payload markers, storage types and byte lengths for every selected head/payload scalar. Do not fetch large ordering keys or JSON merely to measure them. The metadata page and driver lookahead also need a reservation before their query starts. Preserve the current filters, outer join and complete ordering; a missing payload remains a candidate for rejection.

Use `typeof` and `octet_length` on original columns, with an explicitly checked database encoding and runtime capability. Do not use text `length`, casts or JSON rewriting to establish the bound. Text length stops at embedded NUL and counts code points rather than bytes. SQLite documents that byte length of text/blob columns can use record metadata without reading the entire value: [scalar functions](https://www.sqlite.org/lang_corefunc.html#octet_length). The local probe on SQLite 3.50.4 / SQLAlchemy 2.0.52 / UTF-8 returned 7 bytes versus text length 1 for the embedded-NUL example. It found 2008 candidates, maximum JSON length 35,587 bytes and total JSON length 27,588,993 bytes. The plan used the head ordering index and payload hash index without a reported temporary sort. These are capability/geometry observations, not allocation or latency results.

Metadata and subsequent payload reads must use the same connection and transaction; never preflight on a separate connection or reopen a transaction after waiting. Existing explicit transaction ownership provides the required snapshot boundary; WAL readers retain their original snapshot: [SQLite isolation](https://www.sqlite.org/isolation.html). Each follower keeps its own snapshot. Row locators are temporary identifiers within that snapshot, not evidence identity or a new trust source.

For the leader, first sum conservative retained-input bounds using a bounded metadata scan; retain totals, not a whole metadata manifest. Atomically admit the required raw storage and progress workspace before materializing the collection. A second bounded metadata pass can construct payload groups. For followers, plan only the next comparison group. Start with 32 metadata rows and a proposed 1 MiB payload-work envelope per active read; both are experiment settings, not established safe limits. Size-based grouping may return fewer rows. If row-location/order equivalence cannot be established for malformed input, fail closed without skipping that evidence or changing the ordered proof.

The payload query itself must select only the admitted locators and a bounded number of rows. Admission happens before `execute`, not merely before `fetchmany`: driver startup, lookahead, result wrappers and conversion can allocate early. Preserve every scalar's actual type, original JSON representation and missing-payload state, then call the unchanged validator or literal comparator. After-fetch accounting is only a detector of an invalid bound; it cannot make an oversized allocation safe retroactively. Check the installed driver path and query plan rather than assuming an ORM setting proves this boundary. [SQLAlchemy buffering](https://docs.sqlalchemy.org/en/20/core/connections.html#streaming-with-a-fixed-buffer-via-yield-per) specifies row counts, not byte reservations.

## GBA03. Lease and accounting contract

Proposed total: `R + T + sum(W_i) + M <= B`. `B` remains 64 MiB. `R` covers all retained raw collections, collection vectors and still-borrowed old flights. `T` covers transport ownership, provisionally the existing 16 MiB envelope. `W_i` covers SQL scalar objects, row wrappers, text-to-bytes conversion, comparison carry-over and scan workspace. `M` covers bounded metadata, locators, ledger/control objects and their overlap. Each allocation belongs to exactly one owning lease; sharing references does not duplicate payload ownership, but extra containers are charged. Allocations beyond these categories must be identified, bounded or explicitly block the gate.

Using the previous measured raw size only as an illustration, reserving 8 work slots of 1 MiB and 1 MiB for metadata/control alongside transport gives 57,041,021 bytes (54.40 MiB). This is a proposed partition, not a proven bound: the new raw upper bound may exceed measured retention, and larger rows may need larger work reservations. Never infer that all existing rows or 8 actual readers already fit. Do not raise the 64 MiB limit or lower the existing 8-reader admission limit to pass the experiment.

Compute type-aware bounds before allocation. Include worst-case Python Unicode storage, exact UTF-8 byte copies, tuple/list capacity, coexistence of the current and next candidate, and driver/native staging. Declared string widths and normal observed JSON sizes cannot certify corrupt stored values. Metadata must inspect all selected columns, not only JSON. SQLite conversion, sorting, page caches, parser models and OS buffers need separate runtime investigation and synchronized process-memory measurement; a Python ledger alone is not an RSS cap.

Use explicit lease ownership transfer from query work to retained raw input. Do not refund an entire batch while its last row, generator local, result object, traceback or comparison still holds it. An exception must not leave private payloads in retained error tracebacks. The rule is allocation first requires a lease; release requires actual reference/resource cleanup, not just a cancelled observer.

## GBA04. Progress, mismatches and fallback

Reserve a non-borrowable progress workspace before a physical validator starts. Its later input feeding and drain must not depend on bytes consumed by followers. Allocate the initial raw/progress reservation atomically; do not grow an unbounded retained prefix while waiting for more memory. Waiting readers hold only their bounded metadata/session state, with the current deadline continuing to run. Do not wait on bytes while holding the flight condition or database/transport cleanup locks.

The current leader waits for collecting followers and borrowed comparisons before validation. A naive byte semaphore can deadlock this path: followers wait for bytes while the leader waits for followers. A follower may pin a flight for comparison only after it owns an eligible comparison workspace, using an atomic coordinator decision or a recheck-and-release protocol. Waiting requests cannot count as comparisons that must finish before validation. Give admitted comparisons a route to completion, keep the existing completion fence, and never keep a completed proof open just to improve sharing statistics. Measure join loss and repeated validation caused by byte waits.

On mismatch, close the comparison cursor, drop transient rows and release the borrowed flight before waiting for the existing single queued-owner slot. Re-scan completely in the same request transaction when admitted; never splice different snapshots, validate only the mismatching suffix or adopt the leader's evidence. Count old retained flights until all borrowers have physically finished. Keep 1 physical validator and 1 queued owner; byte admission schedules memory work, not a hidden increase in concurrency.

Unsupported transport or an input collection too large to retain may select full thread streaming before child submission, but that scanner must also acquire byte leases. An unbudgeted fallback would defeat the global guarantee. No post-submission fallback or duplicate validation. An oversized row must not be truncated or silently omitted. Near the existing 16 MiB write limit, conservative decoded-text/copy bounds may already exceed the entire allowance. This is a feasibility blocker requiring measurement and possibly a separate capture/validation design; it cannot be hidden by new resource rejections for previously valid inputs. Arbitrarily large corrupt input may fail closed, but valid-input coverage and protected rejection rates are explicit acceptance gates.

## GBA05. Authority, time and cancellation invariants

Keep every request's independent authority-before/after checks, activation reread, original transaction, observation clock and existing 2-attempt logic. Sharing applies only after full ordered literal equality of independently read evidence; size, row locator, hash or metadata equality never replaces that comparison or full historical canonical/domain validation. No completed-result cache.

Budget waits must not reset the 15-second waiting deadline or extend target/90-second validity. Recheck cancellation and admission before metadata queries, payload queries and every new reservation. Successful responses still pass the existing time/authority checks. Deterministic tests must establish behavior when waits cross activation, publication, retention and clock boundaries; do not invent a refreshed clock inside an already assembled snapshot.

Cancellation before payload admission removes only the waiter and unused reservation. Cancellation during SQL/conversion cannot refund bytes until the owned work has closed the cursor and released references. Submitted child proofs continue to outcome and `DRAINED`, or supervised exit and bridge cleanup. A follower cancellation cannot revoke the leader's proof. Stop/storage pause first fences new leases and wakes waiters, then drains owned readers, comparisons, transport and byte leases. Cleanup failure retains the relevant lease and storage fence; a new generation must not allocate against a reset counter. Add no cache of authority and no shortened drain.

## GBA06. Next implementation and decision gates

First restore bilingual specification/task parity for this new contract, then implement only an isolated P0 prototype:

1. Audit the complete allocation sequence, metadata capability, bounded payload query and native lookahead on the installed runtime. Record a formal ledger scope and the absolute parent-plus-child memory budget before acceptance sampling; leaving the latter unspecified keeps production integration blocked.
2. Build the shared ledger, preflight scanner and progress-safe comparison admission with the original thread validator. Test atomic reservations and transfer/release before introducing process transport. Include the stopped-health composition path and generation overlap in the ownership design.
3. Test exact bounds and over-bound allocation attempts, concurrent same/changed inputs, large and malformed old rows, every historical integrity check, independent authority, time boundaries, repeated cancellation and cleanup failure. Kill mutations that admit after query execution, omit follower bytes, reuse a completed proof, skip literal comparison, bypass authority or release before physical cleanup.
4. Compare the original thread path, budgeted thread path and budgeted chunk-process experiment separately. Predeclare 1/2/8-reader same-snapshot and changed-snapshot workloads, plus result-page overlap, late arrivals, mismatches and oversized fallback. Use 10 A/A pairs and 20 alternating ABBA/BAAB blocks per pairwise workload; keep all failures, timeouts, fallbacks and cancellations. Do not replace failed samples. Use separate repeated memory/allocation runs and synchronized parent/child observations.
5. Publish bilingual findings and a P1 decision. Measure metadata/payload SQL count and time, admission wait, comparison duration, join rate, repeated full proofs, lease high water by category, actual allocation high water, transaction duration, WAL/checkpoint pressure, total CPU and full request completion. Do not subtract admission waits from latency or mistake a lower success rate for an improvement.

Hard gates: no admitted allocation outside its lease, no aggregate breach of 64 MiB, complete output/integrity equivalence, independent authority, safe physical drain, no deadlock/starvation within the existing bounds, no new rejection of the valid-input fixtures, and no worse protected rejection/timeout rate. Require at least 20% mixed result median improvement for the process variant, no more than 5% isolated-result regression, and no more than 10% monitor median or total CPU regression. The pure budgeted thread variant must meet memory/correctness gates and the same regression ceilings; it need not claim a process speedup.

P1 is conditional on all gates, including native/absolute process-memory bounds. Only then propose a default-disabled production integration and real-owner/browser validation with 100 attempts per variant; require at least 100 successful observations per variant before a p95 claim, retain every failure in the denominator, and preserve the existing 20% real mixed p95 target. A failed size, correctness, lifecycle or availability gate keeps the current production path and triggers another design review.

## GBA07. Alternatives and analysis limits

Smaller `yield_per` is an experimental control, not a byte guarantee. A semaphore acquired after fetch is too late. Reading all evidence to estimate its size repeats the original problem. Comparing hashes or metadata alone weakens exact sharing; serializing all requests hides concurrency costs. Raising the limit or unbudgeted thread fallback invalidates the requirement. JSON-to-BLOB capture or incremental validation might reduce large-row copies but changes a separate representation/core boundary and is deferred.

This analysis adds only this paired proposal and sanitized metadata evidence. It has not measured a global-admission prototype, run new concurrency/browser acceptance or proved the proposed partition. Production and parallel AI extraction/daily-inventory work are untouched; no commit or push is part of this analysis request.
