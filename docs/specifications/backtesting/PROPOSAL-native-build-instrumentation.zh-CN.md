# 可复现原生资格验证与失败回收 CPU

## BIR01. 决策与范围

继续 P0，交付两个具体成果：具备分配覆盖的、已准备好工具且可复现的 Windows 资格目标，以及在证明安全的分支避免不必要全量回收的同生命周期失败释放实验。之后才改变大行准入。P1 维持 NO-GO。

本分析承接 `5cb920b` 与[已提交报告](../../verification/native-build-error-budget-p0-2026-10-23.zh-CN.md)。仅新增双语方案和[脱敏证据](../../verification/evidence/2026-10-23-native-build-instrumentation-next/analysis.json)。生产/实验实现、已有证据、README 及并行 AI 提取/日库存工作均保留。不安装工具链、不替换依赖、不提交、不推送。实施前补齐双语规格与任务。

## BIR02. 修正 PGO 标志的解释

对应发布的 [build.rs](https://github.com/pydantic/pydantic/blob/cf67d4b3193c3fe43ede18612ed62785eee11382/pydantic-core/build.rs)读取 `RUSTFLAGS`，查找 `-Cprofile-use=` 来设置 PGO 报告标志。然而 Cargo 文档明确：Rust `1.55` 起，构建脚本接收 `CARGO_ENCODED_RUSTFLAGS`，而 `RUSTFLAGS` 被移除。见 [Cargo 构建脚本环境契约](https://doc.rust-lang.org/cargo/reference/environment-variables.html)。

因此，`profile=release pgo=false` 不能证明本机 wheel 未使用 PGO。按已公开的 Cargo 环境规则，该报告代码存在具体的假阴性路径。这是源码/文档推断，不是重建 wheel 实验；历史实际参数与剖析输入仍未知。不能继续把标志与工作流的差异当成未解释的二进制不匹配或性能原因。工具准备后先用最小构建脚本探针验证报告机制，记录实际编译器命令和编码参数，而不是信任此字符串。

此前 wheel/归档摘要仍证明二进制身份和源码身份。历史作业日志/产物恢复尚未完成。逐字节重现历史官方 wheel，与构建新的可复现、可审计资格二进制，是两个不同目标。不能让缺失历史日志阻止全部实验，也不能以新构建认证旧 wheel。

## BIR03. 具体构建路线

优先使用独立 Windows x64 构建环境。当前 Python 为 `3.14.7`、带 GIL 的发布构建，编译器标识为 `MSC v.1944`；已安装 core 为 `2.46.4`。当前 Docker 上下文是 `desktop-linux`：可支持 Linux 探索，但不能认证 Windows 分配器/CRT 行为。本次没有启动 Docker 服务或容器。

| 路线 | 用途 | 决策 |
|---|---|---|
| 本机 Windows Build Tools、Rust 和隔离 Python 环境 | 在目标 ABI 上重复构建与插桩测试 | 可以准备工具时首选 |
| 锁定镜像与工具的独立 Windows VM/runner | 本机不适合安装时保持相同目标 | 可行替代；记录实际镜像/工具版本，不能只写浮动 runner 标签 |
| 现有 Linux 容器 | 解析器源码探索与早期钩子测试 | 仅作补充，不能闭合 Windows 门槛 |

使用 Microsoft 独立 C++ Build Tools 和 Windows SDK，不要求完整 IDE。通过受支持的开发环境脚本发现工具集并记录精确版本。`14.44` 工具集系列与观察到的解释器编译器相符，但不代表原 core 编译器。构建前锁定实际补丁和 SDK，不能使用浮动默认值。见 [Microsoft 构建环境说明](https://learn.microsoft.com/en-us/cpp/build/building-on-the-command-line?view=msvc-170)。

建议隔离布局：`tools/native-qualification/` 存放构建/探针配方与清单；下载归档、vendor 缓存、wheel 和临时环境放在 `.pytest_cache/native-qualification/`。服务环境不得导入这些 wheel。预检输出安装器位置、磁盘需求、目标 ABI、实际工具版本及缺失项。缺少编译器必须导向具体环境准备结果或明确的构建未执行，不能伪造通过。

构建顺序：

1. 锁定已核对的发布归档、`Cargo.lock`、依赖校验和/特性与 `maturin 1.13.1`，将锁定依赖获取到独立缓存。选择并锁定满足源码最低要求的明确 Rust 版本；记录 `rustc -Vv`、Cargo、MSVC、链接器、SDK、CRT、Python DLL/导入库身份、环境及源码补丁摘要。新选编译器不能被称为历史编译器。
2. 在独立 Python 环境构建未改动的发布目标 R，使用 `maturin build --release --locked --offline --target x86_64-pc-windows-msvc --interpreter PATH`。明确声明 PGO 策略。先建立非 PGO 资格目标；若后续引入 PGO，需锁定训练语料与剖析摘要并重新认证。记录完整实际编译/链接命令。[Maturin 说明了 locked/offline 构建选项](https://www.maturin.rs/distribution.html)。
3. 在第二个全新构建目录重复 R。比对 wheel 成员和原生二进制摘要；分别调查路径、时间戳、签名与编译器不确定性。功能一致不等于字节可复现，未解释差异不能通过该声明。官方原 wheel 保留为行为参考，不要求其摘要与新构建相等。
4. 在相同工具链/配置下，以小型、经过审查的分配观测补丁构建 I。记录精确 R/I 补丁。解释分配结果前先证明合法完整输出、规范字节和失败类别等价。插桩会改变分配/性能行为，必须核算差异，不能把 I 当生产候选测速。

任何缩减后的准入预算都必须绑定精确的获资格运行时清单，包括未插桩二进制与依赖身份。若 R 成为部署候选，还需相对当前已安装 wheel 单独验证真实服务行为与 CPU；本方案不授权替换该 wheel。运行时不同或尚未验证时，继续使用保守准入。若未核算观测补丁对分配行为的影响，仅凭 I 测量不能为 R 或已安装 wheel 降低预留。

## BIR04. 分配器插桩需要三个领域

| 领域 | 入口与初始化 | 覆盖限制 |
|---|---|---|
| Rust core/解析器依赖 | 构建时使用 `GlobalAlloc` 包装选定底层分配器，覆盖分配、清零分配、重分配与释放 | 不自动覆盖 Python、SQLite、直接 `System` 调用或全部 CRT 分配 |
| Python 对象/writer/驱动对象 | 在隔离启动器中安装 RAW/MEM/OBJ 原生包装，并观测 arena | 嵌套转发不能累加为多份物理内存；arena 保留不同于活对象 |
| SQLite 查询/cast/缓存 | 初始化前，通过 `SQLITE_CONFIG_GETMALLOC` / `SQLITE_CONFIG_MALLOC` 包装实际加载的库 | 钩住不同 SQLite DLL 无法证明本库；不能重配运行中的服务 |

使用固定容量原生事件缓冲和预分配指针/所有者表，单独计入其内存。记录请求/可用字节（接口可得时）、活跃/高水位字节、分配次数、阶段、物理所有者及排空时未释放分配。跨线程转移和阶段变化仍保留所有者身份；仅线程局部阶段不足以解释后续释放。防止溢出、递归分配和事件丢失：任何核算遗漏均使本轮无效。钩子内禁止 Python 回调、格式化、日志及会分配的锁。[Rust 分配器契约](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html)明确约束展开和重入。

重分配前预留旧/新可能重叠量，再调用底层分配器；失败时保留旧所有权，成功后才转移。只记净增量不能界定底层临时复制。分别记录逻辑领域总量与去重的底层物理分配；不能把 Python arena 容量、对象请求和 OS 堆字节当成不同副本相加。进程包络应包含元数据取整、保留 arena、碎片与观测器开销。

版本对应的 [CPython 内存 API](https://github.com/python/cpython/blob/v3.14.7/Doc/c-api/memory.rst)要求线程安全包装，并在初始化后包装既有分配器。`PyTraceMalloc_Track` 只是可选诊断导出，不是预算门禁；不能在钩子内部递归调用会分配的跟踪 API。SQLite 的[配置](https://www.sqlite.org/c3ref/config.html)和[内存方法接口](https://www.sqlite.org/c3ref/mem_methods.html)要求关注初始化时机。当前 SQLite 为 `3.50.4`，使用 `SYSTEM_MALLOC`；记录实际 DLL 摘要、源码 ID 和选项，先通过已知查询分配确认覆盖，再运行证明基准。

先验证各领域分配次数/字节探针、重分配增长/失败、跨线程释放与事件溢出，再覆盖长 Decimal、密集模型、密集错误和畸形 JSON。原生失败注入必须放在受监督的一次性子进程：Rust 分配失败可能终止进程，而不是变成 Python `MemoryError`。不能在服务中注入、依赖 Python 捕获兜底，或穿过分配回调展开。异常退出子进程不能产出证明；父进程保留所有权，直到退出、传输关闭和实际排空，清理失败仍保留债务隔离。正常观察者取消仍不能杀死同步物理工作。

观测高水位本身不是所有输入上界。需要结合源码推导的形状边界、最大并发所有者、分配器增长契约、插桩覆盖和进程总量。CRT/arena/驱动覆盖缺失时保留保守预留。运行时分配失败门禁不能替代分配前准入，也不保证合法输入可用。

## BIR05. 新的失败 CPU 与持有证据

此前跟踪基准将候选全量回收计入调用，却把基线错误保留到调用之后，释放终点并不一致。新探针对每次调用启动新进程，仅在该进程关闭自动 GC，CPU 测量不启用跟踪，并对两个版本都计时校验、引用释放与全量回收。每组 `3` 轮交替，共 `18` 次调用。所有记录的全量回收均返回 `0` 个回收对象。

| 非法夹具 | 融合总 CPU 秒 | 边界总 CPU 秒 | 边界全量回收 CPU 秒 |
|---|---:|---:|---:|
| 长 Decimal | 0.250000 | 0.250000 | 0.078125 |
| 密集 | 0.578125 | 0.562500 | 0.093750 |
| 密集，额外保留 100000 组字典/list | 0.562500 | 0.562500 | 0.109375 |

这些是 CPU 分辨率较粗的诊断中位数，不是验收或精确提速证据。额外对象在计时前分配并晋代，小差异不能证明增长曲线。与旧数据不同，这次总量包括两边的物理释放。不能与启用跟踪的运行直接比较绝对时间。

另一次跟踪检查调用既有失败捕获，但不执行包装器的全量回收：

| 非法夹具 | 全量 GC 前 live 字节 | 全量 GC 后 live 字节 | 构造峰值字节 |
|---|---:|---:|---:|
| 长 Decimal | 54680 | 18104 | 25113000 |
| 密集 | 147072 | 25488 | 156796064 |

两次回收仍报告 `0`。这些夹具的大部分失败对象图已随作用域退出/引用计数释放；剩余跟踪字节变化可能包括空闲链表清理和记账，并非回收循环。[精确 Python GC 文档](https://github.com/python/cpython/blob/v3.14.7/Doc/library/gc.rst)区分了循环回收和空闲链表清理。预建输入不计入，不能据此认证原生内存上限。

合成测试主动创建 `payload.cycle = payload`。它证明既有通用循环清理行为，不能证明每次持久化 JSON 错误都产生循环或需要进程级回收。应将该对抗用例保留为排空/所有权要求，不能为了让优化分支通过而删除。

## BIR06. 建议的失败释放优化

首先实验：保留既有有界失败作用域，对经模式资格证明的普通失败分支不再无条件做全量 GC。通过精确模型/源码所有权分析、可用时的弱引用、阶段计数和分配台账排空证明释放。覆盖字段/模型错误、模型构造后的域/字面值失败、合法非法项混合、末尾错误、嵌套异常以及自动 GC 开启时的重复调用。当前两个夹具只支持假设，不足以完成资格证明。

异常保持本地、描述不可变，每个观察者获得新的本地异常。若失败路径可能保留循环或所有权未证明，继续保留债务并走明确的物理清理路径。比较每个物理失败证明最多一次串行回收，与已完成 worker 架构资格时的独立 worker 完整排空。两者都不能提前退款，或借观察者完成隐藏待清理对象。计入无关堆暂停与回收协调器自身内存，等待其他清理所有者时不得占用扫描许可。

不能全局关闭/冻结 GC、调整阈值、把所有全量回收换成第 `0/1` 代，或通过 `gc.is_tracked` 推断无环。生产对象可能已经历晋代。如果无法安全区分已知失败类别，保持当前实验的保守行为，生产仍不启用。禁止解析器快速失败、截断错误遍历、放松模型规则或省略哈希。

## BIR07. 资格通过后的大行准入

当前失败仍发生在载荷前：对 `67108864 B` 上限请求 `197697036 B` 和 `145472808 B`。不是测得 OOM。假设去掉显式整段解码文本，当前编码目标下长 Decimal 完整推进预算仍为 `69195268 B`，继续超限。下一步必须证明分配确实消失以及所有者重叠关系，不能只扣系数。

根据获资格的 R/I 证据建立阶段/所有者预算：元数据、SQL step/cast/驱动、不可变原始别名、前后代、解析/模型/错误峰值、规范化/编码临时区、选中结果、跟随者比对和物理清理。保持原输入类别与进程聚合限制，不能重分类制造通过。只有身份和生命周期均已证明才将不可变别名计一次。模型/错误即使不属于输入副本，也继续计入聚合包络。

载荷前原子预留完整推进预算包。解析/编码/清理使用已获预算的子租约，禁止部分原始租约加阻塞编码升级。先保障唯一物理证明所有者，再准入可容纳的跟随者比对工作区。各跟随者独立读取并将全部原始证据与仍在运行的证明精确比较。按字节调度可以降低实体化并发，不能减少权威检查或八读取者契约。保留小行 `1` 证明加 `7` 加入、公平性、原截止/次数及查询次数。完整校验流式回退必须先证明单行可容纳，否则合法大行可用性仍为失败。

## BIR08. 阶段与不变门槛

| 阶段 | 必须交付 | 停止条件 |
|---|---|---|
| P0-A | 双语规格/任务；实际准备的 Windows 工具链；编译器命令探针；两次干净 R 构建和 I 清单 | 缺工具、可复现差异未解释或目标身份不清 |
| P0-B | 三领域覆盖探针、源码所有权包络与受监督的分配失败测试 | 丢事件、分配器重叠未知、提前退款或遥测无界 |
| P0-C | 同生命周期 CPU/持有对比；经资格证明而免去不必要全量 GC 的失败分支 | 循环或调用者对象释放脱离债务核算、失败语义改变 |
| P0-D | 完整预付的合法大行 SQL 路径及并发实验 | 大行超限、死锁、拒绝/超时恶化或完整性/权威检查遗漏 |
| P1 | 条件式集成与真实所有者/浏览器验收 | 任一前置门槛未闭合 |

每个请求保留独立前后权威检查及激活重读；全部历史、`19` 个原始字段/类型、缺失依赖、严格模型、规范 UTF-8/EOF、bar/request/root/formula 和逐 fact 校验不变。不使用完成证明缓存或信任存储哈希。取消仅脱离观察者或阻止未开始工作；物理工作、保留结果和传输均有所有者直到实际释放。清理失败保留债务并隔离后续代。

保持 `64 MiB` 输入、`768 MiB` 聚合工作集、`2560 MiB` 私有提交、`1` 个物理证明、`1` 个排队所有者、`15-second` 等待、`90-second` 资格和 `2` 次尝试。测试 `1/2/8` 个读取者、时间边界两侧、末尾/重算哈希篡改、领导者/跟随者取消、最后观察者离开、存储失败与大小行推进。未过门槛允许 `3` 轮标注诊断；获资格候选执行 `10` 对 A/A、`20` 个 ABBA/BAAB 区块、`20%` 混合进程收益、结果与监控/总 CPU 回退不超过 `5%` 和 `10%`，拒绝/超时不恶化。浏览器每版本 `100` 次尝试，达到 `100` 次成功才可声称 p95，保持原 `20%` 混合 p95 目标。

证据嵌入两份临时探针及每次结果。CPU/持有输入指纹与所检源码指纹标识本次分析。没有改变应用代码或测试策略，也没有声称完成新原生构建、分配器拦截、更低预算准入或浏览器验收。
