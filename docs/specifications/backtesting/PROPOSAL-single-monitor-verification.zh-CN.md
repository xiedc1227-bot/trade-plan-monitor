# 单次监控证据校验优化方案

状态：仅分析，2026-10-21。基线：`ba4156e`。[英文规范版](PROPOSAL-single-monitor-verification.md)。[原始观测](../../verification/evidence/2026-10-21-single-monitor-analysis/measurements.json)。现有[共享契约](SPEC-monitor-evidence-sharing.zh-CN.md)继续生效；本方案不授权生产实现、已完成证明缓存或服务重启。

## SMR01. 结论与测量范围

不重叠请求正确地无法命中在途共享，仍重新校验全部历史候选。主要开销来自单条校验内部反复导出模型、规范化和编码，而非 SQL 查询次数。应先消除同一份完整校验快照的重复表示，保留完整历史遍历。

Windows / Python 3.14，沿用此前冻结只读监控副本：2,008 个候选、72,280 根内嵌 bar、27,588,993 字节原始 JSON UTF-8。该样本没有活动计划、事实请求或指标事实。SQLite 使用显式事务、`mode=ro`、`query_only=ON` 和有界池。固定时钟与合成 owner 缺席权威用于隔离历史指数成本，不能证明实际运行时权威。每次连续调用均拥有全新的读取，前一次完成后才开始下一次，没有在途加入或已完成缓存命中。

十轮交替、不插桩对照，完整 dashboard 相等，每次请求在所属循环调用权威提供方两次：

| 完整单次读取 | 当前实现 | 进程内单次规范树实验 |
|---|---:|---:|
| 墙钟中位数，秒 | 3.4802 | 1.9768 |
| 进程 CPU 中位数，秒 | 3.4219 | 1.9688 |
| 墙钟范围，秒 | 3.4237–3.5353 | 1.9559–2.0391 |
| 每次物理候选校验数 | 2,008 | 2,008 |
| 每次权威调用数 | 2 | 2 |

探索性墙钟改善 43.2%，CPU 改善 42.5%。这是可行性结果，不是已部署耗时或生产验收。全部 2,008 个存储候选的完整行结果也相等。保留原始输入峰值仍为 30,826,621 字节，排空后归零。这是现有共享输入计量，不代表新增瞬时规范树或整个进程的内存测量。

补充纯行夹具包含 8 根 bar、4 个请求、4 个指标事实，覆盖 SMA、SMA_LOOKBACK、RETURN。每轮完整校验 500 次、交替五轮，墙钟中位数 0.2769 → 0.1667 秒。两种实现均接受请求与事实一起重排且正确重算哈希的快照，也均拒绝错误的事实公式、请求哈希、Decimal 写法、JSON 数字与时间戳写法。不能将主要冻结样本描述成事实密集或活动计划工作负载覆盖。

## SMR02. 单次读取耗时分布

一次分段插桩与上面的无插桩基准分开。指数路径墙钟 3.5329 秒，行校验 3.3770 秒，约占 95.6%。以下阶段相互独立，不再与包含它们的父调用耗时相加：

| 校验阶段 | 墙钟秒数 |
|---|---:|
| 类型化 JSON 解析与模型校验器 | 0.6346 |
| bar 集合规范化/编码/哈希 | 0.9344 |
| 快照规范化/编码/哈希 | 0.8213 |
| 最终规范 JSON 原始字节相等检查 | 0.8573 |

上述三个规范化/哈希阶段约占完整指数路径的 74.0%，其中包含模型导出、规范化与编码，不能全算作 SHA-256。排名、元数据、输入捕获及 SQL 占剩余部分；改变赢家查询不能消除证据校验要求。

直接扫描、捕获并计量全部 2,008 个 SQL 原始候选，三次补充观测墙钟为 0.2112 / 0.0682 / 0.0640 秒，不宣称冷缓存测试。查询计划已经按 mapping/index 搜索 head 主键索引，按 snapshot hash 搜索 payload 主键索引，使用一次左连接。该路径没有测到 N+1 查询或新增索引的依据。

单独的工作线程 cProfile 定位到 8,032 次 `canonical_json`、3,701,644 次递归 `canonical_value`、1,328,368 次 `canonical_decimal`。插桩改变成本，使组装耗时达到 10.4385 秒，不能把它当普通请求延迟，也不能叠加嵌套累计耗时。参见 [Python 性能分析文档](https://docs.python.org/3.14/library/profile.html)。Windows 单次线程 CPU 计量较粗，极短阶段可能量化为零，因此分开记录分段墙钟与未插桩进程 CPU。

纯校验器前缀实验中，128 个候选的当前/原型墙钟为 0.1325 / 0.0729 秒，512 个为 1.0773 / 0.5913 秒，2,008 个为 3.3768 / 1.8681 秒。前缀载荷分布不同，这些只是组件观测，不能作为合法缩短的监控读取，也不能仅按候选数预测增长。成本仍取决于证据总字节和内嵌 bar 数。

## SMR03. P0：每条完整校验快照只构建一次规范表示

保留类型化 JSON 解析与全部模型校验器。沿用现有 Python 模式导出和规范化规则，构建一份规范原始值树。仅在当前行校验内复用它，派生有序 bar 集合哈希、排序请求集合哈希、只排除根快照哈希字段的快照哈希，以及用于原始存储相等检查的完整规范文本。

保留精确 tuple/type 边界、类型化排序、domain 前缀、公式定义与事实公式检查、行元数据/provider 绑定、缺失 payload 拒绝、head 身份及已验证排名。bar 排序沿用类型化时间戳/周期，请求排序必须与当前规范排序键完全一致。哈希相同不能代替规范字节相同。处理完当前行就释放规范树，不能为全部 2,008 个候选再保留一整份规范表示。

使用同一个内部校验实现向仓储读取返回已验证的规范文本。保留现有公开哈希 helper，以及 `validate_market_index_snapshot_integrity` 的接口和原有返回行为，避免维护两套独立完整性算法。原型只在被忽略的可行性脚本内重复逻辑，不能原样复制为生产并行校验器。

未经字节等价证明，不用 `model_dump_json()` 或通用 JSON 模式替代项目编解码。Decimal 规范化、微秒时间戳写法、Unicode、enum/子类行为和 float 拒绝均属于证据格式。Pydantic 文档说明 Python 模式递归导出和不同序列化模式，这支持复用表示，不代表可以更改项目规范策略。参见 [Pydantic 序列化](https://docs.pydantic.dev/latest/concepts/serialization/)。不重提此前已回退的原始类型快速分支实验。

独立读取保持不变：自身观测时间与 BEGIN 快照，计划/库存/风险/日历/完成证明检查，包括 progress 状态的权威前后检查，激活身份重读和最多两次尝试。保留每个 socket 的游标、重放和周期；取消所有权、原等待期限、关闭/存储排空及当前准入/字节上限均不变。仍校验未选中的全部历史。不需要改变财务计算、API、schema、保留规则、超时或线程池。

## SMR04. 条件性 P1 与备选方向

先对正式 P0 重新剖析，再决定 P1。如果仍由重复规范化主导，可实验仅在一次物理校验内，用明确小上限复用重复不可变 bar/Decimal 的规范表示。每份快照仍须通过类型解析、全部 domain 哈希、元数据绑定与规范原始字节比较。测量键构建成本、相等语义和内存峰值，物理完成即丢弃。目前不承诺该项收益。

如果类型校验成为主要开销，保留 `model_validate_json()` 与完整校验链，再寻找测得的重复工作。不能换成未验证 dict 或 `model_construct()`。其他序列化库、编译校验器或进程隔离需要独立等价/生命周期评估；只增加 worker 不能降低单次读取 CPU。

本轮不引入已完成证明缓存。在全新快照中精确比较原始字节，再复用有界的已完成纯证明，理论上与缓存权威不同，但它会改变已经接受的“不复用已完成结果”契约，还需新增内存、语义版本与生命周期边界。仅依靠摘要、事件序号、mtime 或 SQLite data-version 的缓存不够。物化最新行、LIMIT 或只在写入时校验会漏掉当前契约要求发现的未选中历史损坏。也不能通过缩短保留时间改善计时。SQLite WAL 快照属于各自读取事务，不能证明后续事务未变化；参见 [SQLite 隔离](https://sqlite.org/isolation.html)。

P0 降低全量校验的常数开销，不改变增长阶数。若之后全历史工作超过预算，应单独提交证据存储/可信证明设计供审查，不能静默跳过旧记录。

## SMR05. 实际服务观测与前置条件

三次连续的 version-2 实际 dashboard 请求快速返回 HTTPError，随后确认是 503 `SERVICE_UNAVAILABLE`。另一次未带所需监控版本的诊断返回预期的 409 契约不匹配。失败请求不计入成功读取性能。当前生产证据在合成 owner 缺席权威、固定分析时钟下，经独立只读完整组装通过，活动标的为零；这不能证明实际实时权威，也不能解释 503。

实施验收前，应通过有界阶段/错误类别观测，定位实际服务是在准入、存储暂停、权威捕获/progress 覆盖或其他安全拒绝边界返回错误，不记录凭据或证据正文。保留未知权威拒绝，不能将实际服务切换成合成 owner 缺席、屏蔽权威错误或仅为取得更快数字而重启。先理解状态并建立成功的真实基线，再在部署后重复相同路径。本次分析没有重启服务或修改生产源代码。

## SMR06. 实施顺序与建议验收线

1. 补齐双语实施规格/任务与逐项检查等价映射，解决 SMR05 的真实测量前提。
2. 先补规范字节/哈希/错误 golden 和差分用例，再通过同一规范核心实现单次表示校验。
3. 对比全部原候选与输出，覆盖未选中历史损坏、同大小/时间篡改、缺失 payload、domain/hash/formula/provider/head 变化、事实密集/请求重排、Decimal 极值、float/bool/enum/子类边界、时区/微秒/Unicode 写法。现有错误形状与排名须一致。在独立进程内移除完整性门禁的变异必须被测试拒绝。
4. 复跑独立权威/配置/generation/激活、库存/风险/日历/证明、90 秒/目标/日期/时钟、STOPPING/STALLED/不可读 owner、全部观察者取消。保留 8 个读取/1 个校验/1 个排队/64 MiB 上限、完成竞态和预算回退，并验证实际存储清理排空物理读取。
5. 在同一 2,008 候选样本至少交替测量 10 轮、不插桩：建议单次 CPU 与墙钟中位数均改善至少 30%，墙钟中位数不超过 2.5 秒。实验已满足建议目标，正式实现仍须重测。另覆盖活动 CURRENT 计划、非空请求/事实、小历史、更大/接近上限载荷，并以相同载荷分布测增长，不纳入 profiler 开销。
6. 重测 2/8 监控加结果和错峰到达。校验变快可能缩小共享窗口，不能假定原命中率保持。相对当前实现，CPU/墙钟中位数退化均不超过 10%；完成边界触发重新校验时仍正确。以新进程测瞬时分配与进程内存峰值，建议单次读取峰值内存退化不超过 10%，原始输入预算不变。未达线应重新评估，不能弱化校验。
7. 完成相关完整性/保留/运行时回归，以及无业务写入/页面异常的真实浏览器结果/监控/心跳路径，记录双语前后验收。仅在剩余实测瓶颈值得优化时考虑 P1。收到后续请求后才提交/推送。
