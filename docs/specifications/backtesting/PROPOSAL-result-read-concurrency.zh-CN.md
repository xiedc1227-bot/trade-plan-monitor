# 结果读取并发延迟定位与优化方案

状态：仅分析，2026-10-21。基线：`cd5113b`。[English 原本](PROPOSAL-result-read-concurrency.md)。未修改应用代码、运行中服务配置或历史证据。只读实验使用 SQLite `mode=ro` 和 `PRAGMA query_only=ON`；候选替换仅存在于隔离测量进程中。

本文保留历史分析记录。关于应用代码未改变的陈述指当时的分析阶段；授权后的落地与最终测量见[规格](SPEC-result-read-concurrency.zh-CN.md)和[验证报告](../../verification/result-read-concurrency-2026-10-21.zh-CN.md)。

## RRC01. 发现与测量

样本：同一份已完成运行，39 个冻结逐日文件和 2,961 个审计事件。完整 API 响应为 15,559 字节。测量仅代表本地观察，不保证生产延迟；性能分析时间包含工具开销，嵌套耗时不能相加。

| 观察 | 证据 | 含义 |
|---|---|---|
| 单次结果读取仍较重 | 两次 HTTP 读取为 4.789 / 6.127 秒。另一次无分析工具的投影耗时为墙钟 5.263 秒 / CPU 5.219 秒。 | 主要路径是密集计算，响应传输不是主因。 |
| 冻结文件读取存在不成比例的临时分配 | `LoopInputStore._read` 每次 `read` 请求 295,108,609 字节；41 个文件实际合计仅 3,077,749 字节。分析中的缓冲读取耗时为 2.389 秒。 | 约 281 MiB 的单次读取长度，在本机 Windows/Python 环境下造成可避免的分配开销。 |
| 审计投影是结果的另一项主要成本 | 带计时的 `_loop_diagnostics` 为 2.792 秒。整个投影的分析记录 15,295 次规范 JSON 调用，递归规范值调用约 2,260,000 次。 | 保留事件校验；先测定分配修复收益，再减少重复的表示转换工作。 |
| 结果 SQL 和响应校验相对很小 | 带计时与性能分析的两次投影，SQL 执行/取行合计 0.0283 秒。路由响应校验 0.0007 秒；JSON 编码 0.0001 秒。 | 新增结果索引或弱化响应校验并未对准主要成本。 |
| 不同结果会排队 | 两组不同运行并发分别约 3.981 / 9.074 秒、3.896 / 8.461 秒完成。 | 已有结果读取器串行执行物理投影。 |
| 监控投影本身也是昂贵读取 | `list_latest_market_index_snapshots` 为返回 5 个当前快照，使用 1,929 次 SELECT 读取 1,928 个历史快照 payload：墙钟 3.728 秒 / CPU 3.672 秒。 | 历史遍历及重复完整性/规范化检查会与结果投影争用资源。 |
| 混合读取相互拖慢 | 结果 + 面板分别为 9.373 / 18.596 秒，随后为 11.741 / 9.307 秒。轻量服务探针仍约 31–200 毫秒。Python 报告 GIL 已开启。 | 测量支持 CPU 争用；不支持普遍事件循环死锁或同一 SQL 写锁是主因的结论。 |

当前监控数据库没有计划版本/活动计划行，因此本样本的原因不是大量计划库扫描。它包含 1,928 个指数 head 和 3,599 个不可变指数快照。性能分析明确指向指数快照校验与规范序列化。

## RRC02. 放大链路与已有保护

- `BacktestResultReadThread` 已隔离昂贵读取、合并相同在途 key，并在观察者取消后等待物理工作排空。最多接受 8 个读取者，排队最多等待 60 秒。简单再加一套相同机制并不是新的优化。
- 两组同运行 HTTP 并发分别约 8.445 秒和 5.202 秒同时完成。0.265 秒取消一次读取观察者后重试，再用 3.679 秒返回相同报告。这些观察符合已有共享行为，但不能据此确定物理调用的准确次数。
- `runtime-status/App.vue` 监听 `route.fullPath`；`monitor.navigation()` 使协议 epoch 失效、取消快照观察者并启动新的面板读取。因此回测筛选/分页/页签变化也会触发与所选结果无关的监控工作。浏览器取消不代表服务端已运行工作停止。
- 真实浏览器的列表 → 结果 → 来源 → 概览流程完成时，只有 1 次结果详情请求，却有 8 次面板请求。其中 7 次面板观察者被取消，最后一次在有界观察结束时仍未完成。结果请求耗时 29.550 秒，几乎全部发生在响应到达前。一次面板观察者达到 20 秒超时并重试。该流程业务写入和页面异常均为零。初始突发期间还有一次服务读取耗时 1.159 秒，上述受控 HTTP 探针范围不能代表通用响应保证。
- `RuntimeStatusReadService.get_health()` 会装配完整监控投影。WebSocket 心跳默认每 20 秒调用这条健康读取路径。authority 变化可能触发最多 2 次投影尝试。多个页签/连接及导航会成倍增加相同的昂贵工作。
- 结果 UI 的 30 秒超时与服务端 60 秒排队上限是不同限制。提高任一期限都不会改善吞吐量。增加线程可能加剧 CPU 和临时内存争用。

## RRC03. 隔离候选对照

仅在隔离进程中把 `payload = file.read(_MAX_OBJECT_BYTES + 1)` 替换成 64 KiB 分块读取。原有目录/链接/大小检查、分域哈希、类型解码、规范格式相等、输入/报告绑定及事件集合校验都仍在执行。没有编辑生产读取器。

| 交替暖读取完整投影 | 既有实现，秒 | 候选实现，秒 |
|---|---|---|
| 1 | 4.4478 | 2.0983 |
| 2 | 4.3525 | 2.1009 |
| 3 | 4.2942 | 2.0679 |
| 中位数 | 4.3525 | 2.0983 |

测得完整投影中位数下降 51.8%。全部对照的完整响应对象（包括报告 identity 和诊断）均一致。这不是 API/并发负载验收结果。

读取一个 506 字节逐日文件时，现有读取长度对应 Python 跟踪分配峰值 295,243,578 字节，分块读取为 198,540 字节。这是隔离 Python 分配峰值，不是进程 RSS，也不保证生产单请求内存。七项读取边界行为一致：空内容、一个字节、小于/等于/大于上限、错误哈希及文件缺失。空字节案例只测试字节读取器，之后仍有类型化 artifact 校验。实施验收前仍须补齐符号链接/junction、并发替换/增长及完整损坏/保留规则回归。

## RRC04. 建议实施顺序

| ID | 优先级 | 改动 | 完整性与验证边界 |
|---|---|---|---|
| RRC-T01 | P0 | 用有界 64 KiB 分块读取替换巨大的请求读取长度，到 EOF 或原有最大值加一个字节即停止。 | `_MAX_OBJECT_BYTES` 不变；解码前拒绝超限数据；对全部返回字节计算相同分域哈希；保留全部后续校验。批准后才能把隔离候选转为有回归测试的正式代码。 |
| RRC-T02 | P0 | 监控导航刷新只针对有意义的监控页面变化，避免每次回测 query/页签变化都刷新。 | 保留协议不匹配处理、命令预检、generation/sequence 校验、观察过期、重连及可见性恢复。进入可操作监控页面前必须建立新鲜 authority，才能显示可操作 UI。不能把旧快照重新标记为当前。 |
| RRC-T03 | P1 | 监控历史 N+1 读取改为有界批量读取 head/payload；在一次已验证遍历内减少重复规范化工作。 | 保留全部候选校验、缺失 payload 失败及既有 `snapshot_rank`：截止时间、LIVE 优先、事实请求数、观察时间、哈希。使用左连接或等价缺失行检查，不能让内连接静默隐藏损坏/缺失 head。不能用最大 revision 或 SQL 元数据排序替代已验证 payload 的选择语义。 |
| RRC-T04 | P1 | 测量后如仍必要，对等价并发监控投影做有界在途工作共享，并在单次读取内复用已验证表示。 | 绑定 authority generation/configuration/token、相关已提交身份及数据边界；保留读取后的 authority 检查和有界重试。取消一个观察者不能取消其他读取者，也不能提前释放物理工作。不是跨请求 TTL 缓存。 |
| RRC-T05 | 后续，仅在测量证明必要时 | 考虑独立 CPU 进程或可复用的已验证类型对象缓存。 | 进程所有权、关闭、错误传播和快照一致性需单独设计。缓存复用类型对象前必须重新读取并校验当前字节/身份，不能掩盖证据缺失/损坏或保留/置顶状态变化。 |

先实施 RRC-T01 和 RRC-T02，重新测量，再确定 RRC-T03/RRC-T04 范围。不立即扩线程、加长超时或引入长效结果缓存。先用风险较低的改动消除已测得的开销和多余请求。

## RRC05. 证据完整性验收门槛

1. 保留类型 schema、规范 Decimal/时间表示、输入/计划/数据集绑定、artifact 分域哈希、行封套检查及事件集合完整性/顺序/摘要检查。不改变 `reportHash` 或原始 artifact 字节。
2. 摘要/可用性/置顶/保留事实必须与读取快照一致。在途共享 key 在相关场景须包含可变 revision；不能仅因 `runId` 和置顶布尔值相同就复用旧 revision。
3. 成功读取后再篡改，下一次读取仍须失败：等长/同时间戳替换、逐日/报告/事件 payload 损坏、异属行身份、文件缺失、截断/超限及指数 payload 缺失。此前校验成功或文件名匹配都不足以信任。
4. 缺失、过期、未记录和不可用证据保持区分。浏览读取不能下载数据、恢复任务或重写持久证据。
5. 当前候选遍历会发现的历史指数损坏，优化后仍必须能发现。只选最新一行却不保留此契约会弱化校验，不属于本方案。

## RRC06. 测量与交付门槛

- 使用相同的 39 日 / 2,961 事件样本；交替进行暖基线/候选测量，冷读取另行标明。对比完整响应和全部证据 identity，不能只对比界面盈亏。
- RRC-T01 的候选目标：完整已验证投影中位数不超过 2.5 秒，且比可比基线至少改善 30%。仅针对该样本/环境，不是通用 SLA。
- RRC-T02 要统计初始路由规范化和回测列表/结果/页签/筛选导航中的面板请求。仅回测 query 变化应新增零次面板读取；重返监控及过期场景仍须获取新鲜 authority。
- RRC-T03 应把 1,929 次指数 SELECT 减为有界批次，同时保留该快照下相同的 1,928 次候选校验和 5 个选中身份。SQL 与校验 CPU 分开报告。
- 重测单次、同/不同运行并发、结果+面板、观察者取消重试和浏览器导航。分别记录排队、物理执行、校验、序列化、CPU、分配/RSS 和轻量服务响应。不能用两次样本发布 p95，后续性能门槛需足够的重复测量。
- 交付前运行既有 artifact/输入/发布/篡改/保留/置顶测试、结果线程共享/排空测试、监控 authority/协议/心跳测试及真实浏览器导航检查。分析实验不能替代这些检查。
