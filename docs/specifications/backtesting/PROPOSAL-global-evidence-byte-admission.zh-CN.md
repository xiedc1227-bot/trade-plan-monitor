# 证据分配前的全局字节准入

[英文原稿](PROPOSAL-global-evidence-byte-admission.md)。分析基线：`1748555`。本提案不代表批准生产集成。承接[有界传输验证报告](../../verification/bounded-validation-transport-2026-10-22.zh-CN.md)。[只读元信息探查](../../verification/evidence/2026-10-22-global-byte-admission-analysis/metadata.json)。

## GBA01. 发现与范围

建议先进行隔离 P0 实验，验证快照内尺寸探查、载荷 SQL 执行前准入，以及由应用持有的统一字节账本。进程集成继续附带前提。本轮分析没有修改生产代码、服务、真实数据库或现有校验。

当前 `IndexEvidenceFlights._lead_owned` 的 64 MiB 计数发生在 SQL 驱动取出候选、`RawIndexCandidate.from_values` 将 JSON 文本编码之后。`yield_per=128` 限制的是行数，而非字节。`_compare` 借用并保留共享证明，同时独立扫描另一个事务；其 SQL 缓冲、解码文本与编码重叠副本均在该计数之外。完整线程回退也使用相同的未纳入预算的扫描器。因此，现有计数约束共享输入的保留量，并不覆盖全部并发证据分配。

此前冻结样本的原始输入保留量为 30,826,621 字节。加上 16,777,216 字节传输预留和 7 份各 7,454,438 字节的跟随请求 SQL 批次保守额度，合计 99,784,903 字节（95.16 MiB），超过 67,108,864 字节（64 MiB）。这是算术包络，并非实测同时峰值。它还未计入额外转换与原生开销，不能证明生产安全。

账本必须由应用组装层持有，注入所有相关读取方，包括停止后的健康诊断、线程回退和重叠的排空代际。`get_health` 当前会创建独立的 `RuntimeStatusReadService`；每个服务各建账本会让额度翻倍。“全局”在此指本应用进程内全部已准入的指数证据输入工作，包括子进程传输租约。结果投影模型、其他应用工作及解释器/原生基线仍需独立的总进程内存门槛。如果部署多个服务进程，必须先定义跨进程或分区预算，才能扩展这一承诺。

## GBA02. 不取出载荷，先探查尺寸

在每个请求现有的显式读事务内，扫描有界元信息页，仅包含整数行定位符、载荷缺失标记、所有选中 head/payload 标量的存储类型与字节长度。不能为了量尺寸就先取出大型排序键或 JSON。元信息页及驱动预读本身也必须在查询前预留额度。保持当前过滤条件、外连接及完整排序；载荷缺失的记录仍须作为候选进入拒绝流程。

对原始列使用 `typeof` 和 `octet_length`，显式检查数据库编码及运行时能力。不能用文本 `length`、类型转换或 JSON 重写建立上界。文本长度在嵌入 NUL 处停止，且计算的是码点而非字节。SQLite 文档说明，文本/blob 列的字节长度可以利用记录元信息，而无需读取整个值：[标量函数](https://www.sqlite.org/lang_corefunc.html#octet_length)。本地 SQLite 3.50.4 / SQLAlchemy 2.0.52 / UTF-8 探查中，嵌入 NUL 示例返回 7 字节，而文本长度为 1。共发现 2008 个候选，最大 JSON 长度 35,587 字节，总 JSON 长度 27,588,993 字节。执行计划使用 head 排序索引与 payload 哈希索引，未报告临时排序。这些只是能力与数据形状观测，不是分配或延迟结果。

元信息与后续载荷读取必须使用同一连接、同一事务；不得另开连接预检，也不得等待后重新开启事务。现有显式事务所有权提供所需快照边界；WAL 读者持续读取原快照：[SQLite 隔离](https://www.sqlite.org/isolation.html)。每个跟随请求保留自己的快照。行定位符只是该快照内的临时标识，不是证据身份或新的信任来源。

主请求先用有界元信息扫描累加原始保留量的保守上界，只保留合计，不保存完整元信息清单。在构造输入集合前，一次性准入所需原始存储与推进工作区。第二次有界元信息扫描可以组织载荷分组。跟随请求仅规划下一组比对输入。初始实验建议采用 32 行元信息页、每个活动读取 1 MiB 载荷工作包络；两者均为实验参数，并非已证明安全的限制。按尺寸分组时可以少取行。若畸形输入无法建立行定位/顺序等价性，应失败关闭，不能跳过证据或改变有序证明。

载荷查询本身必须只选择已获准的定位符和有界行数。准入发生在 `execute` 之前，而不是仅在 `fetchmany` 之前：驱动启动、预读、结果封装及转换都可能提前分配。保持每个标量的实际类型、原始 JSON 表示和载荷缺失状态，再调用未改变的校验器或字面比对。取出后的计数仅用于发现上界失效，不能事后让越界分配变安全。应检查已安装驱动路径与执行计划，不能假定 ORM 参数能证明这一边界。[SQLAlchemy 缓冲说明](https://docs.sqlalchemy.org/en/20/core/connections.html#streaming-with-a-fixed-buffer-via-yield-per)规定的是行数，而非字节预留。

## GBA03. 租约与计量契约

建议总量公式：`R + T + sum(W_i) + M <= B`。`B` 仍为 64 MiB。`R` 覆盖全部保留的原始集合、集合向量和仍被借用的旧证明。`T` 覆盖传输所有权，暂用现有 16 MiB 包络。`W_i` 覆盖 SQL 标量对象、行封装、文本转字节、比对遗留引用和扫描工作区。`M` 覆盖有界元信息、定位符、账本/控制对象及其重叠。每项分配只有一个所属租约；共享引用不重复计算载荷所有权，但额外容器必须计入。超出这些类别的分配必须识别、约束，或明确判定门槛未通过。

仅以前次实测原始保留量举例：除传输外，再预留 8 个各 1 MiB 的工作槽及 1 MiB 元信息/控制额度，合计 57,041,021 字节（54.40 MiB）。这是建议分区，不是已证明的上界：新计算的原始输入上界可能高于实测保留量，大行也可能需要更大的工作区。不能由此推断全部现有记录或 8 个真实读者已满足预算。不得扩大 64 MiB 总限额或降低现有 8 读者准入上限来通过实验。

在分配前按类型计算上界，包含 Python Unicode 最坏存储、准确 UTF-8 字节副本、元组/列表容量、当前与下一候选共存，以及驱动/原生暂存。声明的字符串宽度和正常观测的 JSON 尺寸不能证明畸形存储值安全。元信息必须检查所有选中列，而非仅 JSON。SQLite 转换、排序、页缓存、解析模型及系统缓冲还需独立运行时调查和同步进程内存测量；Python 账本不是 RSS 上限。

显式转移查询工作区到原始输入保留区的租约所有权。最后一行、生成器局部变量、结果对象、异常栈或比对仍持有数据时，不能整批退还额度。异常不能让私有载荷滞留在保存的异常栈中。规则是先有租约才能分配；真正释放引用/资源后才能归还，不能只因观察者取消就退还。

## GBA04. 推进、不匹配与回退

物理校验开始前，预留不可被借走的推进工作区。它后续供数和排空不能依赖已被跟随请求用完的字节。初始原始输入/推进额度必须原子分配，不能一边保留不断增长的前缀，一边等待更多内存。等待请求只保留有界元信息/会话状态，原有截止时间继续流逝。不能持有 flight 条件锁或数据库/传输清理锁等待字节。

当前主请求会在校验前等待收集阶段的跟随者和已借用的比对。简单增加字节信号量可能造成死锁：跟随者等内存，主请求等跟随者。跟随者只有取得合适的比对工作区，才能借用证明；应使用协调器的原子决策，或重检并释放协议。等待额度的请求不能计入“校验前必须完成”的比对。已准入比对必须能够完成，保留现有完成边界，不能为了提高共享统计而延长已完成证明的开放时间。需要测量字节等待导致的共享损失和重复校验。

发现不匹配时，先关闭比对游标、释放临时行及借用证明，再等待现有唯一的排队主请求位置。获准后，在该请求原事务内完整重扫；不能拼接不同快照、仅校验不匹配后缀，或采用主请求证据。旧证明在所有借用者实际结束前持续计量。保持 1 个物理校验者和 1 个排队主请求；字节准入调度内存工作，不能暗中扩大并发。

不支持的传输类型或无法整体保留的输入，可以在向子进程提交前选择完整线程流式校验，但该扫描器同样必须申请字节租约。无预算回退会使全局承诺失效。不得提交后回退或重复校验。超大行不能截断或静默遗漏。接近现有 16 MiB 写入上限时，保守的解码文本/副本上界可能已经超过全部额度。这是需要测量、甚至单独设计捕获/校验方式的可行性阻塞，不能通过新增对原本合法输入的资源拒绝来掩盖。任意超大畸形输入可以失败关闭，但合法输入覆盖及受保护拒绝率是明确验收门槛。

## GBA05. 权威、时间与取消不变量

保留每个请求独立的前后权威检查、激活重读、原事务、观测时钟及现有 2 次尝试逻辑。共享仅在独立读取的证据完成全部有序字面相等比对后成立；尺寸、行定位符、哈希或元信息相等，不能替代该比对或全历史规范化/领域校验。不缓存已完成结果。

预算等待不能重置 15 秒等待截止时间，或延长目标/90 秒有效期。在元信息查询、载荷查询和每次新预留前重检取消与准入。成功响应仍须通过现有时间/权威检查。确定性测试应覆盖等待跨越激活、发布、保留规则和时钟边界；不能在已组装的快照内部临时刷新时钟。

载荷准入前取消，仅移除等待者及未使用预留。SQL/转换过程中取消，必须等所属工作关闭游标并释放引用，才能退还额度。已提交的子进程证明继续到结果和 `DRAINED`，或监督退出并完成桥接清理。跟随者取消不能撤销主请求证明。停止/存储暂停先阻止新租约并唤醒等待者，再排空所属读取、比对、传输和字节租约。清理失败保留相关租约和存储屏障；新代际不能依赖重置计数取得额度。不缓存权威，不缩短排空。

## GBA06. 下一步实施与决策门槛

先补齐本契约的双语规格/任务一致性，再仅实现隔离 P0 原型：

1. 审计已安装运行时的完整分配顺序、元信息能力、有界载荷查询和原生预读。在验收采样前记录正式账本范围及父子进程总内存绝对预算；后者未明确时，生产集成继续阻塞。
2. 先结合原线程校验器构建共享账本、预检扫描器及可持续推进的比对准入。在引入进程传输前验证原子预留与转移/释放。所有权设计覆盖停止后的健康组装路径和代际重叠。
3. 测试精确边界及越界分配尝试、并发相同/变更输入、大型与畸形旧行、全部历史完整性检查、独立权威、时间边界、重复取消和清理失败。变异测试必须捕获查询后才准入、漏记跟随者字节、复用完成证明、跳过字面比对、绕过权威或物理清理前释放。
4. 分别比较原线程路径、预算线程路径和预算分块进程实验。预先声明 1/2/8 读者同快照与变更快照工作负载，加上结果页重叠、迟到请求、不匹配和超大回退。每组两两对比使用 10 对 A/A 和 20 个交替 ABBA/BAAB 区块，保留全部失败、超时、回退及取消。不得替换失败样本。内存/分配采用独立重复运行和同步父子观测。
5. 发布双语发现及 P1 决策。测量元信息/载荷 SQL 次数与耗时、准入等待、比对耗时、共享率、重复完整证明、各类租约高水位、实际分配高水位、事务时长、WAL/checkpoint 压力、总 CPU 及完整请求完成时间。不能从延迟中扣掉准入等待，也不能把成功率下降当作改善。

硬门槛：已准入分配全部受租约覆盖，总量不超过 64 MiB，输出/完整性完全等价，独立权威、物理排空安全，既有边界内无死锁/饥饿，不新增合法输入样本拒绝，受保护拒绝/超时率不恶化。进程方案要求混合结果中位数至少改善 20%，孤立结果回退不超过 5%，监控中位数或总 CPU 回退不超过 10%。纯预算线程方案必须满足内存/正确性门槛及相同回退上限，无需声称进程加速。

P1 取决于全部门槛，包括原生/总进程内存边界。之后才提议默认关闭的生产集成，以及每方案 100 次尝试的真实所有者/浏览器验证；声称 p95 前必须每方案至少有 100 次成功观测，所有失败保留在分母中，并保留现有真实混合 p95 改善 20% 的目标。尺寸、正确性、生命周期或可用性门槛失败时，保留现有生产路径并重新审查设计。

## GBA07. 替代方案与分析限制

缩小 `yield_per` 可以作为实验对照，但不能保证字节有界。取数后申请信号量已经太晚。先读全量证据再估算大小会重现原问题。仅比较哈希或元信息会削弱精确共享；串行化全部请求会掩盖并发成本。扩大限额或无预算线程回退均违背要求。JSON 转 BLOB 捕获或增量校验可能减少大行副本，但涉及另一项表示/核心边界变更，暂不推进。

本轮分析仅增加双语提案和脱敏元信息证据，未测量全局准入原型、未运行新的并发/浏览器验收，也未证明建议分区成立。生产及并行 AI 提取/日库存工作保持不变；本次分析请求不包含提交或推送。
