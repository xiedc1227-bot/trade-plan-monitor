# 有界编码生产者与字节解析优化提案

## BEP01. 结论与范围

建议再进行一轮隔离 P0：先实现按大小规划的 C 编码生产者，独立证明字节解析器的生命周期包络，再修正字节准入。P1 继续阻断。不集成上一轮 Python token 编码器，也不直接降低其预留倍数。以 `786950f` 为起点，保留已有文件及并行 AI 提取、日库存改动。本次仅包含分析、双语提案和脱敏探针证据，不修改运行时或测试，不重启服务，不提交、不推送。

[上一轮报告](../../verification/validator-scan-2026-10-23.zh-CN.md)证明了跟踪内存降低，但 CPU、合法大行可用性和原生内存边界仍未通过。[新增分析证据](../../verification/evidence/2026-10-23-bounded-encoding-analysis/analysis.json)包含探针源码、全部诊断结果和指纹，冻结数据库保持不变。这些观察用于确定实验方向，不代表生产内存保证，也不代表真实页面尾延迟已解决。

## BEP02. CPU 回退与替代方案

当前 CPython 的 `JSONEncoder.encode()` 通过一次性路径调用 C 编码器。上一轮的 `iterencode()` 则在 Python 层遍历容器，产生大量小字符串，再逐块转成 UTF-8。仅第一条 1887 字节的历史行就产生 230 个 token。C 一次性调用也不是有界流：它完成整个 Unicode writer 后才返回输出。事后切分不能限制此前的分配。

新探针保留全部原有模型、域哈希、标量、头记录、历史行和字面值检查，仅在进程内临时替换实验生产者。对相同 2008 行、5 个指数执行 3 轮交替测试，全部 15 次完整输出比较均与原校验器一致。计时不包含 SQL、权威检查和样本构建。

| 方案 | 墙钟中位数，秒 | 线程 CPU 中位数，秒 | 相对原版 CPU 变化 |
|---|---:|---:|---:|
| 原完整校验器 | 1.9233 | 1.890625 | 0.00% |
| 上一轮 Python token 生产者 | 4.1880 | 4.171875 | +120.66% |
| 字节解析加整份文档 C 编码 | 1.9803 | 1.968750 | +4.13% |
| C 子树编码，64 KiB 逻辑输出目标 | 2.3640 | 2.328125 | +23.14% |
| C 子树编码，256 KiB 逻辑输出目标 | 2.3694 | 2.343750 | +23.97% |

整份文档方案是归因对照，不是内存安全候选。子树探针先遍历规范化树估算输出，保存容器大小映射，再对能放入预算的子树或列表批次调用 C 编码。每个域哈希和字面值遍历都重新规划。它收回了大量 CPU 损失，但仍超过 10% 回退上限；单纯扩大目标块没有解决问题。其大小映射、Unicode writer、批次切片和 UTF-8 分配没有受强制租约覆盖，不能直接复制为实现。

保留原有通用模型与规范化策略。优先评估在规范化时一次累计大小信息、有界批次规划、小文档 C 快速路径。如果仍有重复编码开销，再独立试验一次规范化遍历同时送入 snapshot 域哈希与字面值比较器，显式处理被排除的 `snapshot_hash` 成员及逗号；完整字面值仍包含该成员。bar/request 域与全部公式检查继续独立，不引入缓存证明或对存储摘要的信任。

## BEP03. 合法标量有上限，合法容器并不小

当前精确模型限制规范化 Decimal 展开长度为 10000 个字符，`display_name` 为 32 个字符。其余规范化标量是有界身份标识、枚举、哈希、受限整数和规范时间戳。因此，模型验证成功后，可以基于模式推导标量包络：Decimal 字符串 token 连同引号最多需要 10002 个 UTF-8 字节。必须审计全部字段及自定义验证器，才能认定这是完整边界。生成的 JSON Schema 本身不包含自定义 Decimal 展开约束。

`five_minute_bars`、`official_daily_bars` 和 `indicator_facts` 没有声明数组长度上限。16 MiB 写入限制不能保证整个规范化快照或编码数组足够小。保持现有合法输入集合，不为通过准入而增加行情数量或 Decimal 精度限制。还需计入排序引用向量、请求排序键、模型导出容器和保留的选中模型。模式或版本改变后，必须使优化包络失效，并在重新验证前阻止使用，不能继续静默套用旧边界。

对事先证明能放入预算的规范化子树调用公共的 C 编码接口。保持 `ensure_ascii=False`、`allow_nan=False`、键排序、紧凑分隔符、规范 Decimal 与微秒时间戳语义。按保守编码大小组批，不按固定行数。初始测量使用 64 KiB 和 256 KiB 逻辑目标，它们不是总内存限制。计入最坏 Unicode 字宽、writer 扩容与重新分配、UTF-8 转换、批次容器、比较缓冲及上一块已产出内容。不能对任意大根节点调用私有 `_one_shot=True` 并称其为流式处理。

补充字节等值检查覆盖长 Decimal 样本、Unicode 与控制字符、大数组，全部 6 次比较通过。通用的 `6 * len(string)` 规划规则让长 Decimal 样本在 64 KiB 下产生 24081 块，在 256 KiB 下产生 1041 块。这也支持从规范化阶段携带已验证的标量类别与长度信息：规范 Decimal 数字属于 ASCII，不需要通用转义字符串的展开系数。细化必须依据已验证类型策略，不能猜测原始 JSON。产出块的大小与这些检查都不能证明生产者或原生分配边界。

## BEP04. 字节解析需要形状与失败路径包络

直接调用 `model_validate_json(bytes)` 消除了完整解码 Unicode 输入，但仍会构建验证后的对象。该 API 接收完整 JSON 输入；接收字节不等于可续传解析器，也不承诺原生层零复制。解析期间必须持续持有不可变输入。不能改用 `model_construct()`、部分解析，或 `from_json()` 后再进行 Python 验证，因为 JSON 模式与 Python 模式的严格行为可能不同。

以下单次跟踪探针在原始输入构建之后开始。两个合法样本均通过未修改的完整校验器。密集样本使用符合当前模型契约的固定 `+08:00` 时间戳；最初采用历史时区规则的样本构建因夏令时偏移在测量前失败，已单独记录。

| 形状 | 原始 JSON 字节 | 内容 | 文本输入解析峰值 MiB | 字节输入解析峰值 MiB | 字节输入非法 OHLC 峰值 MiB |
|---|---:|---|---:|---:|---:|
| 长 Decimal | 16472833 | 480 条行情，8500 位小数 | 94.26 | 7.54 | 23.94 |
| 密集小对象 | 12120814 | 40000 条行情，1 位小数 | 107.95 | 73.27 | 149.53 |

非法变体把每条最高价替换为违反 OHLC 关系的值，分别产生 480 和 40000 个错误。探针有意保留错误对象直到显式释放，之后跟踪存活内存回到基线附近。这是解析器与错误生命周期诊断，不是生产泄漏证据。现有 flight outcome 会脱敏外层 projection 错误，而不保留其 traceback。应同时测量脱敏前峰值与排空后状态；最终缩短消息不能撤销此前已分配的错误集合。

这些测量不包含预先构建的原始输入和未跟踪的原生分配，不是端到端内存峰值、强制边界或计时验收。尤其不能把此前长 Decimal 样本的 23.71 MiB 完整校验峰值推广到全部合法行。仅按该样本校准字节长度系数不充分。需要形成覆盖原始字节、结构数量、Decimal 位数、Unicode 与转义、原生临时值、验证错误及保留结果的明确包络。固定实际安装的解析器构建并审计分配与清理行为。如果确需有界结构预扫描，应测量额外完整扫描的成本，并证明它不认证证据、不改变合法输入接受集合；不能在本轮 P0 隐式引入新解析器。

## BEP05. 准入与生命周期设计

当前字节扫描仍按近似 `12 * N + fixed_overhead` 预留：两代驱动字节、原始字节及最坏 `4 * N` 解码输入。因此，16472833 字节的合法行在执行 payload 查询前申请 197697036 字节，超过不变的 64 MiB 输入上限。这是旧路径的保守预留，不是新字节解析器的实测需求。不能用实测平均值或猜测的 `2 * N` 边界替代。

为每个阶段建立分配与所有权表：元数据、SQL 执行与取行、不可变原始数据捕获、解析器输入与临时值、模型及规范化、编码与哈希及字面值比较、选中结果保留、异常与排空。逐项明确分配、分配前租约、重叠持有者、转移及物理释放条件，尤其包括：

1. 保持既有输入账本范围：所有读取及排空代次中的原始数据保留、SQL 与输入转换、规范化或传输输入副本、比较工作区及元数据。解析模型、原生内存和选中输出也继续按现有记账契约纳入总进程内存门槛。不能把此前计费的输入文本重新归为模型或输出来制造“能放下”。73.27 MiB 的模型密集解析结果本身不等于突破了 64 MiB 输入账本。
2. 只移除已证明不再存在的解码文本分配。对同一不可变字节的引用可以共享所有者，额外缓冲和容器不可以。保留集合和 SQL 游标缓冲不能当成同一别名。只有迭代器、驱动及消费者生命周期证明不能重叠，才能减少前后两代预留。只有不能共存的阶段才能取最大值，否则必须累加同时存活的预留。
3. 在 execute、parse、encode 之前预留完整推进包络。区分仅比较工作区与物理证明工作区：追随者加入在途证明时会比较全部原始字段，但不会自己运行模型解析器。这种区分不能跳过其元数据扫描、字面值比较或权威检查。持有扫描许可或协调器、清理锁时，不得再等待额外字节。
4. 大行可以使用更大的按字节加权工作区，同时减少实际并行扫描数，仍保持 8 个读取请求准入。先预留领导者推进空间，再资助能完整放入预算的追随比较，并在等待 cohort 或证明之前释放扫描许可。验证大、小请求公平性、作用域变化和期限，不承诺同时提供 7 个大行比较工作区。现有小输入确定性 cohort 仍须达到 1 次证明、7 次共享。
5. 若完整保留集合放不下，应在任何子进程提交前选择完整验证、受预算约束的线程流式路径。只有单条合法大行确实能放入已证明的包络，这个回退才有意义。先释放不兼容的原始输入引用，不能携带无界保留前缀进入回退。单行准入失败仍是可用性门槛失败，不能记为回退成功。禁止提交后的重复证明。

输入限制继续为 64 MiB，总 working-set/private-commit 实验上限继续为 768 MiB/2560 MiB。覆盖全部 5 个选中指数、结果并发读取、替换时的旧选中模型、异常链，以及适用情况下的子进程内存和分配器保留。采样与 `tracemalloc` 不能证明原生边界。如果全部受支持形状不能满足不变上限，应报告具体阻碍并保持 P1 阻断，不能提高限制或静默缩小接受范围。

## BEP06. 权威、完整性与取消

每个请求保留独立的前后权威检查、激活状态重读、原始事务与观察时钟，以及 2 次尝试。字节和扫描等待继续沿用原始 15 秒等待期限、90 秒资格边界。只有完成独立完整等值比较后，才能共享仍在运行的纯证明。禁止已完成结果缓存、共享权威或预检证书、信任存储哈希、只验证最新数据。

保留所有历史行、依赖缺失和头记录检查、全部 19 个原始字段及存储类型、严格模型验证、含 EOF 的规范 UTF-8、排序后的 bar/request 域、snapshot 哈希、公式定义及每项事实公式哈希。生产者分段或双路输出必须生成与参考实现完全相同的字节，包括空列表、可选值、转义及控制字符、补充平面 Unicode、负零和 Decimal 极值。

取消只移除观察者或撤销未开始的工作，不能退还仍存活的 SQL 缓冲、原始引用、原生解析调用、编码块、传输或物理选中结果。同步解析器必须持有所有权直到实际返回，取消标志不等于物理中断。在有界生产单元之间检查取消，但不得授予部分证明。租约保持到资源释放；子进程还需达到 `DRAINED` 或受监督退出及桥接清理。其他观察者不能取消共享证明。游标或 worker 清理失败后，即使 CPU 许可可用，仍须跨代保留字节债务与存储围栏。

## BEP07. 下一轮实施顺序

1. **P0-A：契约与归因。** 编码前补齐双语规格和任务一致性。固定解析器、编码器及模式指纹与各阶段所有权类别。扩充长 Decimal、密集数组、全部 5 个选中指数、Unicode 与转义、密集错误样本。分别测量原始、模型、规范化、错误对象保留，原生分配，以及解析器和生产者线程 CPU。在改变任何预留前建立分配前边界。
2. **P0-B：C 生产者。** 分别比较原版、上一轮 token 生产者与按大小规划的 C 变体。在现有规范化遍历中累计可复用大小信息，约束描述符存储，避免每个哈希另建完整树索引。小文档使用快速路径，大数组按大小有界组批。仅在仍有必要时，再独立测试 snapshot 哈希与字面值双路输出。保持全部原有规范化 API 和验证策略。
3. **P0-C：解析器与准入。** 保留直接字节解析和显式不可变所有权。证明成功与失败路径的输入副本边界、模型和原生进程边界以及实际清理。证明成立后才引入证明与比较工作区区分和所有权转移。让接近 16 MiB 的合法输入贯穿 SQL 预检、payload、完整验证、排名和排空，仅解析器成功不够。在这些门槛通过前，保持前一轮 2 槽扫描候选独立。
4. **P0-D：组合门槛。** 验证 1/2/8 读取、相同或变化及晚到 cohort、大小混合负载、内存边界、死锁与饥饿、权威和时间变化、清理失败。之后比较有无扫描准入，且只有前置条件通过后才恢复进程传输。任何硬门槛失败都停止性能验收，可进行 3 轮明确标注的诊断来定位原因。
5. **P1：条件集成。** 只有正确性、合法输入可用性、所有权和原生边界全部通过，才恢复 10 对 A/A 和 20 个 ABBA/BAAB 块。保留进程方案混合读取收益至少 20%、独立结果回退最多 5%、监控及总 CPU 回退最多 10%、拒绝和超时率不得变差。获准的集成候选再进行真实 owner 与浏览器验收：每变体 100 次尝试，保留所有失败，成功不足 100 次不报告 p95，并保留现有真实混合 p95 改善 20% 的目标。

## BEP08. 必须完成的验证

与未修改的校验器差分比较完整输出和失败类别。覆盖全部域、标量及头记录篡改，重算根哈希后的破坏，旧行、缺失或多余及乱序证据，SQL TEXT/BLOB/NULL/数字区别，非法 UTF-8、重复键、非规范拼写及尾随内容。覆盖精确标量与批次边界、巨大合法 Decimal、大量小对象、大非 JSON 列、规范化展开及 writer 扩容，同时验证请求与行情排序、模式漂移。

内存方面验证 execute、parse、encode 前预留，规划器和缓冲增长，前后行保留，选中模型替换，异常 traceback 生命周期及重复排空。变异检查必须捕获未计费分配、遗漏字面值或权威检查、接受部分输出、复用已完成证明及提前退款。覆盖准入前、原生解析中、编码中的取消，以及 15 秒和 90 秒边界两侧；验证追随者离开、最后观察者离开、停止以及游标和子进程清理失败。保留既有权威、保留规则及取消排空测试。不能为未集成的诊断声称完成浏览器验证。

## BEP09. 来源、复现与限制

实测运行时为 Python 3.14.7、Pydantic 2.13.4、pydantic-core 2.46.4、SQLite 3.50.4、SQLAlchemy 2.0.52。对应 CPython 的 [Python 编码器](https://github.com/python/cpython/blob/v3.14.7/Lib/json/encoder.py)与 [C 编码器](https://github.com/python/cpython/blob/v3.14.7/Modules/_json.c)解释了分发路径和完整 writer 分配。Pydantic 文档说明 [JSON 与部分解析](https://pydantic.dev/docs/validation/latest/concepts/json/)及[直接 JSON 验证](https://pydantic.dev/docs/validation/latest/concepts/performance/)，这些 API 不保证解析工作区有界。Python 文档说明[跟踪分配范围](https://docs.python.org/3.14/library/tracemalloc.html)。本轮无法取得与已安装版本精确对应标签的公开 pydantic-core 源码，因此不声称已证明该版本原生分配边界。

证据内嵌修正后的诊断源码及运行时、源码、输入指纹。复现时保存到 `.pytest_cache/encoder-analysis-20261023/probe.py`，在仓库根目录依次运行 `.venv/Scripts/python.exe .pytest_cache/encoder-analysis-20261023/probe.py cpu` 与 `.venv/Scripts/python.exe .pytest_cache/encoder-analysis-20261023/probe.py parser`。CPU 模式使用现有冻结监控样本，解析模式仅构建本地合成输入，不发布原始证据内容。

CPU 诊断只改变生产者输出方式，并验证合法样本完整输出一致；探针没有完整篡改、生命周期或原生测试覆盖，不是可集成候选。解析计时使用跟踪且只有单次，CPU 为 3 轮中位数，均不是性能验收。本提案明确保持 P1 阻断，记录尚待证明的条件，不把更小的输出块当作内存保证。
