Canonical English; `SPEC-daily-plan.zh-CN.md` is the equivalent Chinese review copy. Date: 2026-10-02. Design baseline: `b2572b6`. ## D01. Objective, evidence and boundaries

**2026-10-02 authorized scope correction:** this product monitors plans and supports explicit user-triggered simulated trades. It does not track broker orders or actual broker fills. This revision supersedes the former daily-only partial-fill/order/reservation requirements. [Cleanup contract and tasks](../../../tasks/2026-10-02-daily-plan-simulation-cleanup.md) are the current implementation handoff; the 2026-10-01 reports remain historical evidence for their former scope.

Implement a complete, deterministic daily-plan chain: natural-language source → faithful partial candidate → deterministic validation → human content review → immutable final plan → explicit review-bound activation → daily confirmation → next-session execution reminder → explicit user confirmation → one atomic full simulated trade. A reminder, acknowledgement, refresh or scheduler callback never changes holdings; only the user simulation command does. There is no live brokerage submission, cancellation or broker-report collection.

The entire unchanged `../docs/TradingAgents/reports/新提示词.txt` was read. Its source-generation instructions do not authorize fetching current prices in this implementation task. The historical Spring Airlines example supplies holdings 100, cost 40.70, maximum 300, proposed CORE 100 / TACTICAL 0, low-buy 39.45–39.90, pressure 41.80–42.20, risk 38.18 and intended buy 100. It does **not** supply reproducible definitions for “明显缩量”, “止跌”, “冲高回落”, “连续受阻”, the status of 39.67/41.96 as fixed or dynamic references, or a proven pre-existing core allocation. Preserve these gaps. The user’s resumed scope overrides the old source’s fundamental-monitoring requirements: preserve that source text as non-monitoring background, without requiring its resolution for daily monitoring.

Code inspected: `domain/plan_models.py`, `plan_codec.py`; `ai/models.py`, `prompts.py`, `review.py`; `decision/risk.py`; `market_data/models.py`, `indicators.py`; `runtime/service.py`, `explicit_service.py`; `state/models.py`, inventory repository; Web plan/position services and routes. Schema 3 only supports completed five-minute rules, one BUY/SELL/RISK_ALERT each, ALL_REGISTERED selling and two repetition modes. Its review/activation already works; historical specifications describing R12 as pending are not evidence that current activation is disabled. `DailyBar` is explicitly unadjusted. `ta-v1` computes MACD histogram as DIF−DEA. Existing position Web values are board-lot constrained and derive some lot revisions from reduced quantity. These are compatibility boundaries, not reusable daily trading semantics.

Always preserve historical bytes, hashes, prompt contracts and evidence; validate user/provider boundaries; record all consumed revisions; keep English/Chinese documents equivalent. Never manufacture missing strategy thresholds, reinterpret advice as fills, edit the source template, weaken old tests or enable partially wired capability. No new dependency, provider, broker integration, cash-balance requirement, live-market/AI call or production-data mutation is needed. Unsupported amount-denominated caps remain visible and block dependent buys unless their reviewed budget/valuation basis and records are implemented; holdings risk must still be reportable.

The resumed scope permits only ordinary and severe technical risk in the new daily monitor. Fundamentals are reviewed by the user when generating the trading plan; fundamental/announcement text must never create a monitored condition, BUY/SELL prerequisite, risk trigger, execution blocker or mandatory announcement-verification task. It must not be relabelled as a technical human fact. Tradability, full-session suspension, exchange calendars, settlement and price-basis evidence remain operational inputs even when an official notice is their source. Broad-market index logic is deferred: preserve existing index behavior, adding or removing none in this revision.

## D03. Complete plan and partial candidate

The sibling plan retains `plan_id`, `version`, `symbol`, `name`, `market`, `metadata`, `activation`. Add the following strict fields; no extra keys, expression strings or executable code. Optional strategy choices are explicit tagged states, never omitted implicit defaults.

| Field | Required meaning |
|---|---|
| `levels` | LOW_BUY/PRESSURE ranges with explicit integer-fen endpoints and both inclusion flags; positive `risk_line_fen`; `risk_comparison=LT` or `LTE` explicitly reviewed. Require risk line < low-buy lower < = upper < pressure lower < = upper; reject intervals containing no valid tick. |
| `position` | `max_qty` in shares; reviewed CORE/TACTICAL allocation policy and its `EXISTING_CONFIRMED` or `PROPOSED` provenance. Targets are never initialized simulated inventory. Ordinary SELL is TACTICAL only. |
| `trading_rules` | Software simulation constants only:100-share units, `settlement=NEXT_EXCHANGE_SESSION`, `tick_size_fen=1`, `special_state_restrictions=BLOCK_UNVERIFIED`. Remove configurable `buy_min_qty`, `buy_increment`, `sell_increment`, `odd_lot_liquidation` and broker-rule `evidence`/`as_of`. No per-plan broker settings or evidence/date review is required; server product-contract binding supplies constants, not AI guesses. Old schemas remain unchanged. |
| `monitoring` | `timeframe=DAILY`, `indicator_formula_version=daily-ta-v2`, `price_basis=QFQ`, source/adjustment comparability requirements. Current execution quotes remain actual tradable prices. |
| `ordinary_rules` | At most one BUY and one SELL rule, each explicitly `ENABLED` or `DISABLED` with reviewed reason. Enabled rule supplies stable `rule_id`, corresponding zone, quantity, bucket, three evidence groups, validity/invalidation and independent-signal policy. A disabled action carries no invented trigger. |
| `risk_branches` | Exactly `ORDINARY_TECHNICAL` and `SEVERE_TECHNICAL`; each supplies scope, CORE involvement, exact target retained shares per bucket, evidence mode and named priority. | `execution_policy` | `confirmation=OFFICIAL_DAILY_CLOSE`, `ordinary_window=NEXT_EXCHANGE_SESSION_ONLY`, `same_signal=ONE_PLANNED_QUANTITY`, `risk_priority=SEVERE_THEN_ORDINARY`, `ordinary_conflict=BLOCK_BOTH`. These are visible Schema 4 product semantics, not an AI guess about an old source. |

An enabled ordinary rule requires `price_structure`, `volume_or_candle`, `technical` condition roots, all simultaneously satisfied, plus applicable reviewed prerequisites (for example a risk/reward judgement; never fundamental or announcement review). Each root may contain explicit ALL/ANY. Price region alone or a standalone indicator cannot supply the three dimensions. Do not mechanically invent fee/return thresholds: a plan-specific reviewed viability fact can carry the computation/evidence where no numeric rule was specified. Missing auxiliary evidence blocks only a branch that actually requires it; unrelated daily inputs must not hide an already-confirmed technical risk obligation. Missing fundamental or announcement information is outside the monitor and causes no missing-input result or execution blocker.

`DailyPlanDraft` mirrors the contract with typed nulls plus source evidence and unresolved/unsupported items. A draft may be saved and displayed with missing quantities, validity, end flags, thresholds or branch scope. Only the complete executable variant plus a current finished review may activate. Runtime missing inventory does not falsify content review; it blocks dependent execution readiness. Missing max quantity can remain in the draft while risk information is visible, but does not grant an incomplete plan general activation.

Every daily simulation quantity is field-validated as0 or a multiple of100: initial CORE/TACTICAL, `max_qty`, position targets, ordinary planned quantities, risk retained targets, simulated holdings/sellable and displayed executable quantities. Executable trade quantities must additionally be positive. Reject incompatible complete plans during review/activation; drafts retain explicit issues. Do not change a global `Qty` alias used by revisions/counters. The technical-risk `PENDING` state means awaiting the next official close and remains; only broker-order PENDING/CANCELLED/UNKNOWN is removed.

## D04. Finite daily conditions and exact evidence

Use a bounded typed tree (depth ≤4, ≤50 leaves across the plan) with three outcomes SATISFIED / UNSATISFIED / MISSING_INPUT. ALL is false if any child is false, otherwise missing if any is missing; ANY is true if any is true, otherwise missing if any is missing. Retain all branch evidence. Bounds are resource constraints, not trading thresholds.

| Leaf family | Required fields and calculation |
|---|---|
| `DAILY_PRICE_COMPARE` / `DAILY_PRICE_IN_RANGE` | OHLC field, completed-bar offset, LT/LTE/EQ/GTE/GT comparator or explicit range, and fixed price or dynamic reference. Offset 0 means the completed confirmation bar; never a forming bar. |
| `DAILY_VOLUME_RATIO` | Current completed volume compared with PREVIOUS or arithmetic MEAN of exactly N preceding completed stock sessions, excluding current; comparator and exact decimal ratio required. No substitution with median or intraday cumulative volume. Missing/uncertified session or zero denominator gives MISSING_INPUT unless an explicitly supported zero-baseline rule is reviewed. |
| `DAILY_CANDLE_RATIO` | Named lower-wick, upper-wick or body/range ratio and comparator/threshold. Lower wick = min(open,close)−low; upper wick = high−max(open,close); body = abs(close−open); denominator = high−low. Zero range is missing for a ratio. Bullish close or nondecreasing close can instead use price comparisons. |
| `DAILY_INDICATOR_COMPARE` | Named indicator, exact formula version/parameters, offset, comparator, and fixed value or another offset/reference of that indicator. Crosses require both previous and current comparisons explicitly; “improving” is not automatically a cross. |
| `DAILY_CLOSE_SEQUENCE` | Explicit N completed sessions, comparator and fixed/dynamic reference or pairwise nondecreasing closes; exact window inclusion and session identities. No implicit interpretation of “连续受阻”. |
| `REVIEWED_FACT` | Typed fact kind, semantic evidence requirement, applicable date/signal, revision and validity scope. Human confirmation must include concrete evidence and identity; generic acknowledgement is insufficient. Used for qualitative structure/volume facts and plan-specific technical/trade-viability judgement that the source cannot safely quantify. `ANNOUNCEMENT_CHECK` and `FUNDAMENTAL_INVALIDATION` are forbidden in the new daily fact/condition contracts, including nested prerequisites, invalidation and independent-event policies; do not encode the same semantics under another fact kind. |

A price/indicator reference is a discriminated object: `FIXED` contains value, unit and as-of/source; `DYNAMIC` contains indicator name, parameters, formula version and completed-bar offset. Fixed 39.67 must never silently become current BOLL_LOWER; dynamic BOLL_LOWER must never freeze at 39.67. Each evaluated leaf records bar IDs, source/cutoff/adjustment basis, operands, exact parameters and outcome. A fact-only ordinary signal still needs verified complete daily OHLC and all three independent evidence groups.

Keep adjusted calculation prices as exact decimal values where needed; do not round every adjusted historical bar to an integer tick. Preserve unadjusted quotes and prove comparison with plan price levels/current quotes. The existing raw `DailyBar` alone does not satisfy this contract. Missing corporate-action factors or a comparability mismatch yields `PRICE_BASIS_UNVERIFIED`, not raw-price substitution. All bars in a series come from the same validated source/basis; no mixed partial histories.

Reuse certified exchange calendars and suspension facts. Windows use the requested completed stock sessions; proven full suspensions may be skipped for indicator windows, but missing scheduled data may not. Record actual dates and skips. Never create zero-volume synthetic bars. Plan dates and execution windows use exchange sessions, which is different from an indicator observation window. Calendar/suspension status unknown is a missing input. Asia/Shanghai timestamps are mandatory; report timestamps with missing timezone remain unverified.

Prefer 250 observations, but do not require 250 for every rule: MA20 needs 20, MA60 needs 60, RSI14 needs 15 closes, ATR14 needs 14 bars; MACD exposes its warm-up length and requires a reviewed adequate-history policy rather than claiming the first EMA sample is reliable. ## D06. Ordinary signal and execution lifecycle (`daily-plan-monitor`)

Confirmation consumes only an official completed daily bar. It creates a durable occurrence with `signal_id`, strategy lineage, rule ID, evidence fingerprint, `confirmed_trade_date`, immutable planned quantity, source/review identity and next exchange-session date. A forming close, intraday touch or five-minute result cannot confirm it. An already confirmed signal imported during its valid window retains its original date after evidence verification; review/update must not add another waiting day.

The execution window is the next exchange session from session opening until that session's close. At close it expires; a close-time replay cannot deliver a newly actionable ordinary instruction. Reevaluate during existing certified live targets using a fresh actual quote: it must still be inside the corresponding zone; stored confirmation must remain valid under the reviewed invalidation policy; higher-priority risk must be absent; current simulated inventory, T+1 sellability, the100-share simulation unit, fixed simulation rules and unconsumed signal quantity are rechecked. Out-of-zone means no chasing. A later return inside the zone during the same window may restore readiness only if the signal was not otherwise invalidated. No new instruction quantity is created.

Use durable ordinary states `CONFIRMED`, `READY`, `SIMULATED`, `INVALIDATED`, `EXPIRED`; delivery/read status is separate. A READY notice grants no automatic position mutation. One successful simulation consumes the entire immutable planned quantity once; `simulated_qty` is either0 or `planned_qty`, never a partial balance. Expiry removes unconsumed authority without erasing a simulation receipt. Remove daily order states `PARTIALLY_FILLED`, `FILLED`, `EXECUTION_UNKNOWN` and broker reconciliation logic; do not rename them to keep the same subsystem.

One confirmation authorizes one planned quantity. New dates, false/true flicker in auxiliary inputs, price re-entry during the same window, restarts, reactivation, replacement and delivery retry are not independent signals. A rule requires an explicitly reviewed independent-signal policy: either a named later completed-day reset/retest condition followed on a subsequent completed day by a fresh confirmation, or a human-verified independent-event fact identifying new structure/evidence and the prior signal. Mere “condition remains true” cannot rearm. Null/missing policy blocks repeated buys. Preserve occurrence lineage and consumption across plan versions; a changed version cannot reuse the same evidence as a new purchase. Carry a still-valid occurrence to a new reviewed version only through explicit lineage/equivalence verification with its original dates and quantities; otherwise expose it as historical without granting new quantity.

Holiday/weekend example uses an injected certified calendar: Friday confirmation, Monday closed, Tuesday open → Tuesday only. If the stock is suspended throughout Tuesday, no ordinary execution; remaining authority expires Tuesday close, not the resumption date. If suspended only part of the day, only certified tradable targets within Tuesday qualify. Missing calendar blocks scheduling. Restart/late data may reconstruct state but cannot emit a historical executable ordinary instruction after expiry.

## D07. Risk branches, scope and persistence

Risk is evaluated before ordinary actions. `SEVERE_TECHNICAL` outranks confirmed `ORDINARY_TECHNICAL`; combine active obligations without increasing a bucket's target retained quantity. A higher-priority branch cannot accidentally cancel a lower branch's already-confirmed reduction. Unknown relevant risk inputs cannot be assumed clear for ordinary execution. Risk facts and instructions are independent of cost/profit and auxiliary indicator filters.

| Branch | Confirmation and earliest execution | Required scope |
|---|---|---|
| `ORDINARY_TECHNICAL` | First official close below the reviewed risk comparison stops additions. The **next exchange session's official close** still below the same line confirms exit; earliest following exchange session. No lower close, higher volume or worse MACD requirement. Recovery before confirmation enters observation, never automatically restores buying. | Explicit TACTICAL reduction first, newest additions first; CORE may be included only when its holding structure is explicitly invalidated and reviewed. Exact retained CORE/TACTICAL targets required. |
| `SEVERE_TECHNICAL` | First completed official daily close with verified substantial structure failure **and** price/volume deterioration → next exchange session. No compulsory second close and no invented universal drop/volume/wick thresholds. | Verified failed structure, deterioration evidence, affected buckets and exact retained targets. |

For LT at 38.18, close 38.00 then 38.10 confirms ordinary exit despite the rebound; equality 38.18 does not count as below. For LTE, equality does count, and that choice must be explicit. Preserve the line and comparison from the first breach; moving it down or editing the plan cannot erase pending/confirmed risk. Adjustment-related equivalent conversion must prove unchanged economic risk.

If the next exchange session has no valid official stock bar because of a verified suspension, do not invent the second close or call a later bar “next day”. Keep additions blocked and show pending confirmation. The source template does not decide whether resumption continues the first breach. Require an explicitly reviewed `suspension_confirmation_policy`: `RESUME_FIRST_CLOSE` confirms on the first valid resumed close still below the line; `RESTART_ADJACENT_PAIR` uses that resumed below-line close as the first of a new adjacent-session pair. Neither is a default. A missing choice blocks this timing decision, not an independent severe technical escalation. An unverified missing bar is data recovery, not suspension. Show and test both alternatives; the user's answer determines the actual plan's value.

Once confirmed, risk remains latched across rebound, ordinary-window expiry, restart and plan replacement until holdings reach the reviewed target or a **separate reviewed reassessment** records new evidence that the original cause is removed. Retiring an active plan cannot fabricate risk resolution; historical outstanding risk remains visible and replacement must carry or explicitly reassess it. Explicit monitoring deactivation stops new monitoring/delivery according to existing controls while preserving the outstanding obligation record. An ordinary alert acknowledgement, generic “risk clear” toggle or plan edit cannot clear it.

Risk simulation quantity is recalculated as excess over target in each applicable bucket, capped by authoritative simulated T+1 sellability and fixed simulation rules, rounded down to complete100-share units without selling below the target. The user confirms the whole currently offered risk quantity; one transaction may apply server-derived debits to both affected buckets. A later settled tranche is a new current risk simulation against the remaining obligation, not partial execution of an order. TACTICAL newest additions are prioritized, without delaying a CORE exit already required by the branch. Record immediately executable quantity, unavailable quantity and its next condition (settlement, suspension, liquidity or unknown sellability). Known risk with unknown inventory still raises a risk notice, with quantity unknown; never fabricate zero or hide the risk. Limit-down/illiquidity without certified tradability does not authorize simulation. No ordinary price-zone requirement applies to a risk exit.

## D08. Simulated inventory and atomic whole-lot trades

Keep simulation storage isolated from real/legacy inventory. Use the existing generic daily `POSITION` and `SIMULATION` records for a minimal simulated holding, a monotonic daily inventory revision and acquisition-date batches needed for T+1/strategy order. Do not write simulated holdings or receipts into shared `PositionLot`, `PositionInventoryConfirmation`, opening balances or legacy inventory revision/sync paths; do not alter those old capabilities. This is a small simulation state, not a brokerage ledger or new storage service. The daily UI calls the position a simulated holding and distinguishes it from a plan target. Initialization confirms aggregate CORE/TACTICAL quantities in100-share units; their sum is the total. It requires only symbol, bucket quantities and current inventory revision, with server time and calendar evidence. An initial baseline means simulated holdings already settled before setup; it is sellable in the first certified open session at/after initialization. When no certified session is available, sellability stays unavailable. Never copy real/legacy holdings automatically. Repeating the exact baseline is idempotent, not an added position. Initialization cannot overwrite a nonempty simulated position, reclassify later batches, delete history or reset consumed signals; conflicting preexisting data returns an explicit conflict. No client lot IDs, allocation arrays, broker evidence, sellable assertions or outstanding-order completeness fields are accepted. T+1 sellability is derived from simulated acquisition/settlement dates and the certified calendar; no guessed weekdays. Unverified legacy settlement/classification remains an explicit unsupported/not-ready condition, never fabricated proof.

BUY capacity = `max_qty - simulated_total_qty`. There are no orders, pending quantities, unknown-execution balances or reservations in the new daily chain. With actual simulated total200 and max300, a valid BUY100 succeeds atomically and leaves300; another BUY is blocked. Ordinary SELL debits only settled TACTICAL, never CORE. Risk SELL follows the applicable reviewed bucket targets and newest additions first internally. The server selects eligible simulated acquisition batches; the user neither sees nor supplies internal debit instructions. Today's simulated buys become sellable only at the next certified exchange session under T+1.

An accepted explicit simulation command succeeds once for the full offered quantity, which is a positive integer multiple of100, or changes nothing. Ordinary quantity must equal the original unconsumed signal's planned quantity; if capacity/sellability only supports part, block instead of shrinking it. A risk command must equal the entire currently offered whole-lot risk action at the requested revision, with targets and T+1 preserved; unavailable exposure stays a risk obligation, not an order remainder. Server-derived current verified quote price and server execution time label the receipt as simulation, not proof of a broker fill. Do not ask for a brokerage execution price/time/evidence report. Insufficient quote/calendar/risk/holdings authority is a business rejection with zero mutation, not a pending simulated order.

Persist a server-generated `simulationId`, plan/review binding, exact cause/revision, side, quantity, simulation price/time and inventory revision before/after. Use existing daily storage with distinct `SIMULATION` receipts and simulation-tagged `POSITION` records under separate simulation IDs, never reinterpret an old broker-position payload. The unpublished0024 CHECK/model may add this kind in place for fresh development databases; do not add a migration series or alter released migrations. An existing incompatible development table/layout returns an explicit unsupported error before mutation, not an automatic rewrite. No order entity, broker identifier or status machine is needed. Atomic idempotency and consumed ordinary authority survive retries, restart, plan edits and plan_id changes. Simulated receipt, simulation position changes, consumed quantity and inventory revision commit together; any failure rolls back all of them. Notification delivery, acknowledgement, extraction, review and activation cannot create a receipt or mutate holdings. Cash balance and a separate manual/unlinked trading workflow are outside this cleanup.

## D10. Atomic runtime, notification and recovery

Add typed dispatch at the real production scheduler/`runtime/service.py`, official-close and intraday targets, context assembly, persistence, projection, read views and notifications. A standalone pure evaluator without this path is incomplete. Confirmation evaluation identity contains plan hash, execution version, rule/branch, official trade date and captured activation/review/data revisions. Durable signal identity additionally uses strategy lineage and evidence fingerprint so revision changes cannot reset consumption. Execution checks reference the existing occurrence and a current target; they cannot create a second planned quantity.

In one short unit of work: claim target, recheck active plan/review, calendar/data authority, inventory/fact revisions, persist evidence/results/state transitions and outbox events. Any mismatch rolls back and reevaluates; external I/O is outside the transaction. Unique occurrence/simulation keys protect races and retries. Simulation commands fence in-flight evaluation. Persist both technical risk branches and the separate ordinary occurrence; no reuse of legacy `RiskState` deterioration gates.
