## 3. Minimal contract and trigger

Add one bounded `buy_suspension` definition to the new current plan/draft contract: the existing 5-minute close predicate, `effective_from`, and fixed semantics “all plan BUY / reviewed replacement only.” These semantics are not configurable policy families. If the source requires this guard, omission is a blocking error; optional means absent only when the source has no such obligation.

Use existing certified, completed minute data, trading-calendar rules, QFQ/comparable-price checks, and price precision. The threshold must be comparable to the existing `CURRENT_QUOTE_BASIS`; unresolved corporate-action or price-basis differences produce unknown eligibility, not a silently rebased threshold. There is no new market-data provider, indicator, rolling-low calculation, or requirement for a preceding close above 24.20.

`effective_from` must explicitly identify an exchange-local `+08:00` 5-minute boundary; do not infer it from filenames/import/activation or silently round it. Include bars whose start is at or after this boundary and whose end is no later than the current applicable completed-bar target. Use one qualifying completed close; incomplete bars, ticks, quotes, daily values, and synthetic gap fills cannot substitute.

## 4. Durable state and BUY enforcement

Reuse the existing plan state, transaction boundaries, and recovery mechanism. Persist only what this capability needs: definition identity, effective start, continuous checked-through position, durable latch/revision, and observed trigger evidence with source/bar identity and price basis. Existing review/source/replacement identities bind this record; do not add a generic evidence registry or lineage platform.

Three logical outcomes are sufficient; these are specification labels, not a demand for three new public DTOs:

- **Unverified:** the applicable interval or ownership/basis is unresolved. BUY is blocked, but the system must not claim a price breach occurred.
- **Clear through target:** the entire applicable interval through the current completed-bar target has been checked without a breach. This only clears this guard; it does not authorize a trade.
- **Latched:** a valid qualifying bar has been observed. The old plan context stays banned across rebounds, days, restarts, normal updates, deactivation/reactivation, or later corrections to the bar. Preserve the original evidence; correction does not silently unlock.

A clear-through conclusion must bind the checked interval to valid data-source/revision proof. If that interval is invalidated or revised, discard its clear eligibility before any further BUY and recheck through bounded batches. For example, a previously checked close revised from `2430` to `2419` must be detected on revalidation and latch the ban; a cursor alone is not sufficient proof. If proof validity cannot be established, remain unverified. This rule is separate from the prohibition on unlocking an already latched ban.

PBS-T01 code check at `ec1eca437940bd5fd79c556c0d5ebbcd41949a68`: `MarketHistoryRepository.list_minutes` and `_upsert_minute` in `src/trade_plan_monitor/state/repositories.py` provide bounded committed-row reads and later-receipt replacement/conflict handling. `reviewed_fact_observation_source_hash` in `src/trade_plan_monitor/state/daily_state_models.py` reaggregates exactly five minute rows into a content hash; it explicitly does not prove ownership or market truth. `upsert_five_minute` rejects conflicting facts at an existing identity instead of revising them. None of these is an interval-wide freshness/revision certificate, and `MinuteBar` storage has no provider revision field. Market-index provider revision heads do not certify stock-minute history.

T05–T06 must add a guard-specific, bounded adapter at these existing storage/runtime seams: bind checked batches to exact committed minute content, calendar and comparable-basis evidence; invalidate the guard's clear eligibility and advance its revision in the same write transaction whenever an affecting minute/basis/calendar change is accepted; then reaggregate and recheck affected coverage in bounded batches. The final clear/BUY check must fence both that revision and the applicable completed-bar target. A stored hash with no current comparison or invalidation guarantee is insufficient. Restart/restore, unobserved mutations, immutable-aggregate conflict, or missing basis/ownership proof must leave the guard unverified until safely revalidated. Do not invent an existing historical-revision API, poll all history without bounds, or add a generic revision service. If the adapter cannot prove validity, blocking BUY is the required result.

The adapter must also make progress: with a finite applicable interval, available verified history and stable calendar/basis/content, resumable batches must finish checking the interval and yield clear-through or latched as the data requires. Use the existing verified historical-batch/calendar seams for prior sessions; `RecoveryService.recover_scope` only repairs current-day gaps. Each recovery step retains the existing 240-minute-identity bound. A revision must lead to invalidation and actual bounded rechecking, not a permanent unverified placeholder for recoverable data. Prove both finite completion and an accepted historical correction through the real storage write path in T06.

A valid observed breach can latch despite an earlier gap; do not describe it as the earliest historical breach unless that is proved. Claiming no breach requires continuous coverage. Initial history and downtime must be checked through existing bounded recovery batches; the current 240-minute-identity recovery limit and provider retention are not permission to truncate the interval. Gaps, exhausted budgets, calendar uncertainty, or unavailable history leave BUY blocked. No unbounded recovery worker, manual “nothing happened” override, or reset-to-now shortcut is introduced.

Evaluate this guard before BUY conditions in each processing cycle. A breach invalidates pending unexecuted BUY signals and suppresses actionable BUY notifications; retain history. Recheck eligibility before dispatching a queued actionable BUY notification. At the actual BUY commit boundary, atomically check the active plan/review identity, guard revision, and checked-through coverage against the latest applicable completed bar. Direct API calls, stale pages, cached readiness, and both tranches must use this check.

Serialize breach, activation, and BUY commits through existing symbol/plan transaction controls. On the same bar the ban takes priority; after a latch commits, a subsequent BUY cannot commit. Already completed BUY is not reversed, and replay/idempotent retries do not fill again. No reset of consumed tranches, position, cost, or accounting is allowed. A missing or latched BUY guard alone must not stop otherwise eligible SELL, independent risk evaluation, or their notifications.

## 5. Ordinary continuation and explicit recovery

Ordinary 03 → 04 continuation inherits the definition/start and any latch. Merely revising the source, changing the date, dropping the field, copying a plan ID, deleting/recreating, deactivating, or selecting an older contract cannot clear the ban. Use existing server-owned predecessor/same-symbol replacement binding; a client must not declare an actual replacement “unrelated” to evade it. Truly unrelated plan contexts and other symbols are not globally banned. If an existing path cannot establish the binding safely, block that activation rather than build a new lineage service.

At the checked HEAD, `PlanUpdateContext.base_hash`/`snapshot` and `SourceCandidateAssurance`'s `binding`/`prefix_hash`/`parent_hash` bind source-update ancestry, while `PlanRepository.activate`, `PlanActivationState`, and activation event/audit history bind the actual per-symbol activation revision. Source ancestry or a client `independent` flag alone does not prove runtime replacement authority. T04/T08 must bind the server-resolved predecessor version, plan/content/source/review identities, activation revision, guard definition/state revision and actual unresolved interval to the exact new version/source/review, replacement reason, retirement decision and `strategy_effective_from`. Store this bounded receipt as `BuySuspensionReplacementBinding`, version `buy-suspension-replacement-v1`, within the existing review/supplement evidence flow. On activation, compare it again under the existing activation writer transaction; never trust a client-selected plan ID as the predecessor. Keep the obligation reachable after deactivation using persisted activation history/guard ownership. Ambiguous same-symbol ownership blocks the affected activation; it does not create an account-wide ban. Existing source cutover receipts are not suspension replacement receipts.

An explicit recovery candidate must contain new BUY instructions, a scoped statement that it replaces the predecessor's ban, an explicit new effective start, and the intended guard under the new strategy. The new plan may omit the old 24.20 guard only if the approved new source explicitly retires it; silence or omission is not retirement. No algorithm detects a new bottom for the reviewer.

The existing review/supplement flow must display and bind the predecessor's ban definition, state/revision, replacement reason, new source hash, new guard/start, and exact plan version. Saving or reviewing alone does not recover. Activation rechecks those bindings and all other mandatory obligations atomically. A newly latched predecessor or changed source after review invalidates the stale approval. Recovery affects only the newly activated context; preserve the old ban and audit evidence. The new context cannot allow BUY before its explicit strategy start. If it contains a new guard, that guard has its own explicit `effective_from` and requires coverage through the current target; a start preceding activation requires catch-up. If the new source explicitly retires the old obligation and sets no `buy_suspension`, no absent-guard interval is required, but all remaining BUY conditions and validity checks still apply. An unverified predecessor may be explicitly superseded only when review acknowledges the unresolved interval and the new source supersedes that obligation; its historical state remains unverified, never clear. Ordinary updates cannot use this exception. Activation itself never creates a trade.
