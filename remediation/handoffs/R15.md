## 1. Outcome and diagnostic path

The real Web extraction entry now records a content-free receipt after each completed extraction. `create_production_app` and the dedicated R14 bounded launcher both select a JSONL sidecar from their configured SQLite path: for a future isolated `data/r14-acceptance/<new-run-id>/monitor.sqlite3`, the receipt is `data/r14-acceptance/<new-run-id>/monitor.ai-extraction-diagnostics.jsonl`. This does **not** add records to the 2026-09-14 R14 database retroactively. The file is local only, inherits the database directory's access controls, and is not served by HTTP. Each record is at most 2,048 bytes; the file retains at most 512 records and 1 MiB, removing older records at the cap. There is no automatic time-based deletion; remove it with the isolated database after diagnostic review.

Each record has version, operation/request ID, source SHA-256, configured provider ID/model, prompt version, completion time, extraction status, stage/reason, safe path, optional allowlisted schema error type and provider error code, normalized finish reason, whether the provider model matched the configured model, attempt count, and validated usage if available. Missing provider envelope/usage is `unknown` or null. Provider-returned model names are never copied into the record; the requested configured model is used. For schema failures, the first path is derived only from code-owned schema field names, up to 12 segments/160 characters with indices at most 255; an unknown key becomes `unknown`. Neither Pydantic input/context/message nor provider error body is stored. The private extraction diagnostic is excluded from ordinary result serialization.

The public `GET /api/v1/plan-extractions/{operation_id}` still has no draft, provider content, model, source hash, or usage on failure. It now has `diagnosticStatus`: `RECORDED` or `WRITE_FAILED`. Normal Web startup/extraction stays available when the sidecar is unwritable, and a later write failure does not change `INVALID_OUTPUT` or `SUCCEEDED` or block valid review persistence. The R14 bounded launcher alone refuses to start its paid session if the sidecar is unwritable, before any AI request. Existing output validation, activation review, byte/token limits, and R14 3-AI/60-market/date/single-session guards are unchanged.

## 4. Conditions before another real R14 attempt

A new, explicit approval and bounded session are required; the 2026-09-14 one-shot claim cannot be reused. Before any paid call, choose a fresh isolated database/run ID, verify the sidecar is writable and the R14 launcher gate remains active, and separately review market/index budget and current date/certification readiness. The future operator can use the normal Web extraction and inspect the sidecar after completion; no live debugging or code edit is required to learn a safe failure category, finish-reason bucket, schema path/type, or available token usage. A successful AI result still needs human source comparison, review, activation, real stock evidence, and user-visible alert checks before R14-A/C7 can pass. If the next result fails, preserve its new bounded diagnostic and investigate offline; do not infer that a simulated case identifies the old three failures.
