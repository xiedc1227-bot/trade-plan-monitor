## 2. 根因与有界修复

四项 dashboard 用例没有处理 `ExplicitRuntimeDashboardPanel.vue` 实际发出的 `GET /api/v1/plan-versions?offset=0&limit=100&status=ACTIVE`。Vite 返回404，浏览器审计正确报错。测试现要求精确路径和查询，并返回符合合同的空活动版本页（`items=[]`、`offset=0`、`limit=100`、`total=0`），同时断言对应的空状态文案。未知 API 仍失败；没有为了适配旧夹具修改产品行为或 API 合同。

持仓命令用例未模拟独立库存读取和人工事件风险读取。两个面板因此显示各自真实的读取失败警报，使全局 `getByRole("alert")` 产生歧义。夹具现在分别提供带 `POSITION_UNKNOWN` 的明确 `UNKNOWN` 库存、`NO_ACTIVE_PLAN` 人工风险状态，并核对真实查询与响应形状。测试验证两个面板的不同状态，把命令冲突警报限定在 `人工持仓批次` 区域，同时保留建仓/减仓请求载荷、后端冲突、私有细节不泄漏及 T+1 原因可见断言。浏览器不自行判定最高数量或当日可卖性。

安装入口用例曾在故意停止自有回环服务时让活动页面持续请求，产生真实的 `ERR_CONNECTION_REFUSED`；不能把它称为服务正常运行阶段的错误。现在先审计完整的停服前页面并关闭它，停止自有子进程，用单独的 Node 探针验证预期的 `ECONNREFUSED`，再使用同一安装入口及临时空 SQLite 重启，并审计新的恢复后页面。前后页面的浏览器控制台警告/错误和失败请求均为零；API 与页面均显示类型化 `UNAVAILABLE/EMPTY_DATABASE`、sequence 0。测试没有抑制浏览器错误或全局过滤连接拒绝，也没有声称故意离线期间的页面无错误。

Windows `EPERM` 定位到该测试临时状态目录中生成的两把仅所有者可访问密钥：`data/monitor.cursor.key` 和 `data/backtest-cursor.key`；旧清理只重置了后者。先仅修正前者的探索性运行仍失败，从而证实两把都需要测试专属收尾。自有服务退出后，清理校验记录的 `mkdtemp` 真实路径、精确临时父目录边界和名称，拒绝替换/重解析的根目录、数据目录或密钥路径，只重置这两把测试生成密钥的 ACL，并要求递归删除真正成功。本任务失败运行留下的两个目录经检查后以精确路径的 PowerShell 操作清除。没有改变仓库、用户或生产游标密钥的 ACL；生产密钥创建时仍保持仅所有者权限。
