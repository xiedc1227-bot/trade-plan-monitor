## 2. Root cause and bounded repair

`AlertOutbox` already reconstructed both canonical event variants, but `notifications/channels.py::_require_event` accepted only exact legacy `AlertEvent`. `NotificationDispatcher` and the channel protocol also advertised the legacy type only. This turned every production `ExplicitAlertEvent` into `CHANNEL_FAILURE`, causing bounded retries and eventual failure even though a separate committed-event/API path made reminders visible.

The repair introduces one typed `NotificationEvent = AlertEvent | ExplicitAlertEvent` boundary and carries it through `NotificationChannel`, `NotificationDispatcher`, `InAppChannel`, `ConsoleChannel`, and `WebhookChannel`. Runtime validation remains exact: subclasses and arbitrary objects are rejected. The Webhook adapter keeps its existing seven-field public envelope; it now dispatches legacy enum signal types and explicit string signal types according to the event variant. No exception is hidden as success and no explicit event is converted into a legacy event.

This restores the already declared R08 E06/E09/E10 consumer contract rather than changing the API or plan specification. The existing `GET /api/v1/plan-capabilities` result (`publicActivationAvailable=true`, `isolatedTrustedReviewOnly=false`, no pending requirements) is no longer contradicted by the mandatory IN_APP consumer in this N01 path. Unknown event versions still fail closed. No new channel, service, dependency, migration, schema, OpenAPI field, prompt, or capability platform was added.
