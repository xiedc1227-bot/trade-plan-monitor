## Implemented contract

- The stored confirmation has exactly two explicit outcomes: `CLEAR` and `RISK_PRESENT`. Its absence, a hash mismatch after plan content changes, expiry, or a confirmation after the evaluation cutoff becomes the third production state: unknown (`None`). Unknown is never coerced to `False` and therefore continues to fail closed through `MANUAL_EVENT_RISK_CLEAR`.
- SQLite migration `0012_manual_event_risk` persists symbol, plan hash, status, expiry, confirmation time, and optimistic revision. Each accepted write adds a `MANUAL_EVENT_RISK_CONFIRMED` audit record. Downgrade refuses to discard existing confirmation evidence.
- The normal production context reads the confirmation in the same unit of work as active-plan and risk facts before constructing `EvaluationContext`. This replaces the former hard-coded `manual_event_risk=None` without changing official-close risk acknowledgement behavior.
- The local API exposes `GET /api/v1/manual-event-risk` and `POST /api/v1/manual-event-risk-confirmations`. The read model makes missing active plan, missing confirmation, plan-content change, and expiry explicit. Writes are plan-hash scoped, revision checked, audited, and idempotently replayable.
- `/stocks/:symbol` composes a dedicated `ManualEventRiskPanel`. It shows authoritative status, plan version, expiry, confirmation time, and an explicit unknown reason. A normal user chooses a conclusion and expiry, reviews the native confirmation dialog, then submits an idempotent command; browser code never derives a clear outcome from unknown state.
