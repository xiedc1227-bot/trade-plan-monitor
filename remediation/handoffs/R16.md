## 1. Result and limits

The production scheduler still makes its ordinary five-index acquisition at each new completed five-minute cutoff. On the immediately following minute, `RuntimeMarketIndexService.retry_publication_lag` claims at most one retry for that cutoff and selects only same-cutoff snapshots with nonempty issues restricted to `MISSING_FIVE_MINUTE_BAR` and `STALE_DATA`. Provider, identity, gap, and other failures are not retry targets. It reacquires with the selected snapshot's original fact requests and the existing turnover minimum counts. The returned batch contains **only retried indexes**, so persistence leaves already-`LIVE` and independently `BLOCKED` heads untouched. A failed retry becomes visibly `BLOCKED`; it is not ranked behind the former stale capture. An in-flight retry is discarded if normal acquisition replaced its original snapshot with a new cutoff or requirements. Normal `prepare` and the coordinator's provider-first revision cache remain unchanged, so fresh requirements, content revisions, and the next trading day still fetch normally.

A new production test exposed a separate pre-existing persistence mismatch within this step's acceptance boundary. A Schema v2 plan with no index leaf received an informational shared snapshot, while the decision engine correctly omitted plan-owned index evidence; persistence then rejected the otherwise valid stock evaluation. The dependency check now allows that informational context only for a stock-only plan. Plans with index leaves retain the strict presence, immutable-hash, and durable-snapshot checks. In a production pipeline comparison, the same stock-only plan committed with either a `LIVE` or `BLOCKED` optional index and had the same result hash, signal intent, next step, and condition outcomes. The failed index stayed `BLOCKED`; it was not treated as a satisfied index condition. Existing index-leaf failure and hash-mismatch tests passed.
